# Постоянный сервер CRM

Подготовка этапа «логика и сервер», 17.11.2026. Рабочее включение — этап выпуска.
Проверенные пути существующих служб есть в `env.example`; перед выпуском повторно
сверить их с Docker mounts. Секреты в этот каталог не копировать.

## Размещение

- Linux-ВМ: PostgreSQL, существующий primary, новый API с планировщиком и обмен.
  `compose.yml` заменяет именно `crm-pilot-api` и `crm-legacy-exchange` после
  остановки старых экземпляров. Бот, parser VPN и остальные приложения сохраняются.
- Отдельный Windows-хост с Excel: мобильный BFF и Python-исполнитель. Нужна
  выделенная вошедшая сессия Windows; Task Scheduler использует Interactive,
  а не Session 0. Блокировка экрана допустима; выход пользователя останавливает
  интерактивную сессию. Этот хост ещё не предоставлен. ПК разработчика не является
  постоянным исполнителем.
- Caddy принимает `/mobile/` и передаёт запросы Windows по TLS с проверкой доверия
  и имени. `/crm-pilot/` направляется в Linux API. Пример фрагмента проверен
  установленным Caddy 2.11.7. Существующие VPN/parser/update-блоки сохраняются.

## Подготовить пакет выпуска

1. Из точного коммита собрать Linux-образ по `server/Dockerfile.crm` с проверенным
   `CRM_BASE_IMAGE`; сохранить digest, использовать его в `CRM_IMAGE`.
   Операторский инструмент находится в образе `/app/tools/crm_runtime.py`.
2. Вычитать текущие primary-модули в приватный baseline и выполнить
   `python tools/crm_primary_package.py --baseline <baseline> --output <new-package>`.
   Manifest содержит SHA до/после каждого файла. Перед применением проверить
   **все** исходные SHA и отсутствие файлов, для которых before_sha256=null.
   При расхождении пересобрать патч поверх нового baseline. Не заменять весь
   primary исходниками CRM: на рабочем сервере есть более новые независимые функции.
3. Для Windows подготовить исходники, проверенный mobile build, venv с текущими
   зависимостями сервера/пульта, установленный Excel. Python/Excel-файлы выполняются
   через xlwings. Секрет сессий — отдельные 32 случайных байта; сохранить вместе
   с TLS-ключом в каталоге, доступном только выделенному пользователю и администраторам.
   DPAPI-профили и очередь принадлежат этому же пользователю.
4. Заполнить `windows.example.json` и зарегистрировать:
   `Register-CrmMobile.ps1 -Config <absolute-config> -User <dedicated-user>`.
   Задание восстанавливается после ошибки; для первого запуска использовать
   `Start-ScheduledTask -TaskName 'Rimborso CRM Mobile'` в вошедшей сессии.
   Входной 8443 разрешить только Linux-ВМ; DNS/SAN сертификата, адрес Windows и
   доверенный CA задать Caddy через CRM_WINDOWS_UPSTREAM, CRM_WINDOWS_TLS_NAME,
   CRM_WINDOWS_CA_FILE. Проверку TLS не отключать.

## Миграция и адресное включение

Операцию выпуска записать в приватный журнал с operation_id, точными пакетами и
квитанцией. До изменений остановить писателей/обмен; сохранить согласованные
backup PostgreSQL и SQLite, код primary, конфигурации, файловые права и ключи.
SQLite копировать через backup API или при полностью остановленных писателях,
а не одним копированием main-файла работающей WAL-базы.

- На прежней SQLite проверить права uid 1000 нового API: чтение/запись базы и
  создание WAL/journal в каталоге. Прежний primary работает от root; новый API
  не переводить в root ради обхода ошибки. Согласованные ACL выставляются на
  точный каталог/БД при выпуске с сохранением прежних прав. Каталог `/status`
  и `/documents` должен быть доступен uid 1000. Проверить это до запуска.
- В окружении оператора с явным owner DSN выполнить `crm_runtime.py migrate`:
  схема 4/6 → 7 и дополнительные права crm_app в одной транзакции. API получает
  только app DSN; обмен сохраняет свой worker DSN. Owner DSN не монтировать в API.
- Применить подготовленный hash-bound primary-патч с backup; сохранить существующие
  `/api/manager/entry_profile`, `/entry_revoke` и проверки неоднозначных имён.
  В primary явно включить `HARD_CRM_MOBILE=1`, `HARD_CRM_DESKTOP=1`.
- В приватном `contracts.json` перечислить точные canonical UUID перехода.
  С заданными `HARD_CRM_DATABASE_URL_FILE` и `HARD_CRM_PRIMARY_DB` выполнить
  `crm_runtime.py plan --contracts <file>`, затем `activate --contracts <file>
  --expected-sha256 <selection_sha256>`. Нет команды «включить всё» по умолчанию.
  Plan подтверждает сопоставление договора/кредитора и исходное назначение.
- Сначала SQLite закрывает прежние записи по выбранным договорам, затем PostgreSQL
  включает CRM. Разрыв между commit восстанавливается повторением того же activate.
  Одновременной работы двух писателей нет. Другие договоры остаются в прежнем режиме.
- Запустить новые API/обмен, проверить `/health` обоих контуров, затем применить
  проверенный `Caddy.fragment`. Сначала validate, после reload — реальный TLS-запрос.
  Пройти вход/отзыв устройства, импорт → назначение → работу → отчёт и проверить
  обе БД/квитанции. До этой проверки выпуск не считается включённым.

## Повседневная работа и восстановление

`crm_runtime.py status` показывает режим, heartbeat, ожидающие проекции и конфликты.
API `/health` требует актуальную схему и здоровый планировщик; exchange health
читает свою сохранённую квитанцию. Зелёный HTTP сам по себе не подтверждает работу
Excel: отдельно проверить Windows-сеанс, `/mobile/health` и результат выгрузки.

Распределение хранится в PostgreSQL; primary получает его устойчивой очередью.
Старый импорт обновляет бизнес-поля, сохраняет ответственность CRM, а расходящиеся
назначения/результаты оставляет в списке сверки. Журнал source conflicts append-only:
его rowid — курсор переноса, записи не удалять и таблицу не пересоздавать отдельно.
Звонки/выезды и правки полей проецируются с квитанцией; повтор после потерянного
ответа не создаёт второй факт. Новые сущности CRM сохраняются в canonical, а не
превращаются в фиктивные звонки прежней базы.

Планировщик работает без открытого клиента. Перед каждой порцией он перепроверяет
действующий вход/права; отзыв доступа блокирует работу. Трёхчасовые снимки фиксируют
реальное наблюдение; пропущенные при простое отсечки задним числом не придумываются.
После истечения/отзыва входа автор входит заново, затем разрешённая работа продолжается.

Windows BFF после перезапуска присоединяется к прежнему Python-процессу; файловая
блокировка запрещает второй исполнитель того же профиля. Работающий исполнитель
не завершается при закрытии браузера/BFF. Неизвестный результат внешней отправки
или записи сначала сверяется; очередь не отправляется повторно вслепую. Удаление
профиля и DPAPI-записей не является способом перезапуска.

При неудаче включения остановить новые писатели, сохранить состояние и повторить
незавершённую идемпотентную операцию либо восстановить согласованную пару backup.
Не удалять fence-триггеры и не включать старых писателей поверх уже принятых CRM
результатов. Возврат одного старого EXE/образа не откатывает рабочие данные.
