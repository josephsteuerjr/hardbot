# Реестры СНГ: отчёт для согласования ночного цикла

Дата: 28.07.2026

Статус: реализация завершена, полный прогон на копиях пройден

Запись в рабочие реестры: **не выполнялась**

## 1. Что подготовлено

Подготовлен единый конфигурируемый цикл для общего реестра СНГ и личных
портфелей сотрудников:

- HARD: Душанбе, Худжанд, Ташкент и Самарканд;
- SOFT: Таджикистан и Узбекистан;
- отдельная HARD-группа `ГПХ Агент выезд`;
- 58 действующих личных книг и один общий реестр;
- Андижан известен системе, но отключён конфигурацией.

Старый скрипт сборки/разборки не используется и автоматически не запускается.

## 2. Согласуемая логика движения данных

### Данные сотрудников

Все 21 жёлтое поле принадлежат сотрудникам и передаются из личного портфеля в
общий реестр. Перед запуском программа автоматически сверяет фактическую жёлтую
заливку заголовков общего реестра с конфигурацией. Расхождение останавливает
цикл.

К жёлтым относятся:

- суммы, даты и прогноз платежа сотрудника;
- общий результат;
- основной и дополнительный телефон/адрес;
- дата и комментарий выезда;
- дата встречи;
- результаты контакта и визита;
- HARD- и SOFT-поля звонка и комментариев.

У уже существующей личной строки эти поля не перезаписываются старой версией из
общего. Пустое поле сотрудника не удаляет непустое значение общего во время
сборки.

### Данные аналитиков

Нежёлтые профильные поля передаются из общего реестра сотрудникам. Аналитические
`Текущие платежи` и история `Оплаты за MM.YY` остаются только в общем и не
попадают в личные книги.

### Защита локальных значений

Если в общем пусты `Телефон` или `Город`, существующее непротиворечивое значение
личной книги сохраняется.

HARD- и SOFT-комментарии сопоставляются по названию и профилю, а не по физическому
номеру столбца. Это исключает прежнее смещение комментария HARD в SOFT.

## 3. Перераспределение кейсов

Канонический ответственный берётся из общего реестра.

- Новые закрепления направляются указанному сотруднику.
- Строка удаляется из книги прежнего сотрудника только при точном подтверждении
  полем `пред отв`.
- При подтверждённой передаче жёлтая история прежнего сотрудника передаётся
  новому как fallback; уже заполненное значение нового владельца приоритетно.
- Если доказательства снятия нет, спорная копия сохраняется read-only.
- Если один КД имеет неоднозначных текущих владельцев в общем, весь пакет
  блокируется.

На свежем снимке четыре строки доказанно снимаются по `пред отв`, девять строк
без соответствующего КД в общем сохраняются read-only. Фактических ячеек
передачи истории новому владельцу на этом снимке нет.

## 4. Даты

`Дата выезда` переносится буквально, включая точки, текст, нестандартные записи
и дату со временем. Массового преобразования дат в единый формат нет.

В остальных полях 117 исторических значений не соответствуют формальному типу
колонки. По принятому решению они сохраняются буквально и отражаются
предупреждением в отчёте, а не отбрасываются.

## 5. Закрытие месяца

В последний календарный день выполняются две независимые операции:

1. В личных книгах очищаются только жёлтые
   `Сумма последнего платежа` и `Дата последнего платежа`. Эти значения не
   архивируются.
2. В общем реестре аналитические `Текущие платежи` копируются значениями в новую
   колонку `Оплаты за MM.YY`, затем текущая колонка очищается.

Повторный запуск не создаёт второй столбец. Если история и текущие платежи
содержат разные непустые значения либо в изменяемом диапазоне обнаружена
формула, закрытие блокируется.

На копиях полностью проверено закрытие июля: перенесено 1 710 аналитических
платежей, очищено 2 446 непустых платёжных ячеек сотрудников, повторный запуск
получил статус `already_complete`.

## 6. Защита от потери данных

Рабочий цикл:

```text
локальные копии → точный план → локальный Excel-staging
→ полная validation → повторный live-preflight
→ соседние backups → атомарная публикация → postcheck
```

Реализованы:

- чтение только локальных копий, без открытия live-книг через Excel;
- SHA-256 и повторная проверка каждого источника перед публикацией;
- полный список разрешённых поклеточных изменений;
- проверка всех ячеек, листов, формул, фильтров и форматов;
- запрет незаявленных изменений;
- соседний backup каждой цели до замены;
- атомарная замена и rollback при любой ошибке;
- общий реестр публикуется последним;
- блокировка одновременного второго запуска;
- технические уведомления только владельцу.

Открытый или изменившийся после snapshot файл не перезаписывается.

## 8. Текущее ограничение перед ручным запуском

После validation две личные книги оказались реально открыты:

- Рахимов Махмадулло;

Общий реестр свободен. Текущая безопасная политика `block` остановит публикацию

клиентского протокола, но отключён до выдачи ИТ отдельного минимального права.

## 9. Что требуется согласовать

Просим подтвердить:

1. 21 жёлтое поле является зоной ответственности сотрудника и движется вверх.
2. Нежёлтые профильные данные движутся из общего вниз.
3. Аналитические текущие платежи остаются только в общем.
4. Строка прежнего сотрудника удаляется только при точном совпадении `пред отв`.
5. При подтверждённой передаче жёлтая история следует новому владельцу.
6. Нестандартные исторические даты сохраняются буквально без массовой
   нормализации.
7. На границе месяца действуют две отдельные платёжные операции, описанные выше.
8. Первый запуск выполняется вручную только при нулевой занятости файлов.

## 10. Порядок первого ручного запуска

После согласования:

1. закрыть все целевые книги;
2. повторно получить нулевую занятость;
3. снять новый snapshot;
4. повторить полный staging и validation;
5. сверить warnings, список строк и полный digest;
6. получить отдельное разрешение владельца на публикацию;
7. применить первый baseline в режиме `block`;
8. проверить backups, SHA, журнал и итоговый baseline.

Планировщик, автопубликация и принудительное SMB-закрытие включаются отдельно
после успешного ручного цикла. Сейчас:

```json
{
  "scheduler.enabled": false,
  "scheduler.publish": false,
  "force_close.enabled": false,
  "notifications.audience": "owner_only"
}
```
