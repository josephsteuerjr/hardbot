# План: вход по логину и паролю, привязка устройств, закрытие уязвимостей

Статус: РЕАЛИЗУЕТСЯ (сервер и CLI готовы 14.10, клиенты в работе). Основан
на адверсарном ревью 13.10 (полный отчёт: `_local/adversarial-review-2026-10-13-scope4/REVIEW.md`)
и на произведённом затем картировании кода входа. Все ссылки вида `файл:строка`
— текущее рабочее дерево. Список сотрудников по офисам для заведения аккаунтов:
`_local/staff-by-office-2026-10-14/` (62 ФИО, без ГПХ/курьеров).

Решение владельца (14.10, согласовано с ИБ и ИТ): персональные ссылки для
сотрудников заменяются входом по логину и паролю (2FA — следующим этапом).
Один аккаунт работает и на телефоне (публичный «человеческий» адрес от ИТ,
без DuckDNS), и на компьютере во внутренней сети (внутренний адрес ВМ).
Телефон обязан иметь снимаемый в офисе отпечаток устройства; вход с чужого
устройства запрещён, кроме аварийного процесса с одобрением руководителя.

## 1. Ситуация: как вход устроен сегодня

Три класса входа, все через одноразовые ссылки:

- **Телефон (PWA)**: короткая ссылка `/i/<код>` → `redeemCode()`
  (`server/miniapp/index.html:1720`) → `/api/redeem` → токен в
  `localStorage['app_token']` (index.html:1704), заголовок `X-App-Token`
  (index.html:2115). Сервер расходует ссылку атомарно
  (`db.redeem_app_link`, server/db.py:2376) и пишет токен в `app_tokens`.
- **ПК выездника (Хард/Софт)**: та же ссылка → `enrollField()`
  (hard-desk/src/main/net.ts:255) → `/api/agent/device/enroll` → токен в
  DPAPI-файле `field.key` (store.ts:123). Класс отдельный: «ПК не вытесняет
  телефон» (web.py:5108, db.enroll_agent_device — db.py:2768).
- **Пульты (руководитель/аналитик/СБ)**: ссылка → `enroll()` (net.ts:201) →
  `manager_devices`; админ-ключи → `admin_devices` (обмен кодом из CLI
  `server/admin_access.py` — «право впустить = доступ к серверу»).

Правила устройств сегодня:
- «Одно ФИО — одно устройство» есть ТОЛЬКО для телефонов: `agent_bind.approved`
  (db.py:946), занятость проверяет `employee_taken_by` (db.py:1876), заявка без
  одобрения ждёт ADMIN (web.py:1176), одобрение руководителем вытесняет старое
  устройство (`set_bind` db.py:1896 → `unbind` db.py:2190 гасит токены и ссылки).
- ПК-устройства (`agent_devices`) ничем не ограничены по числу; «отпечаток» ПК —
  строка `hostname · user` (net.ts:55), для телефона отпечатка НЕТ вовсе: сервер
  классифицирует только UA+standalone (`_agent_class`, web.py:3049).
- Журнала входов (кто, когда, с какого устройства, удача/отказ) нет — аудит
  фиксирует лишь отдельные события.

Слабые места, найденные ревью 13.10 (полный список — в REVIEW.md), критичные
именно для смены входа:

## 2. Целевая картина

1. **Аккаунт** = логин (транслит ФИО, задаётся при заведении) + пароль (scrypt,
   принудительная смена при первом входе). Владелец/ИБ завозит аккаунты
   серверным CLI без HTTP-ручек записи — как `admin_access.py`. 2FA (TOTP) —
   задел: поле в схеме, шаг в логине, включение CLI.
2. **Два входа, один аккаунт**: телефон — публичный https-адрес ИТ; ПК —
   внутренний адрес ВМ (https с внутренним CA или plain-http для приватных IP —
   патч link.ts уже в 3.1.5). Токен един для обоих входов, класс токена
   определяется типом устройства, не адресом.
3. **Устройство-пропуск для телефонов**: вход только с привязанного устройства;
   привязка снимается в офисе одноразовым кодом руководителя («на глазах»).
   Каждый вход/отказ пишется в журнал с отпечатком, моделью, IP и адресом входа
   (публичный/внутренний) — «вход в аккаунт прозрачно виден».
4. **Аварийный вход** (сломался телефон): на новом устройстве — экран
   «Устройство не закреплено» + код запроса; руководитель в офисе сверяет
   человека и одобряет: прежнее устройство гасится автоматически, новое
   становится доверенным, всё фиксируется автором одобрения. Вход разрешён
   только после одобрения.
5. ПК не требует отпечатка такого же класса (он в корп. сети, машина именована
   и учтена ИТ), но имя машины+пользователя и журнал входов пишутся так же.

## 3. Серверная часть

Схема (инициализация в init_db по образцу employee_identity, db.py:857):

```sql
CREATE TABLE accounts (            -- логин-пароль вместо ссылки
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  username TEXT NOT NULL UNIQUE,          -- нормализованный транслит
  employee TEXT NOT NULL,                 -- ФИО как в реестрах
  role TEXT NOT NULL DEFAULT 'agent',     -- agent|manager|security|full
  password_hash TEXT NOT NULL,            -- scrypt$N$r$p$salt$hash
  must_change_password INTEGER NOT NULL DEFAULT 1,
  status TEXT NOT NULL DEFAULT 'active',  -- active|disabled
  totp_secret TEXT,                       -- задел 2FA (пока NULL)
  created_by TEXT, created_at TEXT, updated_at TEXT,
  failed_attempts INTEGER NOT NULL DEFAULT 0,
  locked_until TEXT
);
CREATE TABLE account_devices (       -- доверенные устройства (телефоны)
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  account_id INTEGER NOT NULL REFERENCES accounts(id),
  fingerprint TEXT NOT NULL,              -- sha-256 собранного профиля
  label TEXT NOT NULL,                    -- «iPhone · iOS 17 · 390×844»
  entrance TEXT NOT NULL DEFAULT 'public',
  bound_by TEXT NOT NULL,                 -- кем одобрено (руководитель/CLI)
  bound_at TEXT NOT NULL,
  last_seen TEXT, revoked_at TEXT
);
CREATE TABLE account_logins (        -- журнал: каждый вход и отказ
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  account_id INTEGER, username_attempted TEXT NOT NULL,
  kind TEXT NOT NULL,                     -- ok|bad_password|locked|no_device|disabled|bound
  fingerprint TEXT, label TEXT, ip TEXT, entrance TEXT,
  at TEXT NOT NULL
);
-- связка выданных токенов с аккаунтом:
ALTER TABLE agent_devices   ADD COLUMN account_id INTEGER;
ALTER TABLE manager_devices ADD COLUMN account_id INTEGER;
```

Эндпоинты (новые, web.py; все с IP-счётчиком `_admin_too_many_fails`,
scope="account"):

- `POST /api/account/login` `{username, password, entrance, device:{kind:
  phone|desktop, fp, label, name}}` →
  - проверка блокировки аккаунта (5 неудач → 15 минут, снимается успешом) и
    статуса; неудача — строка в `account_logins` (bad_password/locked/disabled);
  - `kind=phone` и нет доверенного устройства с этим `fp` → 403 `no_device`
    + создаётся **запрос привязки** (см. §5), вход не выдаётся;
  - успех → токен существующего класса: agent → INSERT в `agent_devices`
    (telegram_id из agent_bind при наличии, иначе NULL — путь уже поддержан
    middleware web.py:215–231), manager/security/full → `manager_devices`
    (требуется telegram_id из `managers`, иначе аккаунт не заводится);
  - ответ `{ok, token, employee, role, must_change_password}`; строка `ok` в
    журнал.
- `POST /api/account/password` `{username, current, new}` — смена, снимает
  `must_change`, не требует токена (доказательство — текущий пароль).
- `GET /api/account/sessions` — «Мои входы» по токену (через account_id
  устройства), последние 30 записей.
- `POST /api/account/logout` — гасит своё устройство (образец:
  `_agent_device_logout` web.py).
- Привязка: `POST /api/account/bind` `{username, password, code, device}` —
  код одноразовый из `account_bind_codes` (см. §5); `POST /api/manager/
  device_requests` и `POST /api/manager/device_resolve` — списки и одобрение
  для руководителя; admin-руки: `/admin/accounts.json` (чтение, с офисами и
  журналами — `office_of` уже есть, db.py:3116).

CLI-регистратор `server/account_access.py` (по образцу admin_access.py, запуск
`docker compose exec -T app python /app/account_access.py …`): `create
--employee "ФИО" --office Душанбе [--role agent]` (логин генерируется, пароль
печатается один раз), `bulk --csv staff.csv` (колонки: ФИО; офис; контур —
CSV собирается из `_local/staff-by-office-2026-10-14/`), `passwd --username`,
`disable/enable`, `list --by-office`, `sessions --username`.

Совместимость: ссылки продолжают работать весь переход (тот же uid/employee);
флаг отключения ссылок для сотрудников — последним этапом, решением владельца.

## 4. Отпечаток телефона

Сегодня PWA ничего о себе не сообщает, кроме UA и `standalone` (grep по
index.html: deviceMemory/hardwareConcurrency/model — 0 попаданий). Добавляем
сборку профиля в PWA: модель из UA, `navigator.platform`, экран+DPR, часовой
пояс, языки, `hardwareConcurrency`, `deviceMemory`, и стабильный UUID,
рождённый при первой сборке и хранимый в IndexedDB. Итог: `fp = sha-256(профиль
+ uuid)` и человекочитаемая строка-«шильдик». Ограничение проговариваем честно:
очистка данных сайта/переустановка PWA рождает новый UUID → устройство выглядит
новым → аварийный процесс. Это соответствует требованию ИБ (любая смена
устройства видна), но текст на экране должен объяснять, что произошло.

«Снять в офисе один раз» = первая привязка кодом руководителя (см. §5): при
выдаче телефона сотрудник при руководителе вводит логин/пароль, руководитель
даёт код привязки со своего экрана, PWA показывает «Устройство закреплено за
вами» и шильдик. Повторная привязка — только через аварийный процесс.

## 5. Активация доступа (решение 14.10, реализовано)

Подтверждает ТОЛЬКО администратор (роль в системе называется «администратор»,
не «владелец»): это Егор и Сергей Мазанов, их админ-вариант подтверждается
самим доступом к серверу (адрес + root-пароль) — CLI/admin-ручки работают из
SSH-сессии сервера или с админ-устройства пульта.

- **Сотрудники (agent)**: ввод на телефоне (GPS обязателен) и ПК в офисе —
  «ввели и там, и там»; руководитель пересылает список «кто ввёл»; доступ
  открывает ОДНО подтверждение администратора.
- **Руководители и аналитик (manager/security/full/analyst)**: условия
  двойного ввода НЕТ; активация аккаунта и каждого устройства требует
  ДВУХ подтверждений РАЗНЫХ администраторов (подтверждения копятся, в
  ответе видно «1 из 2»). Токен — класса manager_devices; внутренний номер пользователя берётся
  из managers по ФИО, а если человека там нет — создаётся запись со
  служебным id (легаси-поле telegram_id к Телеграму отношения не имеет).
- До активации вход «работает, но без данных»: экран ожидания; повторный
  вход с нового устройства — тот же круг; подтверждение нового телефона
  гасит прежний. Ссылочный вход продолжает работать весь переход.

## 6. Интерфейсы (по существующему дизайн-коду)

- **PWA**: форма «Логин и пароль» встаёт в точке нынешнего экрана входа
  (`renderAppAuthGone`, index.html:1859; `enterCode` 1990 остаётся переходным
  путём для ссылок). Новые состояния: «Устройство не закреплено» (заявка),
  «Смена пароля» (первый вход), «Мои входы» (журнал: дата, шильдик, адрес
  входа). Стили и уведомляющая полоса офлайн-очереди не меняются.
- **Десктоп Хард/Софт**: экран входа `enrollFieldScreen` (app.ts:162) получает
  вторую вкладку «Логин и пароль» (логин, пароль, сервер по умолчанию —
  внутренний адрес, валидация как в link.ts); отпечаток ПК = hostname · user ·
  sha-256(machine-id) (расширение `deviceName`, net.ts:55). «Мои входы» и
  «Сменить пароль» — в меню раздела «Ещё» (misc.ts). Обязательные попутные
  фиксы из §1: очистка/перенос очереди при смене аккаунта и guard переноса.
- **Руководитель**: раздел «Вход команды» (misc.ts:54) расширяется до «Вход и
  устройства»: существующая таблица ссылок + колонка «Телефон» (шильдик,
  последний вход) + панель «Заявки на закрепление» (кто, прежний, новый, одна
  кнопка). Дизайн — те же DataTable/chips/bulk, новые строки не изобретаем.
- **Аналитик**: новый раздел «Аккаунты и устройства» по образцу «Руководители»
  (analyst/managers.ts:36–72: таблица + bulk): аккаунты по офисам, журнал
  входов, гашение устройства, сброс пароля (CLI-хук недоступен — HTTP только
  чтение и гашение; заводит аккаунты владелец на сервере).
- **СБ**: read-only журнал входов по людям/офисам (существующий read-only
  паттерн `_require_field_write`-инверсий).
- **Rust-пульт руководителя**: переводится на логин-пароль последним, после
  фикса P1 с токенами (settings.rs) — сначала починить, потом менять вход.

## 8. Решения владельца (закрыты 14.10)

1. Логины: транслит ФИО, генерируются при заведении (CLI), подтверждает список
   владелец при выдаче в офисе.
2. Подтверждение: ТОЛЬКО владелец (руководителям нельзя доверять); список
   «кто ввёл» руководитель пересылает владельцу кнопкой «Скопировать».
3. Внутренний вход ПК: внутренний адрес ВМ; для 3.1.4+ — https (Caddy) или
   plain-http приватных IP (патч 3.1.5 уже в исходниках).
4. Люди в двух контурах (Нарбеков, Уткиров, Эркинов): один аккаунт на
   человека — контур, как и сегодня, выбирается сервером по портфелю.
5. Руководители/аналитик/СБ: переводятся на логин-пароль следующей волной
   (после 2FA-задела); сейчас остаются на ссылках/ключах.
6. Пароли: ≥8 символов с буквой и цифрой, смена при первом входе; GPS на
   телефоне обязателен при входе (отклонили разрешение — переустановка PWA).

7. Открытый вопрос (для ИТ): внутренний адрес для десктопа — рекомендован
   https от контейнерного Caddy на LAN-интерфейсе ВМ либо публикация порта
   приложения только в корп. сети; решение за ИТ при выдаче публичного имени.
