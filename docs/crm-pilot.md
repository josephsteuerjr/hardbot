# CRM: отдельный кандидат 3.3.0-pilot.1

Кандидат не включает включение CRM на рабочем сервере. Его EXE использует
`ru.rimborso.crm.pilot`, отдельную регистрацию Windows и профиль
`%LOCALAPPDATA%/Hard/crm-pilot/data`. Первый запуск открывает синтетический
сценарий. Реальные сотрудники автоматически в группу не включаются.
Автообновление выключено; рабочие stable/pilot feeds других программ не меняются.

## Проверка кандидата

1. Установить current-user через собственный мастер. Открыть первого клиента.
2. В «Подключение» включить проверку офлайн. Сохранить звонок по двум договорам.
3. Проверить «Очередь», закрыть и снова открыть программу. После подключения
   будет один исходный звонок и его точное подтверждение. Устаревшие поля требуют
   сверки; более свежие значения не затираются.
4. В синтетическом сценарии выбрать руководителя. В «Реестры» записать книги по
   маршрутам `general:demo` и `personal:demo`. Доставка подтверждается только
   после записи и повторного чтения обеих книг, по конкретному ID события.
5. Изменить комментарий в копии книги, выбрать «Сверить изменения Excel»,
   проверить сравнение и применить. История получит отдельную правку Excel.
   Обычный повторный экспорт не порождает новых рабочих действий.
6. Проверить скрипт: черновик, публикация, открытая версия в форме звонка.
   Проверить начало смены, перерыв, продолжение, завершение и серверное время.
7. Панель «Внедрение» показывает группу из кадрового источника, включая
   участника без запуска, плановые смены 2/2, числители/знаменатели, покрытие,
   маршруты доставки, фильтры периода, команды, роли, версии и функции.

## Модель и границы

`server/crm` содержит отдельные сущности person/contract/employee/assignment,
неизменяемые события и исправления с причиной. Договор определяется кредитором
и внешним номером; имя и телефон не используются для автоматического склеивания.
Деньги хранятся десятичными строками с валютой. Заявленная оплата не считается
подтверждённым поступлением. Задачи имеют ревизию завершения. Документы проверяются
по SHA-256, хранятся вне исходников и доступны по правам договора.

Запись команды, событие, проекция, ожидаемые маршруты, outbox и квитанция ответа
фиксируются одной SQLite-транзакцией. Тот же operation_id с другим телом
отклоняется. При потере ответа повтор возвращает исходную квитанцию.
Проекции восстанавливаются из журнала. Метрики обрабатываются отдельным worker;
его отставание видно в отчёте и не откатывает принятую работу.

Очередь, черновики, локальные снимки и журнал выгрузок защищены прямым DPAPI
текущего пользователя. Шифрование не зависит от сохранения Local State Electron.
Неподтверждённые операции не удаляются при ошибке, смене роли или обновлении.
Техническая очередь ограничена; пропуски отражаются отдельным событием.

## Excel

Единая книга содержит лист «Портфель» и скрытый манифест `_CRM`: версия,
export_id, период, scope, ID договоров и исходные ревизии. Сервер хранит baseline.
Новый XLSX и копии XLSX/XLSM/XLSB проверяются через установленный Microsoft Excel.
Исходная книга не переписывается. Неизвестные листы/столбцы, формулы и VBA
сохраняются; конфликт с формулой останавливает публикацию копии. Макросы при
автоматизации отключены. Ячейки читаются пакетно, изменённые диапазоны записываются
пакетно. При отсутствии «Портфеля» он создаётся только в копии.

Пусто означает отсутствие ручного изменения; `0` — значение; `[[CLEAR]]` —
явная очистка. Пропущенная строка не снимает назначение. Импорт неизвестной версии,
подменённого scope, дубликата ID или изменённого файла отклоняется.
Конфликт требует выбора Excel/сервер. После выбора текущие ревизии проверяются
повторно. Неизвестная старая книга сначала становится версионированной копией;
импорт без baseline не применяется.

## Подготовка отдельного сервера

Подготовку выполняет оператор на отдельной локальной копии базы:

```text
python tools/crm_pilot.py prepare --source source.sqlite3 --destination pilot.sqlite3 --mapping approved-mapping.json
python tools/crm_pilot.py rebuild --database pilot.sqlite3
python tools/crm_pilot.py release-legacy-guard --database pilot.sqlite3
```

Последняя команда только показывает план. `--apply` создаёт локальный backup,
снимает блокировки старых writers и сохраняет всю CRM-историю. Откат кода сам
по себе не означает удаление новых событий или восстановление старого снимка
поверх принятой работы. Перед переключением: остановить writers, сохранить базу
и документы, проверить очередь/последние квитанции, пересобрать совместимые
проекции; после — сверить counts, SHA и контрольные операции.

Карта миграции содержит `source`, `contracts`, `employees`. Контракт сопоставляется
по старому ID с creditor_id/external_id/person_ref/currency; объединение person
требует evidence. Каждый сотрудник задаётся явно: staff_id, name, team_id, role,
capabilities, timezone, starts_at, actor_uids, assignments и evidence.
Без карты сохраняются отдельные люди по договору и журнал неоднозначностей;
доступы и состав пилота не выдумываются. Повтор миграции той же карты идемпотентен.

Серверные маршруты `/api/crm/*`, `/admin/crm/*` включаются только переменной
`HARD_CRM_PILOT=1`. Используется существующий вход и серверная проверка актуальных
прав. Старые изменяющие HTTP-маршруты возвращают `crm_cutover`, а SQL-триггеры
блокируют обход канонической записи через clients/calls/visits.
Это включается только на отдельном подготовленном стенде. Кандидат блокирует
подключение к рабочему `hard.rimborso.ru:443`.

До запуска реальной группы нужны подтверждённые связи сотрудников, назначений,
состав группы/периоды доступа, график смен с источником, ожидаемые реестры и сроки
доставки, выбранная политика хранения диагностики. Эти организационные решения
не подменены синтетическим сценарием. Группа задаётся через `cohort`, смены через
`plan`, маршруты — версионированными `crm_route_policies`.

## Диагностика и интерпретация

Корневое действие учитывается один раз даже при нескольких договорах. Исправление,
ручной импорт, повтор отправки и техническое открытие экрана не равны новому
полезному действию. Для времени используются серверные отметки и монотонные
якоря; непроверенное время клиента показывается как неопределённое. Заявленные
смены не являются табелем или расчётом оплаты.

В диагностику передаются только разрешённые типы событий, ID операции,
версия/функция, код ошибки и ограниченная длительность. Текстов заметок,
контактов клиентов, клавиатуры, скриншотов и геолокации там нет.
Срок хранения сырых событий допускает 30–365 дней; предлагаемые 90 дней ещё
не являются утверждённой политикой. Очистка запускается владельцем явно.
История работы хранится отдельно. Недоступность, пропуски, неизвестный график,
будущая первая смена и отсутствие работы различаются. Доля работы через
приложение неизвестна, пока внешний поток не наблюдается полностью.
Цели пилота и пороги не назначены владельцу автоматически; панель показывает
наблюдаемые значения и полноту, без рейтингов сотрудников.

## Воспроизводимая проверка

Серверные проверки: `pytest tests/test_crm_*.py tests/test_call_scripts.py`.
Native Excel: `tests/test_crm_workbook.py` на Windows с Excel.
Живой UI: `hard-desk/tools/test-crm-pilot.cjs`.
Аварийный цикл: `hard-desk/tools/test-crm-recovery.cjs`, фазы 1–3 в одном
явном `HARD_CRM_QA_ROOT`, с остановкой только принадлежащего тесту дерева процессов.
`HARD_QA_BACKEND` позволяет проверить тот же сценарий с точным frozen runtime.
Сборка: `python hard-desk/tools/build-backend.py`, затем из `hard-desk`
`node tools/installers.mjs crm`; аудит EXE: `node tools/audit-installers.mjs --product crm`.
Весь пакет собирается только из Git allowlist; рабочие базы и настройки не входят.
