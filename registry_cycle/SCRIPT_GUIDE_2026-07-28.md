# Контур реестров СНГ: что делает скрипт и что уже внедрено

Дата состояния: 28.07.2026

Продукт: `Контур · Реестры`

Назначение: безопасная сборка данных из личных портфелей в общий реестр и
обратная разборка общего реестра по актуальным ответственным.

## Коротко

Новый контур заменяет логику старого скрипта сборки/разборки, но сам старый
скрипт не изменяет и автоматически не запускает.

Основной цикл выглядит так:

```text
конфигурация
    ↓
поиск общего и личных реестров
    ↓
стабильные локальные snapshot-копии
    ↓
поклеточный план и отчёт конфликтов
    ↓
локальный Excel-staging
    ↓
полная валидация staging
    ↓
повторная проверка live-файлов и их занятости
    ↓
соседние backup-копии → атомарная публикация → postcheck
    ↓
новый baseline и owner-only уведомление
```

До последнего этапа живые книги на `U:` не изменяются. Полноценный ночной
автопаблиш сейчас намеренно не включён: сначала нужен зелёный приёмочный прогон
на свежем снимке и отдельное подтверждение владельца.

## 1. Какие задачи решает контур

Контур выполняет две связанные операции в одном детерминированном цикле.

### 1.1. Сборка

Из личных книг сотрудников собираются только разрешённые рабочие поля. Изменения
попадают в соответствующие строки общего реестра по ключу
`Номер КД / ID`, а не по номеру строки и не по порядку обхода файлов.

### 1.2. Разборка

После применения безопасных изменений общий реестр проецируется обратно в
личные портфели:

- строка направляется сотруднику, указанному в поле
  `ответственный Сотрудник` общего реестра;
- состав колонок определяется профилем HARD/SOFT и служебной строкой типов
  общего реестра;
- новые закрепления появляются в нужном личном портфеле;
- кейсы, просто исчезнувшие из общего без истории, не удаляются молча;
- кейс удаляется из старой книги только при доказательстве через
  `пред отв` общего реестра;
- новый пустой портфель остаётся корректной пустой книгой, пока в общем нет
  назначенных на него строк.

## 2. С какими реестрами он работает

Все расположения и группы находятся в `config/app.json`; в алгоритмах нет
зашитых ФИО сотрудников или путей конкретных городов.

Текущая конфигурация охватывает:

- HARD Душанбе;
- HARD Худжанд;
- HARD Ташкент;
- HARD Самарканд;
- SOFT Таджикистана;
- SOFT Узбекистана;
- отдельную HARD-группу `ГПХ Агент выезд`;
- Андижан как известную, но отключённую группу.

Профиль определяется конфигурацией группы. Дополнительное правило для файлов с
префиксом `СОФТ ` позволяет корректно распознать SOFT-книгу даже внутри папки
HARD-сотрудника.

На текущем live-контуре discovery находит 58 активных личных книг. Найденные
backup- и sidecar-копии не воспринимаются как рабочие портфели.

## 3. Discovery: как формируется точный manifest

Перед чтением данных скрипт:

1. вычисляет имя общего реестра для текущего месяца;
2. обходит только включённые страны, группы и профили;
3. находит активные `.xlsb`;
4. исключает временные, резервные и служебные копии;
5. фиксирует для каждой книги:
   - полный путь;
   - страну;
   - группу;
   - профиль HARD/SOFT;
   - папку сотрудника;
   - ожидаемого владельца;
6. проверяет отсутствующие обязательные группы, неизвестные группы с файлами,
   повторные активные книги и несовместимые цели;
7. создаёт воспроизводимый manifest запуска.

Discovery не открывает Excel и ничего не пишет в рабочие книги.

## 4. Snapshot: почему чтение не блокирует сотрудников

Живые книги не используются как рабочая площадка.

Для каждого запуска:

- проверяется стабильность размера и времени изменения источника;
- с live-файла снимается локальная копия в `_local/registry_cycle_v2/runs/...`;
- вычисляется SHA-256, размер и `mtime`;
- данные читаются из локальной копии через `python-calamine`;
- Excel COM не открывает live-файл для анализа или staging;
- исходный fingerprint сохраняется для будущего optimistic-lock.

Если сотрудник изменит файл после snapshot, публикация не станет перетирать его
новую работу: несовпадение fingerprint остановит замену.

## 5. Какие поля собираются

Список находится в `config/fields.json`.

### 5.1. Общие для HARD и SOFT

- `Сумма последнего платежа`;
- `Дата последнего платежа`;
- `Сумма прогноза`;
- `Прогноз`;
- `дата обещания`;
- `Общий результат`;
- `Телефон глав`;
- `Доп. Адрес/Доп.Номер`;
- `Дата встречи`.

### 5.2. Только HARD

- `Дата выезда`;
- `Комментарий текущего месяца выезда`;
- `С кем был контакт?`;
- `Договорились на оплату?`;
- `Кто был на адресе?`;
- `Местоположение клиента`;
- `Цель приезда в РФ`;
- `Cтатус звонка`;
- `комментарий звонка`.

### 5.3. Только SOFT

- `статус звонка софт`;
- `Дата перезвона`;
- `Комментарий текущего месяца Софт`.

Колонки сопоставляются по нормализованному заголовку и профилю, а не по
физической позиции. Поэтому HARD-комментарий не может «уехать» в SOFT-комментарий
из-за сдвига столбцов. Если схема, порядок или набор профильных колонок не
совпадает с ожидаемым, цикл блокируется.

### 5.4. Два платёжных источника

Исходные `Сборка.py` и `Разборка.py` различают два платёжных блока:

| Блок | Источник | Поведение |
|---|---|---|
| `Сумма последнего платежа`, `Дата последнего платежа` | сотрудник | непустая версия собирается вверх; у существующей личной строки значение общего никогда не записывается обратно вниз |
| `Оплаты за 01.26 … 06.26`, `Текущие платежи` | аналитики в общем | из личных книг не собираются и в личные книги не попадают, потому что у них нет профильной метки в строке 3 |
| `Сумма прогноза`, `дата обещания`, `Прогноз` | сотрудник | собирается вверх и сохраняется из личной строки; из общего вниз приходит только при создании строки у нового владельца |

Матрица больше не выводится только из строки типов. Перед каждым планом Excel на
локальной копии сверяет жёлтую заливку заголовков `#FFFF00` с 21 полем
`collect`. Любое расхождение блокирует цикл. Именно эта проверка обнаружила
пропущенный старым скриптом `Телефон глав`.

На границе месяца действуют две независимые операции:

1. У сотрудников очищаются только жёлтые `Сумма последнего платежа` и
   `Дата последнего платежа`. Они никуда не архивируются.
2. В общем реестре аналитические `Текущие платежи` копируются значениями в
   новую колонку `Оплаты за MM.YY`, после чего `Текущие платежи` очищаются.

Колонка истории вставляется непосредственно перед текущими платежами. Повторный
запуск не создаёт дубль: совпадающий завершённый месяц распознаётся как
`already_complete`, а различающиеся непустые история и текущая сумма блокируют
операцию. Формулы в архивируемом диапазоне также являются блокером.

## 6. Правила пустых и непустых значений

Главное правило: пустота из личного файла не удаляет значение из общего.

- `None` и пустая строка считаются одной семантической пустотой;
- пустое значение сотрудника игнорируется при сборке;
- непустое значение не заменяется старым только потому, что скрипт обошёл другой
  файл позже;
- два разных непустых источника одного КД и поля образуют конфликт;
- для комментариев и `Доп. Адрес/Доп.Номер` разрешено безопасное дополнение,
  когда один текст доказуемо является расширением другого;
- никакого общего «последний победил» нет.

При обратной разборке есть два специально разрешённых passthrough-поля:

- `Телефон`;
- `Город`.

Если соответствующая ячейка общего реестра пуста, а в прежней личной строке
сохранилось одно непротиворечивое непустое значение, оно остаётся в личном файле.
Это защищает дополнительные номера и локальные данные от исчезновения при
разборке.

## 7. Трёхсторонний merge и baseline

Baseline — это сжатая карта разрешённых полей общего реестра после последней
полностью проверенной публикации. Он нужен, чтобы отличать новую правку
сотрудника от новой правки общего реестра.

| После baseline | Решение |
|---|---|
| ни одна сторона не менялась | оставить как есть |
| изменился только личный файл | перенести личную правку в общий |
| изменился только общий в нежёлтом поле | сохранить общий и раздать его в личный файл |
| изменился только общий в жёлтом поле | вернуть значение сотрудника в общий и выпустить warning |
| обе стороны пришли к одному значению | принять без конфликта |
| обе стороны изменили поле по-разному | заблокировать весь пакет |
| один комментарий — точное дополнение другого | принять более полный текст |
| из общего удалили ранее непустое жёлтое значение | восстановить его из книги сотрудника и выпустить warning |

Baseline хранит не только сравнимое значение, но и исходный тип/представление
literal-полей. Он создаётся только из проверенного итогового мастера и привязан к
конкретному пути общего реестра и digest плана.

### Первый baseline

До появления штатного baseline разные непустые значения общего и личного файла
по умолчанию блокируются. Допустимы только:

- заполнение пустого общего значения;
- точное совпадение;
- доказуемое текстовое дополнение для разрешённых полей.

Для приёмки реализована отдельная команда
`rehearse-first-baseline`. Она строит кандидатный baseline внутри изолированного
аудит-прогона, выполняет весь staging и validation, но:

- помечает пакет `publishable: false`;
- не активирует baseline;
- не публикуется обычной командой;
- не меняет live-файлы.

После отдельного решения владельца этот же свежий пакет можно продвинуть только
через `promote-first-baseline`. Команда повторно строит план с кандидатным
baseline, повторяет validation, требует полный SHA-256 digest и затем использует
тот же optimistic-lock, backups, атомарную замену и rollback. Если появился
active baseline, изменился хотя бы один live-файл или staging относится к другому
snapshot, продвижение запрещается.

## 8. Даты и решение встречи

### 8.1. `Дата выезда`

Поле переведено в семантику `literal`.

Это означает, что скрипт переносит исходное представление:

- настоящую Excel-даты;
- дату со временем;
- строку с датой;
- `.`, `..`, текст, пометку и другой исторический вариант;
- исходное число, если в ячейке именно число.

Строка не превращается молча в Excel serial. Непарсящееся значение не
блокируется только из-за того, что оно не похоже на нормальную дату.

### 8.2. Остальные даты и числа

Массовой нормализации нет. Для исторически неканонических значений действует
политика `invalid: preserve`: значение переносится буквально, а в отчёте
появляется warning.

Если источником была настоящая Excel `date`/`datetime`, staging:

- сохраняет дату и дробную часть времени;
- ставит формат даты только изменяемой ячейке;
- берёт локальный формат из самой книги;
- проверяет через COM, что дата не осталась в `General`.

Если исходником было обычное число, оно остаётся числом в локализованном
`Общий/General`-формате. Скрипт не превращает всё число- и датоподобное содержимое
в единый формат.

## 9. HARD и SOFT больше не смешиваются

Разделение построено сразу на двух уровнях:

1. профиль книги определяется manifest;
2. доступные колонки берутся из служебных меток `хард`, `софт`, `сх` общего
   реестра.

Сборщик разрешает поле только для профилей, перечисленных у него в конфиге.
Разборщик строит схему портфеля из тех же профильных меток. Несовпадение
заголовков, лишняя колонка, пропавшая колонка или изменение порядка — блокер, а
не повод писать «примерно в тот же столбец».

Это закрывает класс регрессий, при котором комментарии HARD попадали в SOFT или
наоборот.

## 10. Кейсы в нескольких портфелях

Внедрена политика `master_responsible`.

Единственным каноническим владельцем и write-целью считается ответственный,
указанный в общем реестре.

Если один КД найден у нескольких сотрудников:

- изменения собираются только из книги канонического владельца;
- если `пред отв` однозначно совпадает с владельцем старой книги, строка
  доказанно снята/передана и удаляется из старой проекции;
- без такого совпадения копия у прежнего владельца сохраняется read-only;
- строка, которой уже нет в общем, также сохраняется read-only;
- строка с пустым ответственным и совпадающим `пред отв` удаляется из книги
  предыдущего сотрудника;
- строка с пустым ответственным без доказанного `пред отв` не назначается
  автоматически и сохраняется read-only;
- если у одного КД в самом общем реестре несколько разных ответственных либо
  смесь пустого и непустого владельца, весь цикл блокируется;
- все такие случаи отражаются в отдельном отчёте с КД, владельцами и путями.

Таким образом, порядок обхода файлов не влияет на результат.

### ФИО-алиасы

Известные варианты написания задаются в `responsible_aliases`. Сейчас настроено:

```text
Тургунов Музафар → Тургунов Музаффар
```

Это устранило 70 ложных несовпадений владельца, не меняя ФИО в живых исходниках
массово.

### Временное замещение

Физическое расположение книги и её канонический владелец могут различаться
только через явную конфигурацию `ownership_delegations`.

Сейчас задано временное размещение книги Турсунова Улугбека в папке
Курбаниязова Ильхомбека на период больничного. Внутри результата ответственным
остаётся Турсунов; случайная книга в чужой папке без такой записи блокирует
цикл.

## 11. Пустые новые портфели и группа ГПХ

Пустой портфель теперь является штатным состоянием:

- владелец выводится из проверенного manifest;
- это разрешено только когда весь диапазон данных действительно пуст;
- непустая книга без однозначного владельца остаётся блокером;
- проекция содержит ноль строк и не получает чужие данные.

В live уже создана отдельная группа:

```text
U:\rbr\Развитие СНГ\Узбекистан\
  Портфели сотрудников УЗБ\ГПХ Агент выезд
```

В ней подготовлены HARD-портфели:

- Кулдашев Абдулло;
- Ахрорхужа Акбаров;
- Ахмедов Давлатбек;
- Коххоров Незомжон.

У каждого есть:

- пустой 51-колоночный HARD-реестр с листами `Портфели`, `Статистика`,
  `Статусы`;
- комплект программы слияния;
- шаблоны и конфигурация;
- пустые папки логов/выгрузки;
- ярлык `ПРОГРАММА СЛИЯНИЕ.lnk` с существующей целью.

Распределения на этих сотрудников пока нет, поэтому цикл корректно показывает
четыре пустые проекции.

## 12. Staging: где реально работает Excel

После зелёного плана все snapshot-копии ещё раз копируются в локальный
`staging`.

Только здесь используется `xlwings`/Excel COM:

- в копии общего меняются только перечисленные в плане ячейки;
- в копиях личных файлов перестраивается только разрешённый диапазон листа
  `Портфели`;
- новые строки получают формат соседних строк;
- скрытые строки и AutoFilter временно учитываются и восстанавливаются;
- формулы в изменяемом диапазоне являются блокером;
- остальные листы не переписываются;
- книга сохраняется локально.

Путь live-файла на этом этапе не является целью записи.

## 13. Полная валидация

После staging скрипт не доверяет самому факту успешного `Save`.

Он повторно читает и проверяет:

- digest плана;
- SHA каждого staging-файла;
- каждую изменяемую ячейку общего реестра;
- все остальные ячейки общего реестра на отсутствие незаявленного diff;
- каждую ожидаемую ячейку всех личных проекций;
- отсутствие неожиданных хвостовых данных;
- набор и порядок листов;
- побайтовые/структурные сигнатуры нетронутых листов;
- состояние AutoFilter;
- отсутствие формул в перезаписываемом диапазоне;
- формат настоящих typed-date изменений;
- число проверенных файлов.

Любая ошибка делает validation красным; красный staging опубликовать нельзя.

## 14. Проверка занятости рабочих файлов

Реализованы три явных режима.

### `block`

Безопасный режим по умолчанию. Любой занятый целевой файл останавливает
публикацию. Сейчас в конфиге выбран именно он.

### `sidecar`

Для занятого личного портфеля создаётся соседняя книга с пометкой
`после ночного цикла`; открытый оригинал не изменяется. Общий реестр никогда не
обходится через sidecar: его занятость остаётся блокером.

Пакет с sidecar помечается незавершённым и требует последующего контролируемого
сведения. Новый baseline остаётся кандидатом и не активируется, пока живой
оригинал не сведён с sidecar.

### `force_close`

Код клиентской части полностью подготовлен:

- формируется manifest только точных файлов цикла;
- сохраняются их fingerprint и сведения о занятости;
- поддерживаются grace period, timeout и audit-каталог;
- после закрытия занятость проверяется повторно;
- snapshot для полного unattended-цикла снимается заново уже после закрытия;
- команда не может закрывать произвольные файлы вне manifest.

Но серверной делегированной команды с минимальными правами у текущей учётной
записи нет. Поэтому `force_close` честно выключен и недоступен в GUI. Скрипт не
обходит ACL и не убивает чужие процессы Excel.

## 15. Транзакционная публикация

Публикация возможна только если одновременно выполнены условия:

- план не содержит ошибок;
- validation зелёный и проверил все файлы;
- digest плана, staging, validation и ручного подтверждения совпадает;
- staging не менялся после проверки;
- каждый live-файл существует и имеет тот же SHA/размер/`mtime`, что при
  snapshot;
- занятость соответствует выбранной политике.

Для каждого изменяемого live-файла:

1. staging копируется во временный sibling-файл на том же сетевом томе;
2. SHA временной копии сверяется;
3. выполняется второй preflight;
4. непосредственно перед заменой снова проверяются lock и fingerprint;
5. создаётся SHA-проверенный соседний backup `до ночного цикла`;
6. временный файл атомарно заменяет цель;
7. SHA опубликованного файла сверяется.

Личные книги публикуются раньше общего, общий — последним.

При любой ошибке уже заменённые цели восстанавливаются из зафиксированных
snapshot-копий. Rollback также проверяется по SHA и пишется в append-only
журнал.

## 16. Cycle-lock, отчёты и аудит

Повторный одновременный запуск запрещён через `cycle.lock`. Для каждого run
остаются:

- `snapshot.json`;
- отчёт discovery;
- план и его digest;
- Markdown/JSON-отчёт изменений;
- staging manifest;
- `validation.json` и `validation.txt`;
- журнал публикации JSONL;
- `publish.json` либо `outcome.json`;
- сведения о backup, rollback и sidecar;
- отдельный audit делегированного закрытия, если оно когда-либо будет включено.

За счёт digest один проверенный пакет нельзя незаметно подменить другим перед
публикацией.

## 17. GUI

В графическом интерфейсе доступны:

- discovery и перечень найденных контуров;
- подготовка полного dry-run;
- ход длительного staging/validation;
- число изменений, проекций, предупреждений и ошибок;
- digest пакета;
- режимы занятых файлов `BLOCK`, `SIDECAR`, `FORCE CLOSE`;
- явное отображение причины недоступности `force_close`;
- раздельные настройки «запускать по расписанию» и «автоматически
  публиковать»;
- итог с количеством опубликованных файлов, sidecar и backup.

Опасные возможности не маскируются: выключенный серверный механизм показан
выключенным, а dry-run и live-публикация являются разными действиями.

## 18. Планировщик Windows

Генерация, установка, удаление и просмотр статуса задачи реализованы.

Задача:

- работает от текущего пользователя с `LeastPrivilege`;
- использует `InteractiveToken`, потому что Excel COM требует вошедшую
  Windows-сессию;
- не запускает параллельный экземпляр;
- требует сеть;
- умеет `StartWhenAvailable`;
- получает дни и время из конфига;
- добавляет `--publish` только при отдельном
  `scheduler.publish: true`.

Текущее безопасное состояние:

```json
{
  "enabled": false,
  "publish": false,
  "time": "23:40",
  "days": ["MON", "TUE", "WED", "THU", "FRI", "SAT", "SUN"]
}
```

То есть задача не установлена и автопубликация не разрешена. Семь дней нужны,
чтобы автоматический trigger последнего календарного дня не пропустил выходной.

## 19. Технические уведомления

Уведомитель принимает только:

```json
{
  "audience": "owner_only"
}
```

Итог или ошибка отправляются через административный endpoint `/admin/notify`,
который адресует сообщение `ADMIN_ID`. Если аудитория в конфиге изменена на
любую другую, конфигурация считается ошибочной.

Сбой уведомления не откатывает корректную файловую транзакцию, но фиксируется в
результате запуска.

## 20. Отдельные безопасные контуры

### 20.1. Аддитивный разброс новых закреплений

Это отдельный режим, который:

- только читает общий реестр;
- добавляет доказанно новые строки в личные книги;
- не перезаписывает старые строки;
- не удаляет КД, исчезнувшие из общего;
- требует assignment-baseline, где ранее ответственный был пуст;
- сохраняет provenance добавленных строк;
- поддерживает SHA-backup, lock-check, sidecar и rollback.

Именно этим режимом ранее были безопасно разложены новые закрепления.

### 20.2. Аддитивное восстановление из архивов

Восстановление также отделено от штатного merge:

- пишет только в пустую ячейку того же КД и ответственного;
- никогда не заменяет текущее непустое значение архивным;
- расходящуюся историю пропускает или блокирует по политике;
- сверяет кандидат с копией общего реестра;
- ограничивает массовость изменений;
- создаёт соседние backups и умеет rollback.

Так восстановление не превращается в скрытую часть каждого ночного запуска.

## 24. Порядок первого боевого запуска

1. Дождаться закрытия рабочих книг либо выбрать согласованную busy-политику.
2. Проверить занятость всех путей manifest.
3. Снять новый snapshot уже после завершения работы сотрудников.
4. Повторить `rehearse-first-baseline` на новом snapshot.
5. Получить план без ошибок и validation без ошибок.
6. Просмотреть:
   - все предупреждения;
   - multi-owner/read-only список;
   - число изменений по файлам и полям;
   - список пустых проекций;
   - digest.
7. Сверить fingerprint общего и личных live-файлов.
8. Получить отдельное подтверждение владельца.
9. Выполнить `promote-first-baseline` с полным digest в режиме `block`.
10. Проверить SHA всех целей, backups, журнал и итоговый baseline.
11. Только после стабильного ручного цикла отдельно включать расписание.

## 25. Основные команды

```powershell
# Только manifest
python -m registry_cycle discover

# Snapshot + план, без записи в live
python -m registry_cycle plan

# Полный dry-run: snapshot + plan + staging + validation
python -m registry_cycle execute

# Непубликуемая репетиция первого baseline
python -m registry_cycle rehearse-first-baseline `
  --snapshot <run>\snapshot.json `
  --summary

# Одноразовое продвижение первой зелёной репетиции
python -m registry_cycle promote-first-baseline `
  --snapshot <run>\snapshot.json `
  --stage <candidate>\staging\stage.json `
  --candidate-baseline <candidate>\candidate-baseline.json.gz `
  --confirm-digest <полный-sha256> `
  --busy-mode block

# Статус планировщика
python -m registry_cycle scheduler status

# GUI
python -m registry_cycle gui
```

Команды с `--publish`, установка планировщика и включение автопубликации до
отдельного решения владельца не выполняются.
