# Хард — проектная память

Обновлено 2026-09-09 (вечер) по текущему коду и рабочему серверу.

## Текущее устройство

- Продукт называется «Хард». Серверный код — `server/` (бывший `hardbot/`).
  Исторические имена `hardbot.db`, IndexedDB `hardbot`, `/opt/hardbot2`
  и форматы квитанций сохранены.
- Рабочее приложение запускается на Linux-сервере через Docker Compose:
  каталог `/opt/hardbot2`, сервис `bot`, контейнер `hardbot2-bot-1`.
  База и фотографии находятся в `/opt/hardbot2/data` (`/data` в контейнере).
  Локальная `server/hardbot.db` не является рабочей серверной базой.
- Пульт — Python + PySide6, точка входа `pult/Пульт.pyw`, логика в `pult/core/`,
  интерфейс в `pult/ui/`. Решение владельца: десктоп с Excel; веб-панель и
  возврат к Tkinter не планируются. С сервером общается по HTTPS токеном устройства.
- Telegram необязателен: с пустым `BOT_TOKEN` работает только приложение.
  `POST /admin/app_link.json` выдаёт ссылку входа; `db.local_identity_for`
  создаёт служебный ID от 900000000000 или использует существующую привязку.
  Добавление учётной записи само по себе не загружает клиентский портфель.
- Состав сотрудников в пульте берётся из `clients.responsible`; доступ к
  портфелю определяется совпадением с `agent_bind.employee`.

## Форма общего реестра меняется — сентябрь 2026

8 сентября офис изменил шапку `ОБЩИЙ РЕЕСТР СЕНТЯБРЬ.xlsb`: «ответственный
Сотрудник» → «ответственный Сотрудник ХАРД» плюс парная колонка СОФТ, так же
разделилась «Дата закрепления», добавился блок акции (условия/начало/окончание/
сумма). Обязательная колонка исчезла по имени, и загрузка встала целиком.

Решение — три уровня, различаются тем, кто и насколько срочно их принимает:
контракт обмена (v4: алиасы «…ХАРД», известные лишние «…СОФТ»), карта колонок
оператора в `settings['registry_column_map']` (правится из пульта, раздел
«Реестр» → «Колонки реестра») и, для настоящего нового поля, схема
`server/fields.py`. Экспортная схема и `export_schema_sha256` при первых двух
не меняются — шаблоны офиса и `registry_cycle` остаются прежними.

Дополнительные колонки читаются в отдельную таблицу `client_extra` и видны
выезднику блоком «Из реестра». Блок акции подключён именно так: 17 договоров,
68 значений. Подробности и порядок приёмки — в `docs/`.

## Что делать дальше — задачи владельца на следующую сессию

Работать планируется **на домашней машине владельца**: там есть Docker Desktop
для живой проверки. Перед переносом проект нужно почистить от мусора, навести
порядок в дереве и проверить чистоту git — папка переносится архивом целиком.

1. **Убрать единственный админ-ключ — это главная уязвимость.**
   Управляющим устройством должно становиться то, которое авторизовалось
   **по SSH**. Ключи доступа — одноразовые; предъявление такого ключа приводит
   к генерации **токена, привязанного к устройству**. Сейчас один
   `ADMIN_API_KEY` открывает всё, и это недопустимо.

2. **Подготовить исходный код, ИЗ КОТОРОГО генерируются скрипты развёртывания.**
   То, что лежит в `deploy/`, — уже готовые скрипты деплоя этого кода, то есть
   результат, а не источник. Нужен слой, порождающий их.

3. **Разделить систему на независимые контейнеры**, разворачиваемые по одному:
   главный «Хард», GPS (маршруты) и Whisper (распознавание речи). Каждый
   деплоится отдельно и без ошибок, соединяются между собой автоматически.
   Владелец согласен, что придётся переписывать.

4. **Отдельное управление сервером для ИТ-инженера — в интерактивном режиме.**
   Всё, что за месяц делалось по просьбе владельца вручную, должно быть
   доступно человеку без SSH: деплой, работа с базой, журналы, диагностика.
   Лазить по SSH — тупик и потенциальная смерть проекта. Вероятно, понадобится
   заметный «фан-аут» (много параллельной работы).
