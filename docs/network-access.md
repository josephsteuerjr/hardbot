# Сетевой доступ и сертификат на ВМ

## Рабочая схема с сертификатом Let's Encrypt

Сертификат корпоративного имени получает и продлевает Caddy на ВМ приложения.
HTTP-01 приходит на внешний порт 80 и далее на порт 80 ВМ. Порты 8080 и 443
корпоративного интерфейса направлены в TLS-порт 443 Caddy; backend приложения
остаётся отдельным HTTP-сервисом внутри Docker. Порт 8080 ВМ в этой схеме — HTTPS.

ИТ направляет внешний TCP443 на TLS-порт 8080 ВМ, сохраняя клиентский TLS и SNI.
До включения этого проброса доступен адрес вида `https://app.example.ru:8080`.
Поле `MINIAPP_URL` должно содержать проверенный рабочий origin, включая порт.
Переход на адрес без порта выполняется отдельно после отправки очередей:
для браузера это другое хранилище, даже когда сервер и сертификат те же.

Фактические значения, ACME-overlay и квитанции находятся в приватных локальных
материалах проекта. При выкладке сохраняют рабочий `COMPOSE_FILE`,
`docker-compose.acme.yml`, `Caddyfile.acme` и постоянные тома Caddy.
Старые примеры HTTP/LAN ниже относятся к отдельному локальному стенду.

Проверка после настройки: HTTPS `/ready.json` с проверкой цепочки и имени,
настоящий вход, свой портфель и контрольная доставка. Порт 80 сохраняют для
продления сертификата; отдельный cron с принудительным reload не нужен.
Требования HTTP-01: [Let's Encrypt](https://letsencrypt.org/docs/challenge-types/).

## Настольные приложения без публичного адреса

Сервер, база и приложения работают без VPS и внешнего DNS. Компьютеру нужен
маршрут до ВМ через корпоративную сеть или VPN. В сборке 3.1.7 адрес сервера
можно менять в форме входа по логину. HTTP разрешён только для приватного IP
или loopback; публичный HTTP автоматически заменяется на HTTPS.

В Linux, в `deploy/units/core/.env`:

```dotenv
COMPOSE_FILE=docker-compose.yml:docker-compose.lan.yml
APP_LAN_IP=10.0.0.25
APP_PORT=8080
```

Адрес выше — пример; нужен конкретный адрес корпоративного интерфейса ВМ.
Overlay добавляет внутренний порт и сохраняет слушатель на loopback.
`./update.sh` проверяет приватный диапазон. При отсутствии интернета и уже
подготовленном образе: `HARD_OFFLINE=1 ./update.sh`. Доступ к порту следует
ограничить корпоративными подсетями и адресами обратного прокси.

Проверка с рабочего компьютера: `/ready.json` должен ответить `{"ok":true}`.
Далее проверить настоящий вход и свой портфель. Ссылки выпускаются с адресом
`MINIAPP_URL`; изменение этого параметра не переносит браузерные очереди и
данные PWA с прежнего origin.

## Телефон внутри сети

Для телефона нужен HTTPS с доверенным сертификатом: браузер требует защищённый
контекст для геолокации, камеры и service worker. Публичный адрес для этого
не обязателен. Подходит внутреннее DNS-имя и сертификат корпоративного УЦ,
если его корень установлен и доверен на телефонах через ИТ/MDM. Возможен
сертификат с SAN внутреннего IP. Самоподписанный сертификат с предупреждением
браузера не является готовым решением. Требования браузера:
[MDN Secure contexts](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Secure_Contexts).

В репозитории есть необязательный офлайн-вариант: добавить
`docker-compose.lan-tls.yml` третьим файлом в `COMPOSE_FILE`. Он запускает
отдельный Caddy только на `APP_LAN_IP:443`, проксирует приложение и выдаёт
сертификат с SAN этого IP через собственный локальный УЦ. Интернет и публичный
DNS ему не нужны; образ `caddy:2` должен быть подготовлен заранее.

Публичный корневой сертификат для ИТ/устройств:

```sh
docker compose exec -T caddy-lan cat /data/caddy/pki/authorities/local/root.crt > lan-root.crt
```

Доверие этому УЦ устанавливают на устройствах через ИТ/MDM или вручную после
проверки отпечатка. До установки доверия телефонный вход не считается готовым.
Данные УЦ лежат в постоянном томе `caddy-lan-data`; приватный ключ УЦ остаётся
на ВМ, его резервную копию хранят с теми же правами, что секреты сервера.
Команда `docker compose down -v` удаляет этот УЦ и потребует заново настраивать
доверие клиентов. После включения проверяют `/ready.json` с полной проверкой
цепочки и IP SAN, без отключения проверки TLS.

ИТ может поставить тот же HTTPS-прокси в корпоративной сети до регистрации
публичного имени. Телефон должен видеть его через Wi-Fi/VPN. При смене адреса
прежде выгружают очереди прежней PWA; новую установку и вход проверяют на
одном пилотном устройстве, затем выдают остальным.

## Альтернатива: TLS на внешнем прокси ИТ

Если сертификат обслуживает ИТ на своём краю, это отдельный вариант схемы.
Протокол upstream выбирается по фактическому слушателю ВМ: после перевода
8080 на TLS требуется HTTPS с SNI корпоративного имени. Для HTTP upstream
используют специально настроенный HTTP-слушатель. Внешний прокси должен:

- передавать исходный `Host`, `X-Forwarded-Proto=https`;
- затирать `X-Forwarded-For` адресом клиента, принимать тело до 30 MiB;
- ждать ответ на загрузку фотографии до 120 секунд;
- не кэшировать авторизованные API и не записывать токены в access log.

В `trusted_proxies` сервера указываются только реальные доверенные промежуточные
адреса/CIDR, включая видимый приложению Docker hop. Клиентский `X-Forwarded-For`
не считается доверенным при прямом подключении к внутреннему порту.

После проверки DNS, цепочки сертификата, `/ready.json`, входов и фотографии
устанавливают `MINIAPP_URL=https://<выданное-имя>` и перезапускают приложение.
Прежний origin сохраняют для выгрузки очередей до окончания перехода.

Семантика объединения Compose-файлов описана в
[Docker Compose environment variables](https://docs.docker.com/compose/how-tos/environment-variables/envvars/#compose_file).
