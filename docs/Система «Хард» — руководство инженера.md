## 1. Что это за система

«Хард» обслуживает выездное взыскание в СНГ. Три группы людей:

- **Выездник** — открывает на телефоне установленное приложение (PWA), видит
  свой портфель должников, едет по адресу, фиксирует результат: статус, кто был
  на адресе, комментарий (можно надиктовать голосом), фотографию, геоточку.
- **Руководитель** — получает в Telegram карточки закрытых визитов, вечернюю
  сводку и утренний список просроченных обещаний; может открыть сводку и карту
  дня.
- **Оператор (аналитик)** — работает в десктопном пульте: грузит общий реестр,
  раздаёт доступы, следит за днём, возвращает результаты в личные книги.

Отдельным контуром живёт **офис взыскания** со своим Excel-хозяйством: общий
реестр и личные книги сотрудников. Система не заменяет это хозяйство, а
обменивается с ним по строгому контракту.

Ключевые свойства, определяющие архитектуру:

- **Телефон работает без сети.** Портфель заранее выкачивается в браузерное
  хранилище; визиты, фото и треки копятся и уходят при появлении связи.
- **Telegram необязателен.** С пустым `BOT_TOKEN` работает всё, кроме
  сообщений в мессенджер.
- **Результат выездника доказуем.** Визит считается настоящим только при
  наличии служебного снимка, созданного фактическим `POST /api/save`. Дата в
  Excel сама по себе доказательством не является.
- **Всё состояние — один файл SQLite** плюс каталог фотографий.

## 2. Топология и процессы

```
телефон выездника (PWA)  ┐
Telegram (необязателен)  ├─► HTTPS-прокси ─► app (aiohttp + aiogram) ─► SQLite + фото
десктопный пульт         ┘                        │
                                                  ├─► stt   (Unix-сокет, распознавание речи)
                                                  └─► osrm/vroom (маршруты по дорогам, необязательно)

рабочее место оператора: Excel + «Перенос реестров» ◄─► общий реестр ◄─► личные книги
```

Один процесс `server/app.py` поднимает и веб-приложение, и (если задан токен)
Telegram-бота на общем цикле событий, с общей базой. Фоново крутятся три
задачи: рассылка дайджестов, утренние обещания, домашняя уборка.

Контур владельца: каталог `/opt/hardbot2`, сервис Compose `bot`, контейнер
`hardbot2-bot-1`, данные в `/opt/hardbot2/data` (в контейнере `/data`). Имена
исторические, продукт переименован позже.

Установка ИТ-службой (`deploy/`) разворачивает то же самое из `docker compose`
со своими именами и своей службой речи.

## 4. Модель данных

Одна база SQLite (`hardbot.db`) и каталог фотографий рядом. Схема создаётся и
мигрируется в `db.init_db()` при каждом старте: недостающие колонки
доливаются `ALTER TABLE`, поэтому обновление кода не требует ручных миграций.

| Таблица | Что хранит |
|---|---|
| `clients` | реестр: по колонке на каждое поле схемы + служебные (гео, счётчик фото, снимок визита, офисные правки, ручное снятие) |
| `client_extra` | значения дополнительных колонок реестра, подключённых оператором |
| `visits` | закрытые выезды: снимок формы, гео, идемпотентный ключ |
| `users` | кто открывал приложение: id, ник, имя, язык, версия оболочки |
| `agent_bind` | привязка «телеграм-аккаунт → сотрудник реестра» |
| `managers` | руководители, их направления и персональные тумблеры рассылок |
| `app_links`, `app_tokens` | одноразовые ссылки входа и скользящие 30-дневные токены приложения |
| `admin_devices` | устройства пульта; хранится SHA-256 токена, не токен |
| `audit` | журнал доступа к персональным данным и административных действий |
| `push_log` | журнал доставки уведомлений |
| `report_chats`, `report_chat_employees` | беседы для пересылки отчётов и их состав |
| `markers`, `notes`, `photo_geo`, `track_points` | метки, заметки, координаты снимков, треки поездок |
| `enrichment_ledger` | реестр доставленного: что именно пульт сам записал в личные книги |
| `import_receipts`, `import_source_heads` | одноразовые разрешения на импорт и монотонная защита от повтора |
| `training_rows` | обезличенный корпус для обучения скоринга |
| `settings` | настройки: беседа, период выгрузки, карта колонок и прочее |

Два принципиальных момента:

**`client_extra` отдельно от `clients`.** Дополнительные колонки офиса не
заводят колонок в `clients` — иначе менялась бы экспортная схема и её
отпечаток, а на нём завязаны шаблоны офиса и перенос реестров.

**Что переживает очистку.** `limited_test_reset.RESET_TABLES` и
`RETAINED_TABLES` разделяют таблицы явно. Переживают очистку: расписки импорта
и их «головы» (защита от повторного проигрывания старого источника), корпус
обучения (в нём нет персональных данных), треки поездок и привязки устройств
пульта. Любая новая таблица обязана быть объявлена в одном из списков — за
этим следит тест.

## 5. HTTP-интерфейс

Три группы ручек. Все административные требуют мастер-ключа (`X-Admin-Key`)
или токена устройства (`X-Device-Token`); операции над самими устройствами —
только мастер-ключа.

### Приложение выездника (`/api/*`)

Авторизация: подписанные данные Telegram (`X-Init-Data`) внутри мессенджера
либо токен приложения (`X-App-Token`) вне его. **Токен принимается только в
заголовке** — в адресной строке он осел бы в логах прокси и истории браузера.

| Ручка | Назначение |
|---|---|
| `GET /api/bootstrap` | стартовые данные: список людей, настройки, версия оболочки |
| `GET /api/cards` | все карточки портфеля разом — прогрев офлайн-кэша |
| `GET /api/person` | одна карточка (точечный просмотр, пишется в журнал доступа) |
| `POST /api/save` | закрыть визит: форма, результат, снимок |
| `POST /api/photo` | снимок (сырое тело, до 25 МиБ, дедупликация по ключу операции) |
| `POST /api/voice` | голосовой комментарий → текст |
| `POST /api/track`, `POST /api/marker`, `POST /api/note` | трек, метка, заметка |
| `GET /api/route`, `/api/route_day`, `/api/route_to` | маршруты |
| `POST /api/redeem`, `POST /api/bind`, `POST /api/act_as`, `POST /api/lang` | вход по ссылке, привязка, просмотр чужого портфеля руководителем, язык |
| `POST /api/client-event` | телеметрия загрузки: только числа, без имён и текстов ошибок |
| `GET /api/manager/*` | экраны руководителя: сводка, сотрудник, обещания, фото, карта |

### Административное API пульта (`/admin/*`)

## 6. Приложение выездника (PWA)

Вся оболочка — один файл `server/miniapp/index.html`. Это сделано намеренно:
приложение должно подниматься офлайн одним запросом из кэша.

**Работа без сети.** `sw.js` кэширует оболочку под именем вида
`hard-shell-v39`. Карточки портфеля клиент выкачивает через `/api/cards` и
складывает в IndexedDB **одной атомарной заменой** — чтобы в поле не оказалось
половины старого и половины нового портфеля. Визиты, фото и треки копятся в
очереди и уходят при связи; повторная доставка не создаёт дублей, потому что у
каждой операции есть идемпотентный ключ.

**Версия оболочки объявлена в двух местах** — `SHELL_VERSION` в `index.html` и
`CACHE` в `sw.js`, — и обязана совпадать; сервер читает её из `sw.js` и отдаёт
в `/version.json`. Клиент сравнивает свою версию с серверной и предлагает
обновиться, но **никогда не перезагружает страницу посреди заполнения формы**.

При изменении `index.html` нужно поднять обе версии и хэш в тесте
`tests/test_pwa_shell_lock.py`. Забыть — значит оставить людям старую оболочку:
service worker отдаст своё, и починка до них не доедет.

**HTTPS обязателен.** По `http://` браузер молча отключает автономный режим,
камеру и геопозицию: приложение откроется и будет выглядеть рабочим.

## 7. Telegram-бот

Необязателен. С пустым `BOT_TOKEN` сервер поднимает только приложение, и в
журнале появляется соответствующая строка; каждый неотправленный пуш
записывается в `push_log`.

Что делает бот: приветствие и кнопка входа в приложение, выдача персональной
ссылки по слову «ссылка», экраны руководителя (сводка, сотрудник, карта дня),
пересылка карточек визитов в закреплённые беседы.

Действия выездника в чате намеренно отключены — вся работа в приложении.

**Один токен — один сервер.** Два экземпляра с одним токеном ломают друг
друга: Telegram отвечает 409.

## 8. Пульт

Десктопное приложение на PySide6. Ходит к серверу по HTTPS, своего доступа к
базе не имеет. Логика отделена от интерфейса: `core/` не знает про Qt и покрыт
тестами, `ui/` — только отрисовка и вызовы.

Два инварианта, которые стоит сохранять при доработках:

**Fail-closed по каждому эффекту.** Сервер в предпросмотре возвращает не только
числа, но и отпечатки точных множеств (что снимется, что вернётся, какие
комментарии заменятся). Применение отправляет эти отпечатки обратно; если
состояние базы успело измениться — импорт откатывается и требует нового
предпросмотра.

**Папка `server/` должна лежать рядом.** Пульт импортирует оттуда контракт
обмена и схему полей, проверяя, что модуль пришёл именно из этого каталога, а
не из случайно одноимённого пакета в окружении Python.

Разделы и порядок работы — в руководстве оператора.

## 9. Реестры: контракт обмена и перенос

### 9.1. Контракт обмена

`server/data_exchange_contract.json` — единственный источник семантики обмена.
В нём: форма книги (лист, строки заголовков, строка профилей), ключевые
колонки, алиасы заголовков, список известных служебных колонок, правила
обогащения (какое поле бота в какую колонку пишется и как сливается), правила
офисных правок, схемы доказательств источника.

Файл защищён дважды: точная форма объекта (лишний или недостающий ключ —
отказ) и пин SHA-256 всех байтов по номеру версии в `exchange_contract.py`.
Правка без поднятия версии и обновления пина не запускается.

Порядок изменения контракта, что при этом двигать нельзя и как зеркалить в
`registry_cycle` — в
[«Колонки реестра — руководство инженера»](Колонки%20реестра%20%E2%80%94%20руководство%20инженера.md),
разделы 8 и 9.

### 9.2. Путь данных

```
личные книги сотрудников
      │  (1) «Перенос реестров», шаг 1: собрать вверх
      ▼
общий реестр (Excel офиса)
      │  (2) пульт: импорт с одноразовым разрешением
      ▼
база «Хард» ──► приложение выездника ──► закрытые визиты
      │  (3) пульт: обогащение личных книг доказанными визитами
      ▼
личные книги сотрудников
      │  (4) «Перенос реестров», шаг 2: раздать вниз свежий общий реестр
      ▼
личные книги сотрудников
```

Правила, которые держат этот цикл честным:

- в базу попадает **только общий реестр**, личные книги — никогда;
- импорт требует явного вида источника, доказательства и **одноразового
  разрешения**, зарегистрированного локальным CLI на сервере; повторное
  проигрывание того же разрешения ничего не пишет;
- повтор канонического номера договора не сливается молча — берётся первая
  строка, остальные уходят в отчёт;
- обогащение пишет только ячейки с доказательством визита и ведёт реестр
  доставленного, поэтому правка офиса поверх доставленного распознаётся и не
  затирается.

### 9.3. Перенос реестров

Отдельная программа с двумя ручными шагами, каждый со своей проверкой, планом,
подтверждением, архивной копией и квитанцией. Живые книги не меняются до
подтверждения: сначала локальный снимок, план, сборка в изоляции и полная
проверка. Excel используется скрытым экземпляром только для корректной записи
`.xlsb`; открытые пользовательские процессы Excel не закрываются.

Колонки сопоставляются по заголовкам, а не по позиции. Имя папки и файла не
определяет владельца: владелец читается из колонки ответственного.

## 10. Скоринг и маршрутизация

Порядок выезда считается по **ожидаемому сбору**: вероятность оплаты × сумма.
Модель обучается на реальном портфеле (`train_scoring.py`), веса лежат в
`scoring_model.json`, коэффициенты — в `scoring_config.py` одним файлом,
чтобы их можно было показать и объяснить.

`scoring.py` — единственный источник истины: его импортируют и сервер, и
демо-движок. Раньше логика дублировалась, и получались «две правды о том, кого
везти».

Маршруты по реальным дорогам необязательны. Без OSRM порядок объезда считается
упрощённо, система работает полностью. `routing_client.py` выбирает граф по
стране и не даёт построить маршрут по чужому графу.

## 11. Голос

Служба речи — отдельный контейнер `stt/`. У неё **нет TCP-порта**: только
Unix-сокет в общем томе, Bearer-токен из файла, один запрос за раз. В журнал не
попадают ни аудио, ни имена файлов, ни распознанный текст — только код ответа,
язык и длительность.

Клиент — `server/stt_client.py`. Автоматического локального запасного варианта
нет: если голос недоступен, выездник вводит комментарий руками.

Модель выбирается переменной `STT_MODEL`; по умолчанию `large-v3-turbo` —
именно она запекается в образ службы (`tools/prepare_stt_model.py`, 0,8 ГБ в
int8). Другая модель означает другой образ: служба в интернет не ходит, поэтому
её нельзя «дозакачать» правкой `.env` — модель готовят скриптом и пересобирают
образ (`cd deploy/units/stt && ./update.sh`).

На контуре владельца используется общий сервис распознавания на том же хосте по
тому же проводному контракту; наличие каталога `stt/` в исходниках не означает,
что им заменён рабочий сервис.

## 12. Геокодинг и карты

Адрес → координаты считается послойно: разбор официального адреса СНГ →
внешний геокодер (если разрешён) → офлайн-справочник GeoNames → ручная метка
выездника. Уровень точности сохраняется отдельно (`geo_precision`): центр
района — не адресная точка, и гео-контроль обязан это учитывать, иначе честный
выездник выглядит нарушителем.

Координаты после импорта проставляются сервером автоматически; отдельной
кнопки в пульте нет.

Карты в приложении — локальные копии в `miniapp/vendor/`, чтобы приложение
поднималось офлайн без внешних CDN.

## 13. Установка и обновление

### Установка ИТ-службой

Полностью описана в [`deploy/README.md`](../deploy/README.md). Коротко:

```bash
cd deploy/units/core
./install.sh            # проверит Docker, создаст .env и секреты, соберёт, запустит
nano .env               # ADMIN_ID, MINIAPP_URL; BOT_TOKEN — если нужен Telegram
./update.sh             # применить настройки
./doctor.sh             # убедиться
```

Это ядро — оно обязательно и достаточно. Речь и маршруты ставятся такими же
тремя командами в `deploy/units/stt` и `deploy/units/gps`, в любом порядке и в
любой момент; система работает и без них. Состояние всех трёх сразу:
`deploy/doctor.sh`.

Сервер без интернета — отдельный путь, `deploy/offline/README.md`. Переезд
живой системы на другой сервер — `deploy/MIGRATION.md` (обычным копированием
базы переезжать нельзя).

Требования: 2–4 ядра, 4 ГБ памяти (8 ГБ, если ставят речь и маршруты),
от 100 ГБ диска, Docker Engine и Compose v2, один поддомен с сертификатом. Диск расходуется в
основном на фотографии — около 250 КБ на снимок.

Обязательная проверка после установки — **шестой пункт из README**: включить
авиарежим, заполнить карточку, выключить авиарежим. Данные должны уйти сами.
Если не работает — почти наверняка дело в HTTPS.

### Выкладка владельцем

Только локальным скриптом из `_local/` в порядке `check` →
`prepare-shared-stt` → `dry-run` → `deploy`, см. [`server/DEPLOY.md`](../server/DEPLOY.md).
`.env`, Compose, база, фотографии и секреты вместе с кодом не загружаются.

### Обновление

`./update.sh` в каталоге единицы снимает копию базы, пересобирает образы,
перезапускает сервисы и ждёт готовности. Единицы обновляются независимо друг от
друга. Данные лежат в `units/core/data`, отдельно от образа, и не затрагиваются.

## 14. Резервные копии и восстановление

```bash
cd deploy/units/core
./backup.sh            # база + фотографии
./backup.sh --db-only  # только база, секунды
./restore.sh backups/20260902T031500 [--photos]
```

База копируется **онлайн-бэкапом SQLite изнутри контейнера**: обычное
копирование файла работающей базы даёт несогласованный снимок. Фотографии не
меняются после записи, поэтому `backups/photos/` — зеркало, в которое досылается
только новое.

Приложение при этом останавливать не надо — и не надо, если оно уже остановлено
или падает по кругу: в этом случае скрипт снимает копию одноразовым контейнером
из того же образа. То есть копия снимается в любом из трёх состояний, в том
числе в аварийном, когда она и нужна.

Рекомендация: ежедневный cron от root, папку `backups/` копировать на другой
носитель средствами компании.

Перед каждой загрузкой реестра оператор делает отдельную копию базы — это часть
процедуры импорта, а не замена регулярным копиям.

## 15. Доступ, секреты, персональные данные

### Кто чем ходит

| Кто | Чем |
|---|---|
| выездник в мессенджере | подписанные данные Telegram |
| выездник вне мессенджера | токен приложения, скользящие 30 дней |
| пульт (всегда) | токен устройства + отпечаток машины, сверяется на каждом запросе |
| привязка нового пульта | одноразовый код, выдаётся на сервере `admin_access.py issue` |
| привязка и отзыв, аварийно | мастер-ключ `ADMIN_API_KEY` — и БОЛЬШЕ НИЧЕГО |

Мастер-ключ открывает данные только до самой первой привязки устройства в жизни
сервера; дальше он умеет ровно две вещи — привязать и отозвать. Флаг об этом
односторонний: отзыв всех устройств не возвращает ключу прежних прав, иначе
обладатель ключа получал бы полный доступ в два шага.

Коды привязки рождаются только на сервере и не имеют HTTP-входа — как и
регистратор импорта. Смысл один: право впустить новую машину привязано к доступу
к серверу, а не к знанию строки из `.env`. Токен устройства генерирует сервер и
показывает один раз, в базе лежит SHA-256. Подробно — `pult/УСТРОЙСТВА.md`.

### Персональные данные

- доступ к карточке пишется в журнал (`view_card`); оптовый прогрев портфеля
  логируется одной строкой, а не строкой на человека;
- телеметрия загрузки принимает **только числа** из закрытого списка: имена,
  адреса и тексты ошибок отбрасываются на сервере;
- в журналах нет адресов должников, координат и содержимого голосовых записей;
- координаты снимков — это данные о самом сотруднике (снимок из галереи часто
  даёт его домашний адрес), поэтому их можно стирать точечно из пульта;
- `_local/` и `_infra/` вне git; в пакет для ИТ они не попадают, а сборщик
  дополнительно сканирует исходники на токены, адреса серверов, пароли и
  приватные ключи и останавливает сборку при находке.

## 16. Диагностика

### Первым делом

```bash
deploy/doctor.sh                              # состояние всех трёх единиц
cd deploy/units/core && docker compose logs --since=1h app
cd deploy/units/stt  && docker compose logs --since=1h stt
```

### Полезные запросы к живой базе

```bash
# карта колонок реестра
docker exec <контейнер> python -c "import db, json; print(json.dumps(db.registry_column_map(), ensure_ascii=False))"

# кто заходил сегодня
docker exec <контейнер> python -c "import sqlite3; c=sqlite3.connect('/data/hardbot.db'); print(c.execute(\"SELECT action, COUNT(*) FROM audit WHERE ts LIKE date('now')||'%' GROUP BY action\").fetchall())"

# доставка уведомлений за сегодня
docker exec <контейнер> python -c "import sqlite3; c=sqlite3.connect('/data/hardbot.db'); print(c.execute(\"SELECT status, COUNT(*) FROM push_log WHERE ts LIKE date('now')||'%' GROUP BY status\").fetchall())"
```

### Как понять, что происходит с конкретным сотрудником

Порядок, который экономит время:

1. **Есть ли его записи в `audit` за нужный день.** Если нет ни одной — его
   телефон вообще не обращался к серверу, и дело не в сервере.
2. **`users.last_seen` и `users.shell_version`** — когда был и с какой
   оболочкой.
3. **`app_tokens.expires_at` минус 30 дней** — точный момент последнего
   успешного запроса: токен продлевается при каждом обращении.
4. **`client_boot_ok` / `client_warm_ok` в `audit`** — метрики загрузки:
   `server_ms` (сколько считал сервер) против `download_ms` (сколько
   скачивалось). Если сервер отвечает за десятки миллисекунд, а скачивание
   идёт секунды — проблема в канале телефона, а не в системе.
5. **Размер его прогрева.** `cards_bytes` растёт вместе с портфелем; при
   медленной сети это прямо влияет на впечатление «тормозит».

### Типичные проблемы

| Симптом | Причина | Что делать |
|---|---|---|
| `app` не становится healthy | ошибка в `.env` | `docker compose logs app` |
| `stt` долго `starting` | скачивается модель | подождать; дольше 15 минут — нет интернета из контейнера |
| Приложение не работает без сети | почти всегда HTTPS | проверить сертификат и прокси |
| Фото не отправляются | лимит тела в прокси | `client_max_body_size` не меньше 30 МБ |
| Telegram отвечает 409 | два сервера с одним токеном | оставить один |
| Импорт: нет обязательных колонок | офис переименовал колонку | карта колонок или алиас контракта |
| Импорт: «состояние БД изменилось» | параллельная работа | новый предпросмотр |
| Пульт не подключается | адрес или ключ | `https://` без косой черты на конце |
| Кончается место | фотографии | `du -sh data/photos`, переносить `backups/` |

## 18. Что нельзя менять и почему

**Не трогать `export_schema_sha256` ради удобства.** На нём завязаны шаблоны
офиса и перенос реестров. Новая колонка от офиса подключается картой колонок,
а не изменением схемы.

**Не ставить лимит памяти контейнеру приложения.** При обычной работе он
занимает около 300 МБ, но при загрузке большого реестра кратковременно берёт
заметно больше. С потолком 768 МБ контейнер убивало пять раз подряд. Если
ограничение требуется политикой — не ниже 2 ГБ.

**Не публиковать порт приложения наружу.** Сервис рассчитан на работу за
обратным прокси и сертификат сам не обслуживает.

**Не запускать два сервера с одним `BOT_TOKEN`.**

**Не копировать работающую базу обычным `cp`** — только `./backup.sh`.

**Не открывать запись из пульта в личные книги мимо доказательств.** Legacy-пути
(`razbros.py`, `daily_cycle.py`, `restore_from_bot.py`) намеренно оставлены
закрытыми: они пересобирают книги из полного слепка и могут стереть локальные
данные.

**Не убирать предпросмотр перед записью.** Отпечатки точных множеств — это не
перестраховка, а единственный способ отличить «состояние не изменилось» от
«кто-то работал параллельно».

**Не менять схемы `praxis.stt.*`** без синхронной правки клиента: это проводной
контракт со службой речи.
