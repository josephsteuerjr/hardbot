# Общий CRM-пилот

Состояние на 04.11.2026: кандидат `3.3.0-pilot.2` проверен. Отдельные
PostgreSQL и HTTPS API развёрнуты; загружена копия общего реестра и заранее
подтверждённый состав руководителей. Проверены настоящие PG-транзакции,
восстановление backup, полный Excel и установка/переустановка/удаление EXE.
Точные SHA, размещение установщика и квитанции — в приватном журнале операции.
`pilot.1` сохранён отдельно; автообновления кандидата отключены.

Физический вход руководителя на его рабочем ПК и внешний периметр окна
на целевой Windows остаются шагами приёмки. Успешный вход реального участника
на ПК сборки не заявляется: его сохранённый старый credential корректно
отклонён authority. Действующие мобильные клиенты используют прежний контур.

## Границы

`crm.storage` выбирает PostgreSQL только при `HARD_CRM_SHARED=1`. Старый
`db.connect()` остаётся SQLite. Отдельный `crm.shared_server` запускает только
API пилота и обработчик outbox; бот и производственные писатели не запускаются.
Отдельные БД, каталог документов и ключ сессий обязательны.

Состав руководителей задаётся до входов в приложение через `shared_setup` по
свежему подтверждённому срезу учётных записей. У каждого свой actor UID и
employee UUID. Одинаковые имена не объединяют людей. Доступ ко всей копии
реестра ограничен пилотной БД; права рабочей системы не расширяются. Смены,
активность, пороги успешности и сроки доставки из факта выдачи доступа не
создаются. Состав группы не зависит от телеметрии и запуска клиента.

Копия реестра загружается `registry_import.load(path, metadata)` только в пустую
базу. JSONL и gzip JSONL проверяются по SHA распакованных строк. Исходные
строки, типы и неизвестные колонки сохраняются отдельно. У договора ключ
кредитор + номер; связи людей между договорами и валюты требуют подтверждения.
Рабочие поля представлены текстом, спорные числовые значения не округляются.

## Вход

Клиент читает только текущий Windows-профиль установленного Руководителя.
Поддерживаются Chromium v10/v11 и прежний DPAPI. Исходные файлы не меняются;
перенаправленные пути и изменение входа во время чтения отклоняются.

Рабочий credential передаётся исключительно в `POST /crm-pilot/auth/exchange`
закреплённого HTTPS origin, без перенаправлений. Сервер обращается к доверенному
`GET /api/manager/device/me`; требуются серверный `subject.actor_uid`, действующее
устройство, роль руководителя и запись в отдельном составе пилота. Локальные
имя/роль не являются доказательством прав. В рабочем API отдельно развёрнуты
минимальные патчи `subject` и разбора версии протокола; весь новый `web.py`
из этой ветки в production не копируется. Допустимый суффикс pilot не отменяет
минимальную версию протокола и прежний отказ старым очередям.

Пилот получает собственную запечатанную сессию на 30 минут. Рабочий credential
не попадает в renderer, БД или журнал. При каждом использовании пилотной сессии
сервер повторно проверяет исходный вход. Отзыв устройства/учётной записи или
состава пилота останавливает дальнейшие запросы. Очередь прежнего пользователя
сохраняется; её нельзя отправить под другим пользователем.

## Подготовка сервера

Нужны `HARD_CRM_DATABASE_URL_FILE`, `HARD_CRM_SESSION_KEY_FILE` (32 байта),
`HARD_CRM_DOCUMENTS` (абсолютный путь), `HARD_CRM_SHARED=1`, `HARD_CRM_PILOT=1`.
Инициализацию DDL выполняет отдельная migration-роль, runtime-роль не владеет
таблицами и не получает DDL/TRUNCATE. История защищена также триггерами.
QA использует другую БД и роль; тесты создают и удаляют только свои схемы.

Развёртывание использует PostgreSQL с `--network none`, `listen_addresses=''`
и общим каталогом Unix-сокета, который монтируется только в API/миграцию/QA.
Проверка пароля SCRAM обязательна и для сокета. IP-подсеть для БД не создаётся.
В DSN используется `?host=%2Frun%2Fcrm-postgres`. Верхний каталог тома PG должен
разрешать проход postgres после сброса привилегий; сам PGDATA остаётся0700.
`APP_DATA=/tmp/crm-compat` нужен для импорта старых определений полей; рабочие
CRM-соединения используют исключительно отдельный PostgreSQL DSN.

Перед созданием сети Docker проверить все маршруты хоста, существующие IPAM
и корпоративные/VPN диапазоны. Использовать явный согласованный subnet;
автоматический выбор пула запрещён. При неизвестном результате операции
сначала прочитать состояние контейнеров/сетей/БД/секретов, не запускать заново.
Порт PostgreSQL на хост не публикуется. Существующие Caddy namespaces, особенно
VPN-блоки других приложений, должны сохраниться побайтно вне добавленного блока.

Порядок: восстановить и проверить сеть → подтвердить фактическое состояние
нового PG → создать/проверить изоляцию и роли → прогнать PG QA → загрузить
проверенную копию и состав → минимальный патч authority API → запустить API
пилота и проверить TLS → две независимые сессии → backup/restore → новый EXE.
Перед каждым внешним изменением нужны preview/backup/operation_id, после —
квитанция. Данные и операционные записи находятся только в приватном `_local`.

## Проверки

Локальные наборы: `test_crm_core`, `test_crm_exchange`, `test_crm_rebuild`,
`test_crm_adoption`, `test_crm_registry_copy`, `test_crm_shared_auth`,
`test_crm_shared_setup`, `test_crm_shared_http`; смежные проверки authority —
`test_pult2_devices_control`, `test_account_cutover`, `test_login_security_e2e`.
`test_crm_workbook` требует настоящего Windows Excel, сохраняет формулы/VBA,
проверяет точное чтение и восстановление выгрузки.

`hard-desk/tools/test-crm-manager-login.cjs C:/htarget/crm-<unique-qa-folder>`
использует настоящий Windows DPAPI и только синтетические credentials.
Проверяет старые форматы, подмену origin/ключа/профиля, смену пользователя,
раздельную сессию, отказ сети и защищённый файл больше 16 МБ в новом процессе.
Новые большие файлы содержат собственный случайный AES-GCM ключ, запечатанный
DPAPI в том же атомарно записываемом файле; прежний формат читается.

Для настоящих PG-тестов установить `HARD_CRM_TEST_DSN_FILE` на приватный файл
DSN роли `crm_qa` в БД `crm_qa` и выполнить `pytest tests/test_crm_postgres.py`.
Без этого параметра набор пропускается, что не является проверкой PostgreSQL.
Нужны повторы после потери ответа, конкурентные изменения, отсутствие взаимной
блокировки разных договоров, целостность транзакций и неизменяемая история.

Перед выпуском проверить полный объём реестра, доступные RAM/диск и резервное
восстановление. Новый XLSX пишется потоком, без хранения миллионов объектов
ячеек. Максимум защищённого локального файла — 256 МБ; лимиты больших запросов
повышены только для сверки/локальной записи Excel. Завершённая выгрузка хранит
манифест и квитанцию, незавершённая — точный снимок для восстановления.
Автообновление CRM и рабочие feeds этим этапом не включаются.

Выгрузка и предварительная/окончательная сверка больших книг используют
общий ограничитель: конкурирующий запрос получает503 `bulk_busy` с
`Retry-After: 5` до чтения тела, без хранения второй полной книги в памяти.
Digest вычисляется потоковым JSON-кодированием с сохранением прежних байтов
канонизации; baseline не загружается дважды. Полный HTTP-прогон Excel
проверен раздельными клиентом и сервером при runtime-лимите1536MiB.

Начальный полный backup восстановлен в отдельную QA-БД с проверкой всех
таблиц, последовательностей и триггеров. Ежедневный backup timer в этот этап
не входит. Для отката кода сохраняется прежний API-контейнер с теми же томами;
восстановление бизнес-БД из старого dump не является обычным откатом кода.
