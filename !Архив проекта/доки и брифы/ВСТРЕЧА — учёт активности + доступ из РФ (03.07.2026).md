# Бриф на встречу — 03.07.2026

Два вопроса: (A) можем ли мы **трекать активность/дисциплину** работников, особенно **курьеров по ГПХ**; (B) можно ли **включать приложение из РФ**. Ниже — что доказано кодом, с файлами и строками, чтобы можно было ткнуть пальцем.

---

## A. Учёт активности и дисциплины — ДА, механика есть и покрыта тестами

Вся активность пишется в SQLite `hardbot/hardbot.db` и привязана к **конкретному работнику** через `agent_bind.telegram_id`.

**Что именно фиксируется по каждому работнику:**

| Метрика | Где в БД | Где пишется (файл:строка) |
|---|---|---|
| Отработанный визит (статус звонка, договорённость, коммент) | `visits(agent_id, created_at, payload)` | `handlers_field.py:144, 177` → `db.log_visit` (`db.py:563`) |
| Гео-метки разведки (координаты + время до секунд) | `markers(telegram_id, lat, lon, created_at)` | `handlers_field.py` → `db.add_marker` (`db.py:596`) |
| Гео выезда (точка выездника) | `clients.geo_lat/geo_lon` | `handlers_field.py:226` (Telegram `F.location`) |
| Фото-подтверждения (счётчик) | `clients.photos_count` | `handlers_field.py:249` → `db.add_photo` (`db.py:577`) |
| Исход визита / реакция (дропдауны) | `clients.overall_result, call_status, agreed_payment, visit_date …` | пишется сразу при выборе, `handlers_field.py:91` |
| Аудит доступа: кто-что-когда смотрел ПД | `audit(ts, actor, action, target)` — append-only | `db.audit_access` (`db.py:542`) |

**Как из этого получается статистика — функция `db.activity_stats()` (`db.py:480–522`):**
на каждого работника считает `visits_7d/30d`, `markers_7d/30d`, `photos_total`, `last_activity` и **`idle_days` (дни простоя)**. Сортировка **«проблемные сверху»**: сначала кто вовсе без активности, потом по убыванию простоя — распиздяй виден с первой строки.

**Курьер ГПХ учитывается отдельно.** Поле `agent_bind.kind`: `'agent'` (штатный выездник) vs **`'courier'` (ГПХ-разведчик)** — `db.py:110, 117`. `activity_stats()` возвращает `kind` в каждой строке, курьеры видны отдельной категорией. Профиль курьера — гео-метки-разведка (`markers`), а не «визиты».

**Живое демо на дев-машине (где стоят зависимости):**
```
cd hardbot
python -m pytest ../tests/test_activity.py -v      # 2 теста: счётчики+простой и сортировка «распиздяй наверху»
python -c "import db; [print(w) for w in db.activity_stats()]"   # таблица активности по каждому работнику
```
Пример вывода `activity_stats()` (сид: выездник, курьер-ГПХ, спящий):
```
employee            kind      vis7 vis30 mrk7 mrk30 photos idle  last_activity
Спящий              agent      0    0     0    0    None  None  None          ← наверху (0 активности)
Рахимов (ГПХ)       courier    0    0     2    3    None   0    2026-07-03T15:57
Иванов              agent      2    2     0    0     4     0    2026-07-03
```

**Честные пробелы (сказать самим, чтобы не поймали):**
- Боевая `hardbot.db` пока **пустая** — реальной активности не накоплено; данные есть только в `_devdata` (30 клиентов, 4 записи аудита). Механика готова, боевых цифр ещё нет.
- **Latency** (дней от закрепления кейса до первого выезда) отдельно не считается — только косвенно через `idle_days`.
- **Соблюдение маршрута** не сверяется: `engine/` строит маршрут, но факт «проехал по нему» с метками не сопоставляется.
- `visits.created_at` — только дата (без времени); почасовую активность по визитам не построить (по меткам — можно, там datetime).

## B. Доступ из РФ — тезис про сервер ВЕРЕН, но узкое место не сервер, а телефон курьера

**Вердикт: условно да. Серверная связь с Telegram из РФ не блокируется вообще (тут заказчик прав). Реальное ограничение — работает ли сам Telegram на устройстве курьера в РФ.**

**Почему сервер — не проблема (подтверждено кодом):**
Бот работает через **long-polling**, не webhook — `app.py:84` `dp.start_polling(...)`. Сервер **сам** ходит наружу на `api.telegram.org`. Входящий статический IP и открытый порт не нужны; РФ-блокировки на этот исходящий канал не влияют. Сервер стоит вне РФ (166.88.185.90). Это же зафиксировано в `docs/security/11-deployment-infra.md:63`.

**Что курьер в РФ достаёт напрямую:** Telegram Mini App (кнопка-меню при заданном `MINIAPP_URL`, `app.py:73`). Веб-сервер миниаппа слушает `127.0.0.1:8080` (наружу не торчит — `docker-compose.yml:7`), публичный доступ — через **домен + TLS** (Cloudflare Tunnel / Caddy / nip.io+Let's Encrypt), не голый IP. То есть проблемы «голый IP без сертификата, WebApp не откроется» здесь **нет** — её обошли доменом.

**Что реально может сломать доступ из РФ:**
1. **Сам Telegram в РФ (главный риск, вне нашего кода).** В 2026 Telegram в России под сильным троттлингом/блокировкой; без VPN или свежего клиента с маскировкой трафика он часто не работает. Mini App живёт внутри Telegram — нет Telegram, нет ничего. Лечится на стороне курьера (VPN / последняя версия Telegram).
2. **Внешние CDN во фронте миниаппа.** `miniapp/index.html` тянет `cdn.jsdelivr.net` (maplibre, pmtiles), `fonts.googleapis/gstatic`, `protomaps.github.io`, `tile.openstreetmap.org` (строки 8–15, 370). Если jsdelivr не загрузится — карта/скрипты могут не подняться (белый экран). Лечится: **self-host этих ассетов на своём домене**.

**Важный нюанс из наших же документов:** `docs/security/11-deployment-infra.md:10–12` прямо пишет — *«в РФ Telegram под запретом — разворачивать его там значит нарушать закон. У компании есть филиал в ЦА, где Telegram доступен штатно, — там контур и работает»*. То есть проектный замысел — **Центральная Азия, а не РФ**, в т.ч. по юридике. «Включать из РФ» — технически возможно (VPN на телефоне курьера + желательно self-host CDN), но это обход, а не штатный сценарий.

**Что требует живой проверки (не выводится из кода):**
- Открывается ли Telegram + его WebView **на реальном устройстве в РФ прямо сейчас** (с VPN / без).
- Грузятся ли из РФ внешние CDN миниаппа (открыть боевой https-URL с российского устройства — не белый ли экран).
- Валиден ли TLS-сертификат прод-домена в `MINIAPP_URL` (Telegram открывает WebApp только по https с публично-доверенным сертификатом).

**Одной фразой для заказчика:** «Сервер вне РФ, связь с Telegram у него исходящая — её не блокируют, вы правы. Единственный вопрос — работает ли Telegram у самого курьера в России: сейчас там нужен VPN или свежий клиент. По нашим же требованиям контур штатно ставится в ЦА.»

## C. Статистика перемещений — точки со временем есть, непрерывного трека пока нет

**Что уже фиксируется во времени.** Единственный источник перемещений — таблица `markers` (`db.py:141`): `telegram_id` работника, `lat/lon`, `created_at` **до секунды**, `kind`, привязка к кейсу. Пишется разовой отметкой по действию (кнопка «метка» в миниаппе → `POST /api/marker` → `db.add_marker`, `db.py:596`). Отдельной таблицы треков/пингов нет; **Telegram live-location не пишется** (в боте `F.location` кладёт координату в карточку клиента, а не в трек; `watchPosition` в миниаппе используется только для навигации «по курсу» и никуда не сохраняется).

**Что из этого уже можно дать как статистику перемещений (на каждого работника, вкл. ГПХ):**

- хронология точек за день/период (`telegram_id` + `created_at` до секунд);
- количество меток 7/30 дн, последняя активность, **дни простоя** — уже считает `db.activity_stats()`, отдаётся в пульт (`GET /admin/activity`);
- расстояние между последовательными метками (гаверсинус — есть; **по дорогам** — прогнать список меток через OSRM, кубики готовы: `engine/routing.py:34,45`, `web.py:213`);
- города/зона покрытия по координатам (газеттир `hardbot/gazetteer.py`);
- **выгрузка всех меток (работник + время + координаты) в Excel** уже есть: `GET /admin/markers.xlsx` (`web.py:533`).

**Что карта рисует сейчас:** точки **клиентов**-должников (цвет = приоритет) и пунктирный «маршрут дня» — это **план объезда по клиентам**, плюс навигационная линия к одному должнику через OSRM. Метки работника показываются **только текстовым списком**, на карту как трек **не выводятся**. Фильтра «работник + дата» нет.

**Чего не хватает для полноценного трекинга (честно):** непрерывный трек (где ехал, а не где отметился), скорость и простои на точке, факт-против-плана, отрисовка трека работника на карте. Ни одной строки в `markers` в демо-БД пока нет — движение показать не на чем.

**Докрутка небольшая, инфраструктура уже есть** (OSRM поднят, карта умеет рисовать geojson-линии, время в метках до секунд): (а) писать Telegram live-location в новую таблицу треков; (б) OSRM `/match` для привязки трека к дорогам + фактический километраж; (в) вывести трек/метки работника на карту с фильтром по работнику и дате.
