## 2. Матрица направления данных

Перед каждым планом скрипт на локальной копии общего реестра сверяет цвет
заголовков. Все 21 жёлтое поле `#FFFF00` должны точно совпадать с конфигурацией.
Расхождение блокирует цикл.

Правила:

| Класс данных | Направление |
|---|---|
| 21 жёлтое поле сотрудника | личный портфель → общий |
| Нежёлтые профильные поля | общий → личный портфель |
| `Телефон`, `Город` при пустом общем | сохраняются из существующей личной строки |
| Аналитические `Текущие платежи` и история месяцев | остаются только в общем |

У существующей личной строки жёлтые значения, включая пустоту, принадлежат
сотруднику и не заполняются старыми значениями из общего. Пустота сотрудника при
этом не очищает непустое значение общего во время сборки.

## 4. Предупреждения плана

### 4.1. Исторические неканонические значения

Найдено 117 значений, не соответствующих заявленному типу колонки. По решению
встречи они не нормализуются и не отбрасываются, а переносятся буквально:

| Поле | Количество |
|---|---:|
| `Дата встречи` | 52 |
| `Дата перезвона` | 23 |
| `Сумма последнего платежа` | 5 |
| `Сумма прогноза` | 12 |
| `дата обещания` | 25 |

`Дата выезда` в warning не попадает: для неё действует отдельная
literal-семантика, сохраняющая исходное представление.

### 4.2. Строки без соответствующего КД в общем

Девять личных строк отсутствуют в общем реестре. Они:

- не собираются в общий;
- не удаляются из личных книг;
- остаются read-only;
- перечислены с КД, владельцем и путём в `plan.json`.

### 4.3. Доказанное снятие по предыдущему ответственному

Четыре КД имеют пустого текущего ответственного, а `пред отв` точно совпадает с
владельцем старой личной книги:

- `24737013` — Азизов Мехрочиддин;
- `43740053` — Муминов Абдулло;
- `45624923` — Муминов Абдулло;
- `47404215` — Рахимов Махмадулло.

Эти строки удаляются только из проекций доказанного предыдущего сотрудника. Если
`пред отв` отсутствует, неоднозначен или указывает не на владельца книги,
автоматического удаления нет.

Если кейс действительно передан новому сотруднику, прежние жёлтые значения
используются как fallback для новой личной строки. Непустое значение нового
владельца имеет приоритет. На свежем snapshot фактических handoff-ячеек нет.

Реально открыты и не дают эксклюзивный доступ:

- Рахимов Махмадулло;
- Хайдаров Аббос.

Для обеих книг присутствует Excel lock-файл, а Windows вернула ошибку
`sharing violation`. Lock-файлы не удалялись, процессы не закрывались.

При текущей политике `busy_file_policy: block` эти книги остановят публикацию до
любой замены. Кроме того, изменение любого live-файла после snapshot остановит
продвижение по optimistic-lock. Поэтому текущий зелёный пакет остаётся
доказательным, но не считается готовым к немедленной публикации.

## 11. Порядок первого live-запуска

1. Дождаться закрытия всех 59 целевых книг.
2. Получить `busy_count = 0`.
3. Снять новый snapshot после закрытия, не использовать этот пакет, если
   изменился хотя бы один источник.
4. Повторить `rehearse-first-baseline`.
5. Просмотреть полный diff, warnings, read-only/removal-списки и digest.
6. Получить отдельное подтверждение владельца на live.
7. Выполнить только `promote-first-baseline` с полным digest и
   `--busy-mode block`.
8. Проверить соседние backups, SHA live-файлов, журнал и active baseline.
9. Лишь после успешного ручного цикла отдельно решать вопрос Планировщика,
   доступности `U:`/UNC и делегированного SMB force-close.

Первый боевой запуск, активация baseline и установка Планировщика в рамках этого
отчёта **не выполнялись**.
