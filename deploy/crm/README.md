# Постоянный сервер CRM

Подготовка этапа «логика и сервер», 17.11.2026, исправленная после замечания владельца.
Новые книги создаются XlsxWriter, читаются calamine; установленный Excel для этого
не требуется. Рабочее включение — этап выпуска.
Проверенные пути существующих служб есть в `env.example`; перед выпуском повторно
сверить их с Docker mounts. Секреты в этот каталог не копировать.

## Размещение

- Linux-ВМ: PostgreSQL, существующий primary, API с планировщиком, обмен, мобильный
  BFF и отдельные процессы Python Аналитика. Отчёты и новые XLSX создаются здесь.
  `compose.yml` заменяет именно `crm-pilot-api` и `crm-legacy-exchange` после
  остановки старых экземпляров. Бот, parser VPN и остальные приложения сохраняются.
- Caddy принимает `/mobile/` и `/crm-pilot/` по HTTPS, затем передаёт запросы
  соответствующему контейнеру по приватной Docker-сети. Порты mobile/API на хост
  не публикуются. Существующие VPN/parser/update-блоки сохраняются.
- Windows остаётся местом исполнения существующих desktop-операций: точечной
  правки исходных XLSB/XLSM с сохранением их устройства и отправки через Outlook
  владельца. Эти команды явно отклоняются Linux-исполнителем до создания задания;
  они не являются условием работы серверных отчётов, новых выгрузок и мобильного BFF.
  `Run-CrmMobile.ps1`/`Register-CrmMobile.ps1` оставлены для необязательного нативного
  варианта. Постоянная схема в compose не требует отдельной Windows-ВМ.

## Подготовить пакет выпуска

1. Из точного коммита собрать Linux-образ по `server/Dockerfile.crm` с проверенным
   `CRM_BASE_IMAGE`; сохранить digest, использовать его в `CRM_IMAGE`.
   Операторский инструмент находится в образе `/runtime/tools/crm_runtime.py`.
2. Вычитать текущие primary-модули в приватный baseline и выполнить
   `python tools/crm_primary_package.py --baseline <baseline> --output <new-package>`.
   Manifest содержит SHA до/после каждого файла. Перед применением проверить
   **все** исходные SHA и отсутствие файлов, для которых before_sha256=null.
   При расхождении пересобрать патч поверх нового baseline. Не заменять весь
   primary исходниками CRM: на рабочем сервере есть более новые независимые функции.
3. В Linux подготовить каталоги mobile state/assets из `env.example`; state
   принадлежит uid 1000 с режимом 0700. Mobile key — отдельные 32 случайных байта,
   файл 0600 для uid 1000, read-only mount. Для сессий и профилей Python используются
   разные криптографические контексты; ключ не встраивается в образ. DPAPI-профили
   Windows сюда не копировать. Сохранить этот ключ для восстановления состояния.
4. Уложить точный проверенный mobile build в assets; запустить сервис `mobile` из
   compose. Он запускается вместе с Linux и восстанавливается Docker. `--internal-proxy`
   разрешён только для рабочего first-party origin; вне приватной Docker-сети
   по-прежнему требуется собственный TLS. Пользовательская сессия Windows не нужна.

## Миграция и адресное включение

Операцию выпуска записать в приватный журнал с operation_id, точными пакетами и
квитанцией. До изменений остановить писателей/обмен; сохранить согласованные
backup PostgreSQL и SQLite, код primary, конфигурации, файловые права и ключи.
SQLite копировать через backup API или при полностью остановленных писателях,
а не одним копированием main-файла работающей WAL-базы.

- На прежней SQLite проверить права uid 1000 нового API: чтение/запись базы и
  создание WAL/journal в каталоге. Прежний primary работает от root; новый API
  не переводить в root ради обхода ошибки. Согласованные ACL выставляются на
  точный каталог/БД при выпуске с сохранением прежних прав. Каталог `/status`
  и `/documents` должен быть доступен uid 1000. Проверить это до запуска.
- В окружении оператора с явным owner DSN выполнить `crm_runtime.py migrate`:
  переход со схемы 9 на 10 и права на новые таблицы в одной транзакции. API получает
  только app DSN; обмен сохраняет свой worker DSN. Owner DSN не монтировать в API.
- Для поиска в «Все клиенты» выполнить `psql -v ON_ERROR_STOP=1 -f portfolio-search.sql`
  с отдельным DSN владельца схемы. Запускать файл вне обёртки `BEGIN`: индексы создаются
  через `CREATE INDEX CONCURRENTLY`.
- Применить подготовленный hash-bound primary-патч с backup; сохранить существующие
  `/api/manager/entry_profile`, `/entry_revoke` и проверки неоднозначных имён.
  В primary явно включить `HARD_CRM_MOBILE=1`, `HARD_CRM_MOBILE_ROLLOUT=1` и `HARD_CRM_DESKTOP=1`.
- В приватном `contracts.json` перечислить точные canonical UUID перехода.
  С заданными `HARD_CRM_DATABASE_URL_FILE` и `HARD_CRM_PRIMARY_DB` выполнить
  `crm_runtime.py plan --contracts <file>`, затем `activate --contracts <file>
  --expected-sha256 <selection_sha256>`. Нет команды «включить всё» по умолчанию.
  Plan подтверждает сопоставление договора/кредитора и исходное назначение.
- Сначала SQLite закрывает прежние записи по выбранным договорам, затем PostgreSQL
  включает CRM. Разрыв между commit восстанавливается повторением того же activate.
  Одновременной работы двух писателей нет. Другие договоры остаются в прежнем режиме.
- Запустить новые API/обмен, проверить `/health` обоих контуров, затем применить
  проверенный `Caddy.fragment`. Сначала validate, после reload — реальный TLS-запрос.
  В окно переключения прежнего мобильного ярлыка добавить
  `mobile-entry.Caddy.fragment` к действующему сайту. По `/` приходит HTTP 200
  с самим мобильным интерфейсом из `root-index.html`. Ресурсы и API остаются
  под `/mobile/` того же origin. После активации мобильного кэша приложение
  устанавливает корневой worker, который очищает кэши `hard-shell-v*` и позволяет
  прежнему ярлыку открывать офлайн-CRM. Worker и скрипт первоначального перехода
  раздаются из каталога `crm-root-mobile-1` сервиса статики. `/sw.js` служит
  дополнительной точкой обновления для старой регистрации. Старый вход с :8080
  направляется на HTTPS без порта. Прежняя оболочка доступна по `/?legacy=1`
  с запретом регистрации её worker.
  Пройти вход/отзыв устройства, импорт → назначение → работу → отчёт и проверить
  обе БД/квитанции. До этой проверки выпуск не считается включённым.
- Для совместной работы выпусков сохраните текущий порог
  `HARD_CRM_MIN_DESKTOP_VERSION`. Проверяйте вход, PWA и обмен после
  публикации подписанных обновлений.

### Переход на схему 10 с работающими старыми клиентами

Используйте ту же рабочую PostgreSQL и прежний URL `/crm-pilot`. Схема 10
добавляет таблицы полномочий. Существующий вход работает в модели 1 до
явного включения модели 2 для этого аккаунта. На первом переключении
проверьте старый и новый клиент со своими сохранёнными сеансами, запись
результата, повтор той же операции, отчёты и курьерский пул. Сохраните
действующее значение минимальной версии клиента.

Пока все аккаунты на модели 1, после остановки серверных писателей
`crm_runtime.py rollback-schema-9` покажет возможность возврата к прошлому
API. При `eligible=true` та же команда с `--expected-sha256` из предпросмотра
меняет отметку схемы. Принятые операции и таблицы сохраняются. После этого
можно запустить сохранённый образ API со схемой 9. После первого включения
полномочий модели 2 или проекции нового аккаунта из регистрации возврат к
бинарнику схемы 9 закрыт. Для восстановления используйте сервер, который
понимает действующие полномочия, области регистрации и квитанции операций.

Для аккаунта, который продолжит работать со старым клиентом в модели 2,
проверьте вход через его прежнюю роль без `X-CRM-Grant`. При нескольких
доступных полномочиях этой роли нужен действующий вариант по умолчанию.
Проверьте старые административные маршруты primary отдельно перед сужением
прав. Они используют собственную проверку исходного входа.

### Несколько полномочий одного входа

Для редактора полномочий на рабочей PostgreSQL создайте отдельный логин
`crm_access_admin`, примените `tools/crm_grant_admin_permissions.sql` и
подключите `grant-admin.compose.yml` с `CRM_GRANT_ADMIN_DSN_FILE`.
Редактор находится в «Команде». Владелец или Аналитик с действующим
`access_manage` выбирает вход сотрудника, добавляет роль с её территорией и
действиями, проверяет предпросмотр и подтверждает. Старый клиент продолжает
использовать полномочие своей роли. В новом клиенте рабочее место
выбирается в «Подключении». Для переключения ролей нужен подтверждённый
вход по логину и паролю с обновлённым primary.

Перед включением модели 2 проверьте отправки и черновики с каждого устройства.
Клиент переносит подтверждённую работу того же входа в единственное
совместимое полномочие прежней роли или в полномочие по умолчанию этой роли.
Записи с неустановленным владельцем требуют сверки.

### Регистрация в Windows и браузере

На месте с действующим `/api/crm-identity` соберите отдельный пакет primary
командой `python tools/crm_primary_package.py --registration --baseline <baseline> --output <new-package>`.
Проверьте исходные SHA из манифеста. Перед запуском нового primary примените
`tools/crm_registry_permissions.sql` к рабочей PostgreSQL от владельца схемы.
Затем используйте Windows- и mobile-сборки этого же среза. Веб-вход для телефона
и браузера на ПК доступен по `/mobile/`.

Сотрудник вводит ФИО, которое сервер сверяет с текущими закреплениями. На время паузы оператор
выдаёт каждому сотруднику личный одноразовый код командой
`python account_access.py registration-code --employee "<ФИО>" --hours 24`.
Код передают сотруднику напрямую. Паузу определяет действующий параметр
`account_device_confirmation_paused_until_utc`. По её окончании подтверждение
новой регистрации возвращается в «Вход команды».

Руководитель выбирает город или всю республику, аналитик указывает ФИО.
Администратор подтверждает их заявки в действующем разделе аккаунтов.
Подтверждение относится к заявке и её первому устройству. После первого
подтверждённого входа аккаунт связывается с правами в общей CRM.
Для распределения владелец отдельно добавляет руководителю право `assign`
и нужные виды работ. Его область по городу или республике и защита
от старых писателей продолжают действовать.

### Переход с Руководителя Tauri 3.5.0

Пакет перехода 3.5.1 предназначен для прежнего подписанного канала
`cis-collection-tauri-stable`. Он загружает конкретный установщик Руководителя
CRM из версионного выпуска GitHub, проверяет размер и SHA-256, сохраняет
копию прежней программы и запускает обновление в существующей регистрации.
Действующий вход копируется в файл CRM с защитой Windows DPAPI. Проверку
доступа выполняет сервер. Исходная SQLite остаётся доступной для восстановления.

Собрать пакет локально после проверки Windows-выпуска.

```powershell
python hard-desk/tools/build-manager-tauri-transition.py --release-dir <signed-release> --output <new-directory> --tauri-private-key <private-manager-key> --tauri-public-key <installed-manager-public-key>
```

При рабочей выкладке сначала подтвердить доступность версионного EXE и его
SHA-256 по URL из квитанции сборки. Затем разместить EXE перехода по URL
из `manager.json` и проверить его SHA-256. Манифест публикуется последним.
Перед включением ограничения проверить переход из 3.5.0 через кнопку обновления,
прежний ярлык и подтверждение роли после входа. При проблеме с установкой
копия прежней программы и её каталог указаны в `Hard/manager/upgrade-recovery`.

### Курьерские пулы

Для каждой страны в приватном JSON задаются списки кадровых UUID `logist`,
`call` и `delivery` под ключом `UZ` или `TJ`. Для логиста и курьера используется
отдельный профиль CRM с действующим связанным входом. Состав Софта относится
только к курьерскому обзвону.

Проверка состава выполняется с owner DSN командой
`crm_runtime.py logistics-staff --roster <file>`. Чтобы применить показанный
состав, передать тот же файл и `--expected-sha256 <selection_sha256>`.
Страна в файле получает указанный состав целиком. Остальные страны сохраняют
свои списки. Права записи в состав остаются у владельца схемы.

В Windows CRM логист выбирает страну, период передачи и книгу. Предпросмотр
показывает строки, которые можно добавить, и причины сверки. Первую загрузку
проверить после перевода выбранных договоров и связки с primary, затем сверить
появление договора у назначенного Софта, запись дозвона и выгрузку. Обычное
назначение Софта продолжает обрабатываться своим контуром.

## Переключение рабочего реестра Аналитика

После миграции canonical в ту же PostgreSQL выполните `tools/crm_migrate_registry.py` на согласованном SQLite-снимке с доступом владельца схемы. Программа сверяет бизнес-таблицы после копирования и устанавливает права из `tools/crm_registry_permissions.sql`. Секреты и права входа сотрудников сохраняются в прежнем сервисе авторизации.

Для штатного primary задайте `HARD_REGISTRY_DATABASE_URL_FILE` с DSN роли `crm_exchange` и подключите сокет PostgreSQL. Указывайте тот же database, что у API и обмена. Право записи через импорт получает только служба штатного обмена. Сохраните действующие клиентские профили, ярлыки и очередь.

Перед сменой маршрута остановите прежнюю запись, сверьте изменения после общей точки, сохраните последние квитанции обмена и примените адресный `activate` с проверенным хэшем. После подтверждения всех выбранных договоров установите `crm_registry.migration_receipt.active = true` для единственной строки. Отметка сообщает серверу и обмену, что результаты, назначения и импорт теперь сходятся в PostgreSQL. Прежний обмен снимками выключается. Проверьте вход из прежнего профиля и штатные API выгрузки и журнала. Восстановление после следующего принятого факта должно сохранять этот факт.

## Повседневная работа и восстановление

`crm_runtime.py status` показывает режим, heartbeat, ожидающие проекции и конфликты.
API `/health` требует актуальную схему и здоровый планировщик; exchange health
читает свою сохранённую квитанцию. `/mobile/health` показывает исполнитель
`python-xlsxwriter`; выгрузку дополнительно проверять по SHA и calamine readback.

Распределение хранится в PostgreSQL; primary получает его устойчивой очередью.
Старый импорт обновляет бизнес-поля, сохраняет ответственность CRM, а расходящиеся
назначения/результаты оставляет в списке сверки. Журнал source conflicts append-only:
его rowid — курсор переноса, записи не удалять и таблицу не пересоздавать отдельно.
Звонки/выезды и правки полей проецируются с квитанцией; повтор после потерянного
ответа не создаёт второй факт. Новые сущности CRM сохраняются в canonical, а не
превращаются в фиктивные звонки прежней базы.

Планировщик работает без открытого клиента. Перед каждой порцией он перепроверяет
действующий вход/права; отзыв доступа блокирует работу. Трёхчасовые снимки фиксируют
реальное наблюдение; пропущенные при простое отсечки задним числом не придумываются.
После истечения/отзыва входа автор входит заново, затем разрешённая работа продолжается.

Linux BFF после перезапуска присоединяется к прежнему Python-процессу; файловая
блокировка запрещает второй исполнитель того же профиля. Работающий исполнитель
не завершается при закрытии браузера/BFF. Неизвестный результат внешней отправки
или записи сначала сверяется; очередь не отправляется повторно вслепую. Удаление
профиля и защищённых записей не является способом перезапуска. После перезапуска
контейнера запускается новый процесс с прежней устойчивой очередью. Обычные XLSX
выгружаются атомарно с чтением записанного файла; формулы содержат рассчитанные
значения, поэтому пересчёт установленным Excel для просмотра не требуется.

При неудаче включения остановить новые писатели, сохранить состояние и повторить
незавершённую идемпотентную операцию либо восстановить согласованную пару backup.
Не удалять fence-триггеры и не включать старых писателей поверх уже принятых CRM
результатов. Возврат одного старого EXE/образа не откатывает рабочие данные.

## Резервная копия рабочей PostgreSQL

При выпуске каталог `/opt/rimborso-crm-runtime/current` указывает на конфигурацию обслуживающего API. В нём находятся `backup_postgres.py`, файл DSN и мобильное состояние. Обычный `deploy/units/core/backup.sh` до составления SHA256SUMS сохраняет в каталог очередной копии логический дамп, документы по хешам из этого дампа и состояние мобильной службы. Для мобильных SQLite применяется backup API. Ключи шифрования восстанавливаются из отдельной приватной копии владельца ВМ.

Восстанавливать `crm-postgres/database.dump` командой `pg_restore --exit-on-error` в свежую базу с теми же ролями. Вместе вернуть соответствующую базу входов, документы, фотографии, чеки, мобильное состояние и ключи. Проверить последнюю операцию, права и совпадение идентификатора отсечки обеих БД до возврата рабочих адресов. Переключение после новых действий должно сохранять их историю.
