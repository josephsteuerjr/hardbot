## 1. Оценка кода (честно, по файлам)

### Что сделано хорошо — назвать прямо, чтобы случайно не переписать

- **Архитектура и закон.** «Два процесса, одна SQLite (WAL)», он-прем на машине аналитика, на демо-сервере — **только синтетика, ПД нет никогда**. Это закрывает локализацию ПД (152-ФЗ / ZRU-547) на уровне дизайна, а не «потом».
- **Инженерная зрелость фолбэков.** `planner.py`: VROOM → гео-балансировка k-means + 2-opt. `routing.py`: OSRM-времена → гаверсинус, причём `_sane()` ловит вырожденную матрицу (дорожный граф только по ТДж — точки УЗ/РФ «прилипают» к погранузлу). Это редкий уровень аккуратности.
- **Безопасность бота сделана корректно.** `web.py::validate_init_data` — настоящая HMAC-SHA256 проверка Telegram WebApp с `compare_digest` (constant-time) и свежестью 24 ч; `_auth` реально отдаёт 401/403. Дев-обход выключается в проде. **Это сильная сторона, не трогать.**
- **Скоринг — в правильную сторону.** Два режима (РАЗВЕДКА для холодного портфеля / ДОЖИМ при наличии исхода), нормализуемые веса, killer-фильтры. Ровно то, что предписывает наука для портфеля «о клиенте ничего не известно».
- **Данные надёжны.** Импорт/экспорт матчит колонки **по смыслу** (переживает «сдвиг влево»), `selftest.py` бьётся round-trip. `.gitignore` корректно прячет `.env / *.db / _devdata`. Проект **не под git** → утечки секретов в историю нет.
- **Компактность.** ~6.8 тыс. строк на весь проект, с комментариями на русском. Читается.

### Производительность (оптимизация)

1. **`routing._two_opt` ≈ O(n⁴) на раунд.** `length(cand)` пересчитывает **всю** длину маршрута на каждый кандидат-своп, внутри двойного цикла, пока есть улучшения. На demo-n (≤18) незаметно; на реальном городе (сотни точек) — затык. → инкрементальная дельта (своп меняет только 2 ребра). Дешёвый, крупный выигрыш.
2. **`routing._finalize` всегда строит полную haversine-матрицу** `_matrix(nodes)` (O(n²)), хотя нужна лишь сумма по уже заданному порядку (O(n)) — и даже когда есть OSRM-длительности. → считать сумму вдоль порядка.
3. **`priority_from_db` / `priority_index`** каждый раз перечитывают всю таблицу `clients` и пересчитывают. Если дёргается на каждый запрос миниаппа — это N+1. → кэш индекса приоритета с инвалидацией при изменении визита.
4. **`_vroom_plan` дедуп leftover по `id(p)`** — хрупко (зависит от идентичности объекта в памяти). → стабильный ключ (`contract_id`).

### Корректность и прозрачность (важно для ревью и для директора)

- **«Магические числа» сигналов дожима** (`+12` обещает, `+8` на родине, `−6` нет контакта, `−8` передал 3-му лицу) зашиты в `compute_priority` и **не крутятся в пульте**, хотя веса долг/кластер/свежесть — крутятся. Непоследовательно и непрозрачно. → вынести в конфиг рядом с весами.
- **`compute_priority` мутирует входной список** (`it["city"]`, `it["lat"]` пишутся в аргумент). → сделать чистой функцией (побочные эффекты ломают переиспользование и тесты).

### Тесты

- Есть `selftest.py` (round-trip данных) — хорошо. **Нет** юнит-тестов на скоринг, маршрут, валидацию подписи. → pytest-набор: скоринг (оба режима, killer-фильтры), routing (2-opt не ухудшает; фолбэк срабатывает), `web.validate_init_data` (подделка/просрочка отвергаются). Для ИБ тесты — это «доказательство», а не «поверьте на слово».

## 2. Безопасность — что увидит ИБ (находки отделены от мифов, по серьёзности)

- 🔴 **API движка без аутентификации.** `engine/app/main.py` (`/api/points|route|plan|analytics`) при заданном `HARDBOT_DB` отдаёт данные должников (договор, город, долг, скор) **без авторизации**. Сейчас защита **только операционная**: порт не открыт наружу, доступ по SSH-туннелю, на сервере крутится лишь синтетика. ИБ потребует **defense-in-depth**: токен/сессия на API, привязка к роли аналитика, запрет старта с реальной БД на сетевом интерфейсе (`0.0.0.0`). → добавить auth-слой.
- 🟠 **Самопривязка выездника без аппрува.** Любой, кто откроет бота, может выбрать себя **любым** «Сотрудником» из реестра и увидеть его список должников — нет шага одобрения админом/инвайта (`is_trusted = ADMIN или есть привязка`). Сама проверка подписи корректна; брешь — в **отсутствии авторизации на этапе привязки**. → инвайт-коды или подтверждение ADMIN перед активацией привязки.
- 🟡 **Открытый CORS на tiles-прокси** (`Access-Control-Allow-Origin: *`). Тайлы без ПД — риск низкий, но прибрать/сузить.
- 🟡 **Операционка по секретам и ПД.** `.gitignore` корректен, репозиторий не под git. Но `.env` с боевым `BOT_TOKEN` и `hardbot.db` лежат в `Downloads\Бот для выездников` → **убедиться, что папка не синхронизируется в облако** (OneDrive/Dropbox). Бэкап БД — только в РФ-хранилище (роадмап уже учёл).
- ✅ **Локализация ПД уже закрыта** он-прем-архитектурой. Нужно лишь **документировать** (диаграмма потоков + резидентность) — см. §5.

## 3. Что показали рынок и наука (синтез 4 машин — «интересное»)

### A. Аналитика и скоринг

- **Стратегия верна.** Для холодного портфеля **ML рано** (нужны исходы «заплатил/нет через 30–60 дней») — двухрежимная эвристика правильна. «Маховик данных» («не уехал, пока не заполнил») — это и есть путь: в полевом RL-эксперименте на микрозаймах политика использовала **на 63% меньше действий при +8.1% к возврату**.
- **Дешёвый апгрейд с доказанным lift'ом:** социо-временные признаки — **религиозный календарь (Рамадан/Курбан), сбор урожая, школьные каникулы** — академически значимо предсказывают платёжное поведение на похожих рынках. Почти бесплатно добавить в скор.
- **Главный концептуальный апгрейд — диспетчеризация по ожидаемой ценности:** выезжать, когда `P(оплата|визит) × ожидаемый возврат ≥ полная стоимость визита`. «Break-even score» **плывёт с размером долга** (большой долг оправдывает меньшую вероятность). Ваш `profit_per_min` (долг ÷ минуты) — **зачаток** этого; стоит формализовать. Поле — самый дорогой канал → резерв для **high-value + high-risk + низкая контактность** (≈20% дел держат ≈70% возврата; цифровой нудж снимает ≈40% ранних выездов).

### B. Маршрут

- **Правильная формулировка — Team Orienteering Problem with Time Windows (TOPTW):** «выбрать и упорядочить самый ценный **поднабор** под бюджет часов», а не «объехать всех». **Сейчас движок** берёт top-N по скору (`[:limit]`), затем строит маршрут по **всем** из набора, а leftover в VROOM ещё и подвешивает — то есть селекция оторвана от маршрутизации и ничего «дальнее-малоценное» не роняется. → дать оптимизатору ронять: VROOM это умеет через `priority` + **`max_travel_time`/`max_tasks`** (включить бюджет времени, а не только вместимость); более строгий рычаг — OR-Tools `AddDisjunction(штраф ∝ ценность)` — стоит A/B на реальных данных.
- **VROOM — адекватный выбор, замены не требует** (1000–1500 точек / ~30 машин за секунды). Реоптимизация в течение дня (каждые 30–60 мин или по событию «нет дома») — тривиальна.
- **Региональный риск №1 — геокодинг УЗ/ТДж** (OSM часто только до улицы). Самый ценный фикс данных — **GPS-пин выездником на месте + флаг доверия к точке** (роадмап это уже заложил: `geo_src='manual'` не перетирать).

### C. Рынок и аналоги

- **Незанятая ниша.** Энтерпрайз (FICO / Experian PowerCurve / C&R) скорят и решают «канал/время», но **не строят физический маршрут**; роут-тулы (Route4Me, OptimoRoute, Onfleet) строят маршрут, но **не знают про взыскание и комплаенс**. Связку целиком + локализацию под СНГ + офлайн никто не закрывает.
- **Ближайший аналог-бенчмарк — Credgenics CG Collect** (Индия/Индонезия): proximity-allocation, оптимизация маршрута, гео-фенс, **офлайн-обновления**, мультиязычность, OTP-подтверждение сбора. Это «зеркало», на которое смотреть по фичам полевого приложения.
- **Региональный референс — Zypl.ai** (родом из Таджикистана, уже в УЗ/КЗ): ИИ-скоринг тонких досье на альтернативных данных. Важно: он скорит **на выдаче** → стадия **взыскания свободна** — это и есть ваша ниша. Потенциальный референс/партнёр.
- **Стратегический козырь:** публичного контролируемого исследования «выезд против звонка» (чистый lift) **не существует**. Через ваш «маховик» + champion-challenger (тест-ячейка 5–25%, 4–6 мес) вы можете **сгенерировать это доказательство сами** — редкий defensible-актив.

### D. Регуляторика и ИБ (жёсткое отделено от best-practice)

- 🔴 **Локализация ПД.** УЗ (ZRU-547, ст. 27-1) и РФ (152-ФЗ, ст. 18(5)) — данные граждан хранить **в стране**; в РФ с **01.07.2025 — прямой запрет** на использование зарубежных БД. Вероятное следствие — **отдельные нац-развёртывания**. ТДж — локализации **нет**, но требуется **сертификация средств защиты** у регулятора.
- 🔴 **Поведение взыскателя.** Единственный числовой закон — **РФ 230-ФЗ**: **≤1 визита в неделю**, часы **будни 08–22 / выходные 09–20**, реестр ФССП, **двойное согласие** для контакта с третьими лицами, хранение записей **1.5 года**. У УЗ/ТДж спец-закона нет → ввести **внутренний стандарт** (числа РФ — разумный бенчмарк). → эти лимиты должны стать **жёсткими ограничениями оптимизатора** (частота визитов на должника, окна часов), а не пожеланием.
- **ИБ-минимум для go-live (must):** TLS в транзите; **RBAC/least-privilege — выездник видит ТОЛЬКО своих**; **tamper-evident аудит-лог** доступа к ПД (кто-что-когда); MFA на привилегиях; секреты в вольте; безопасное хранилище на мобиле + remote wipe; IR-план под сроки уведомления об утечке; **пентест до прода**. Маппинг на **ISO 27001/27701, OWASP ASVS/MASVS, NIST**.

## 5. Пакет документации для ИТ/ИБ («чтобы поняли и контролировали»)

Это и есть «спеки», от которых зависит решение о запуске. 15 артефактов:

1. Обзор системы/архитектуры (компоненты, стек, среды DEV/STAGING/PROD).
2. **Диаграммы потоков данных с границами доверия** — где ходят координаты должника и GPS выездника.
3. **Классификация и инвентарь ПД + резидентность** — показать хранение в стране (закрывает локализацию).
4. **Threat model (STRIDE)** — митигатор на каждую угрозу (подмена выездника → MFA; утечка реестра → RBAC+шифрование; и т.д.).
5. Матрица контролей (controls → ISO 27001 Annex A / NIST).
6. RBAC-матрица ролей (least privilege; выездник = только свои записи).
7. Шифрование и управление ключами (at rest / in transit).
8. Дизайн аудита/логирования (кто-что-когда смотрел в ПД, tamper-evident, SIEM-готово).
9. Сетевая/деплой-диаграмма (сегментация + резидентность).
10. Управление секретами.
11. Политика хранения/удаления ПД (особенно координаты/трекинг).
12. План реагирования на инциденты (под сроки уведомления регулятора).
13. Список третьих сторон/субпроцессоров (хостинг/гео/телеком — с подтверждением резидентности).
14. Результаты пентеста.
15. Маппинг на 152-ФЗ / ZRU-547 / закон ТДж № 1537 + ISO 27001.

> Дисклеймер: это исследование, **не юридическая консультация**. Локальные юристы по каждой юрисдикции — обязательно.
