# Данные рабочего места сотрудника

Таблица договоров и карточка используют одни поля `clients`, загруженные штатным импортом. Запись из таблицы не предусмотрена. Выборка, поиск, сортировка и страницы строятся на сервере только внутри текущего Hard/Soft-закрепления; имя сотрудника из параметров HTTP не принимается. Номер договора, партнёр, клиент и данные выдачи показываются по каждому договору отдельно.

| Интерфейс | Поле БД / исходная колонка |
|---|---|
| Договор, контрагент, клиент | contract_id, partner, client |
| Дата выдачи / оформления | kd_date / «Дата оформления КД» |
| Выданная сумма | issued_sum / «Выданная сумма» |
| Дни просрочки | dp / «ДП» |
| Текущий долг | debt_today, при отсутствии debt_total |
| Кредитные статьи | debt_overdue, interest_overdue, penalty, duty |
| Каршеринг и дополнительные статьи | dtp, rent, camera_fine, dirt, trash, new_damage, evacuation, peni, other |
| Рабочие результаты | существующие эффективные статусы и даты звонка/выезда |

Суммы сохраняют копейки; явный ноль отличается от отсутствующего значения. Неизвестная составляющая долга не подменяется нулём. Итог долга берётся из реестра, а не вычисляется повторно суммированием статей: реестр может содержать дополнительные начисления. Валюта берётся из действующего модуля `debt`, разные валюты не складываются.

## Месячные оплаты

`registry_monthly_totals` хранит по одному значению на договор и месяц. Источник — `Оплаты за MM.YY`; колонка `Текущие платежи` относится к следующему месяцу после последней явно датированной месячной колонки стандартного реестра. Если датированных колонок нет, месяц текущих платежей не угадывается по часам. Поэтому октябрьский файл при загрузке в ноябре не переносит октябрьские сборы в ноябрь.

Пустая ячейка существующей месячной колонки означает отсутствие оплаты, как в прежнем расчёте `paid_months`. Отсутствующий столбец или отсутствующий снимок договора за месяц означает неизвестное значение. Некорректная сумма не превращается в ноль. Повторный импорт заменяет значение, а не прибавляет его; подписанные отрицательные корректировки уменьшают итог. Частичный импорт не очищает сведения других договоров. Предпросмотр откатывает изменения в этой таблице вместе со всей транзакцией.

Общий итог кабинета — сумма месячных значений договоров **текущего** закрепления выбранного продукта. Это не атрибуция оплаты ответственному на историческую дату. Переназначение меняет состав кабинета, но не переписывает первичные операции и платежи. Soft/Hard переключаются отдельно, объединённого удвоенного итога нет. Количество плативших договоров считает положительные месячные значения. Ручные сообщения об оплате, чеки, суммы обещаний и последний платёж не добавляются к месячному сбору.

## Операционные показатели

Рабочие дни считаются по действующему UTC+5. Звонки/RPC/PTP/KP используют прежние правила `office_work.report` и `soft_reporting`; офисные действия и реальные выезды остаются разными метриками. Обработанные договоры — уникальные договоры текущего закрепления, упомянутые в собственных операциях периода. Собственные исторические операции сохраняются после смены закрепления; договоры вне текущих прав не раскрываются и не открываются из детализации. План не выдумывается при его отсутствии.

Действующие обещания выводятся отдельно с состояниями и реестровой сверкой. Месяц ограничивает дату обещания/срок, но сверка выполнения использует доступные фактические сведения. Показатель явно подписан как состояние действующих обещаний, а не закрытая историческая воронка.

## Актуальность и совместимость

Интерфейс показывает последний успешный импорт; у детализации месячной оплаты есть время наблюдения конкретного значения. Частичный/отсутствующий месячный источник отмечается в кабинете. Начальное заполнение новой месячной таблицы — отдельная журналируемая операция из стабильного текущего master с проверкой идентичности договора/партнёра и online backup; назначения и бизнес-поля не изменяются.

Новые GET API и поля карточки аддитивны. Контракт обмена 11, существующие поля/схема экспорта и каналы других приложений не меняются. Токены, DPAPI-ключи, идентификаторы приложений и прежняя очередь сохраняются.

Существующее ограничение БД `UNIQUE(contract_id)` для одинаковых номеров разных партнёров остаётся отдельной задачей. Такие неоднозначные строки не суммируются дважды и исключаются из начального заполнения месячных снимков, а не объединяются догадкой.
