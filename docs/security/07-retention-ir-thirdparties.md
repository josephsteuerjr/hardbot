# 11+12+13. Retention, IR-план, третьи стороны

## 11. Политика хранения и удаления ПД (retention)

| Данные | Срок хранения | Основание / правило |
|---|---|---|
| Записи взаимодействий с должником (`visits`, аудит контактов) | **1.5 года** | РФ 230-ФЗ (хранение записей) |
| Реестр должников (`clients`) | На время работы по портфелю + срок по договору с принципалом | Договорный; по достижении цели — удаление/обезличивание |
| GPS-координаты / `markers` / трекинг | Минимально необходимый; пересмотр после закрытия дела | Минимизация (С3-чувствительное) |
| Фото | До закрытия дела, затем удаление | Минимизация |
| Аудит-лог доступа | ≥ срока хранения связанных ПД | A.8.15 |
| Бэкапы | `keep_daily: 7, keep_weekly: 4` (borgmatic) | Ротация |
| Синтетика (демо) | Бессрочно (ПД нет) | — |

**Процедуры (к формализации):**
- **Удаление по запросу субъекта / по достижении цели:** удалить строки должника из `clients`,
  связанные `visits`/`markers`/фото; в аудите оставить факт удаления (не сами ПД).
- **Обезличивание для аналитики:** агрегаты в дашборде без идентификаторов (уже так).
- **Право на доступ/исправление** субъекта — через оператора (DPO), процедура к описанию.

> GAP: процедуры удаления/обезличивания пока не автоматизированы — нужен скрипт `purge(contract_id)`
> и регламент. Рекомендация к go-live.

## 12. План реагирования на инциденты (IR)

### Сроки уведомления (жёсткие)
- **РФ 152-ФЗ:** уведомить РКН об утечке — **в течение 24 часов** (первичное), 72 ч — детали.
- УЗ/ТДж — по локальному регулятору (уточнить у юристов).

### Этапы
1. **Обнаружение** — алерт из аудита/SIEM, жалоба, аномалия. Точка контакта: владелец (ADMIN).
2. **Локализация** — отключить скомпрометированный узел; на боте — остановить поллер; сменить
   `BOT_TOKEN`/`ENGINE_API_TOKEN`/`ADMIN_API_KEY`; отозвать привязки (`unbind`).
3. **Оценка** — что за данные, сколько субъектов, юрисдикция (по `audit` и БД).
4. **Уведомление** — РКН (24 ч), принципал (ЗК/Делимобиль) по договору, субъекты при высоком риске.
5. **Восстановление** — из бэкапа (borgmatic), проверка целостности (`selftest`).
6. **Post-mortem** — причина, контроль, обновить threat model.

## 13. Третьи стороны / субпроцессоры

| Сторона | Роль | ПД? | Резидентность | Примечание |
|---|---|---|---|---|
| **Telegram** | Транспорт сообщений/миниаппа | telegram_id, контент карточки в транзите | Внешнее облако | Неизбежно (канал бота); ПД в БД у нас, не у Telegram |
| **Let's Encrypt** | TLS-сертификаты | Нет (только домен) | Внешнее | Только издание сертификатов |
| **OSM/Nominatim/Photon (публ.)** | Геокодер (по умолчанию) | **адрес должника** при запросе | Внешнее | 🔴 на PROD заменить на СВОЙ инстанс/офлайн |
| **GeoNames** | Офлайн-дамп газеттира | Нет (скачивается единожды) | Локально | CC-BY |
| **Yandex Geocoder** (опц.) | Точный геокодер РФ | адрес | РФ | Только при `YANDEX_GEOCODER_KEY` + Advanced-лицензия для хранения |
| **Yandex Object Storage** (план) | Бэкапы | зашифрованные бэкапы | **РФ** | Закрывает локализацию бэкапов |
| **Tailscale/Headscale** (план) | VPN-доступ к филиалу | Нет (метаданные) | Headscale — свой контрол-сервер (план Б при блокировке) | |
| Хостинг-провайдер VPS (демо) | Демо-стенд | **Нет ПД** (синтетика) | — | ПД туда не уезжают |

**Контроль:** на PROD исключить публичные геокодеры для реальных адресов; подтвердить
резидентность бэкапов (РФ); вести реестр субпроцессоров и DPA с каждым, кто касается ПД.
