# Руководитель: сравнение и предлагаемый рабочий вариант

Основание: поручение владельца 14.11.2026 — сравнить действующий отдельный
«Руководитель» с первым CRM-кандидатом от 03.11, выбрать оптимальную структуру
и закончить таблицу сотрудника. Версии для сравнения подтверждены владельцем.

## Предлагаемая структура

**Обзор → Портфель → Команда → Задачи → Показатели → Скрипт → Подключение.**

Это проект решения, а не новое дословное требование владельца.

- **Обзор.** Что требует вмешательства: договоры без результата, истёкшие обещания,
  просроченные задачи, ожидающие заявки устройств. Каждое число открывает тот же
  набор строк или событий. Область: команда/офис/сотрудник, период — явный.
- **Портфель.** Канонические договоры в таблице; доска — дополнительное представление.
  Один отбор, одна сумма, те же права. Виды работы звонок/выезд/оба/доставка не
  создают двух портфелей и не удваивают долг. Одинаковый КД разных кредиторов
  остаётся двумя договорами. Клиент объединяет свои договоры, сохраняя их различие.
  Результаты звонка и выезда остаются отдельными; доска должна явно показывать
  выбранный вид результата или определённую проблему, а не выдуманный общий статус.
- **Команда.** Полный состав в разрешённой кадровой области. Из сотрудника доступны
  его портфель, подтверждённые результаты, задачи, смены/активность и вход/устройства.
  Добавление на доску, назначение договора, выдача роли и подтверждение устройства
  остаются разными действиями с разными полномочиями.
- **Задачи.** Сроки и исполнители, состояния и переход к клиенту. Для руководителя
  это рабочий инструмент распределения отдельных поручений; ежедневный звонок
  сотрудника по-прежнему не требует задачи.
- **Показатели.** Сводка команды за период с детализацией до исходных событий/КД.
  Звонки, выезды, обработанные договоры, месячные поступления, заявленные оплаты,
  обещания и время не смешиваются. Excel — действие текущего отчёта, не отдельная
  параллельная модель работы. Данные без установленного источника не считать нулём.
- **Скрипт.** Черновик, опубликованная версия, аудитория и история публикаций.
- **Подключение.** Собственная личность, доступ, связь, очередь и диагностика.
  «Вход команды» здесь не дублируется. Административный «Контроль» сохраняется
  как отдельная возможность только при существующем capability.

Убираются дубли меню: Рабочий обзор/Активность/Команда не становятся тремя
конкурирующими главными страницами. Обещания становятся отбором и раскрытием
в соответствующем контексте. Отчёт — текущая выгрузка Показателей. При этом
пользовательские возможности старых экранов сохраняются по матрице выше.

## Что уже есть в CRM и что действительно предстоит сделать

| Основа | Состояние | Следующая реализация |
|---|---|---|
| Портфель/карточка/история | Канонические UUID, общее чтение и собственные полномочия, dual-work без двойного долга | Менеджерская компоновка и общие отборы/переходы, сохранение контекста |
| Задачи | Общий `tasks`, назначение, детали и завершение реализованы | Свести их с сотрудником/карточкой и менеджерскими списками без второй сущности |
| Показатели сотрудника | `cabinet.dashboard` разрешает выбранного сотрудника по серверной области | Командный read model и пакетная сводка; не выполнять десятки запросов на каждый элемент интерфейса |
| Смены | Есть командный `shift-report` | Показ в сотруднике и Показателях с прежним смыслом |
| Активное время | `active_time.summary` сейчас читает только собственные интервалы | Новый scoped read сотрудников команды, отдельная проверка прав и часового пояса; не подмена principal на клиенте |
| Скрипт | Версионная публикация и snapshot открытой формы готовы | Отдельный руководительский экран и сохранение аудитории/прав |
| Входы, устройства, полный состав | Полноценные действия находятся в действующем primary manager API | Безопасный адаптер/маршруты с теми же manager gates и постоянным соответствием личности |
| Обзор обещаний, доказательства, чеки | Есть в прежнем продукте, не всё представлено в новой роли | Инвентаризировать источники, добавить недостающие scoped read DTO; не объявлять это готовым по красивому макету |

Особые ограничения доступа:

- Руководитель читает договор по серверному scope, но не становится сотрудником
  при просмотре и не записывает звонок от его имени.
- Право управлять устройством не даёт право менять бухгалтерские значения,
  кадровую личность или чужой результат. Роль PostgreSQL приложения остаётся
  SELECT-only к кадровым таблицам; расширять её ради интерфейса нельзя.
- Сопоставление кадровой записи, аккаунта, устройства и `employee_uuid` — явное.
  При неоднозначности показывается состояние сверки; по совпадению ФИО доступ
  не выдаётся. Полный roster и активные CRM memberships — разные наборы.
- Старый обмен и авторство истории сохраняются; initial import/baseline не повторять.
- «Внедрение» и Excel-обмен остаются доступными тем ролям, которым уже разрешены;
  перенос из повседневной навигации не означает удаления или выдачи новых прав.

## Порядок следующей реализации

1. Закрыть доработку реестра сотрудника и его повторный запуск/права. Это сделано
   в текущем SOURCE, результаты ниже; доставленный pilot.7 не перезаписывался.
2. Собрать один сквозной read-сценарий Руководителя: **Обзор → отбор команды →
   сотрудник/договор → полная карточка → возврат в тот же список**. Числа и строки
   должны совпадать в реальном PostgreSQL, включая двойную работу и разные валюты.
3. Встроить существующую задачу: назначить из клиента → сотрудник получает →
   выполняет разрешённую работу → результат/завершение видны руководителю.
4. Подключить полный состав, входы и устройства через действующие scoped gates.
   Проверить человека без профиля/договора, повтор заявки, отзыв и чужую область.
5. Свести Показатели/время и сохранить точные определения/источники сумм.
   Перенести подтверждения/документы, не теряя возможностей прежней программы.
6. Проверить полный день руководителя в собранном клиенте, затем готовить
   следующую общую поставку. Не делать новый EXE вместо этой функциональной работы.

## Реально сделанное по таблице в этом этапе

- Явные границы колонок с перетягиванием, клавиатурой, сбросом одной/всех ширин.
  Ширины адресованы ключам колонок и хранятся в существующем DPAPI-профиле личности.
- При масштабе ширина пересчитывается из логического размера, не накапливает ошибку.
- Закреплённый номер/кредитор стоит после фактической ширины служебной колонки;
  граница не зависит от прежней константы 120px и от padding.
- Активная ячейка и граница выделения сохраняются по UUID договора и ключу поля,
  а не только по номеру строки. Выделение не сбрасывается при перерисовке.
- Сохраняются обе координаты прокрутки и настройки при выходе из раздела.
- Проверен настоящий Chromium pointer drag и клавиатурное изменение, геометрия
  при 125%, обновление/перезапуск, сброс, раздельные профили, черновик/очередь,
  потерянный ACK, конфликт и отсутствие фиктивных рабочих фактов.

Проверки: TypeScript, сборка renderer и два запуска настоящего Electron/main/
preload/DPAPI с синтетической базой. Изменения интерфейса находятся в SOURCE;
новый установщик в этом этапе не собирался, сервер/данные/feeds не менялись.
