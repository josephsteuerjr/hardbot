# Быстрый обмен — опыт 30.09.2026 (ветка `exp/fast-exchange`)

Вопрос владельца: почему обогащение и импорт такие медленные, и можно ли
через локальную базу. Правило — «не навреди»: смысл обмена не меняется,
меняется только, как байты ездят и как Excel пишет.

## Где уходило время (замеры, только чтение шары)

| что | было | замер |
|---|---|---|
| обращение к шаре U: | — | ~75 мс на любой stat/открытие (WAN) |
| SHA-256 книги выездника по сети | 3 раза на книгу | 0,43 с (книга 0,1 МБ) |
| Excel открывает книгу с шары | 2 раза на книгу | ~2 с (локально 0,13 с) |
| запись ячейки через `xw.Range.value` | по одной | 16,7 мс/ячейку |
| та же ячейка напрямую `Cells(r,c).Value` | — | 1,9 мс/ячейку |
| реестр 50 тыс. строк: JSON, как шлёт пульт | 2 раза (предпросмотр + применение) | 45–57 МБ, gzip — 3–6 МБ |
| сервер: `import_grid` на 50 тыс. строк | — | 1,4–2,5 с — не узкое место |

Книг выездников 54, всего 4,5 МБ; общий реестр — 8,9 МБ xlsb, 50 614 строк.

## Что сделано в ветке

1. **Обогащение, способ `local`** (`enrich_many(engine="local")`): книга один
   раз читается с шары → Excel работает с локальной копией (план, запись
   напрямую через COM, сохранение, повторное открытие и нулевой второй план —
   всё локально) → копия «до обогащения» из нетронутой локальной копии →
   если книгу за это время никто не открыл и не изменил, проверенный файл
   заменяет её на шаре (служебная копия рядом + переименование, как делает сам
   Excel). Всё, что ломается до замены, оставляет книгу на шаре нетронутой.
2. **Запись через COM** (`_write_cells`, и в способе `share+batch`): те же
   значения, даты через преобразователь самого xlwings (наивный datetime
   pywin32 сдвигает на часовой пояс: 30.09 → 29.09 20:00 — проверено).
3. **Цифры, которые Excel портит** (`excel_digits_lossy`): «0012345» → 12345,
   больше 15 цифр — потеря точности. Теперь такие строки пишутся текстом.
   Ошибка есть и в main: книга сохраняется искажённой, а повторная сверка
   падает «план не нулевой» уже после записи.
4. **Сжатие тела запроса** пульта (> 64 КБ → gzip). aiohttp распаковывает сам и
   меряет лимит по распакованному (проверено: 8,8 МБ в 21 КБ gzip → 413).
5. **Импорт разницей** (`server/grid_delta.py`, `pult/core/exchange_state.py`):
   пульт помнит в локальной SQLite последние отправленные гриды и шлёт разницу;
   сервер помнит 3 последних принятых грида, собирает из разницы тот же грид и
   сверяет SHA-256 — дальше путь импорта прежний. Не знает базы или отпечаток
   не сошёлся — 409, пульт шлёт целиком.

## Сравнение подходов (синтетика, `bench/`)

**Обогащение, A/B** (`bench/enrich_ab.py`, книга 330 строк, «шара» — локальная
папка той же формы): 5 сценариев — свежие выезды с реестром доставленного, без
него, «сервер главнее», решения по конфликтам, вся история (3 049 ячеек).
Каждую книгу Excel пересохраняет в xlsx, openpyxl сверяет каждую ячейку
(значение, тип, формат, шрифт, заливка, апостроф) — 14,8–16,9 тыс. ячеек.

| сценарий | share (как было) | share+batch | local | совпало |
|---|---|---|---|---|
| свежие выезды (~590 ячеек) | 13,1 с | 4,6 с | 4,5 с | отчёт и все ячейки |
| вся история (3 049 ячеек) | 52,7 с | 9,1 с | 9,0 с | отчёт и все ячейки |
| повторный прогон | 0 записей | 0 | 0 | — |

Из ~4,5 с около 3,3 с — запуск Excel на прогон (один раз на пачку, не на
книгу). На настоящей шаре `local` дополнительно убирает два открытия по сети
и сохранение по сети (~2 с каждое): оценка на книгу — ~3 с вместо ~9 с,
книга без записей — ~1,4 с вместо ~5 с.

Гонки (только `local`): книгу держат открытой с начала — отказ, книга цела;
её изменили посреди прогона — отказ, правка офиса сохранена; открыли перед
заменой — отказ, книга цела; служебных файлов не остаётся.

**Импорт разницей** (`bench/delta_bench.py`, 50 тыс. строк; целиком — 45 МБ
JSON, 3 МБ gzip):

| изменение | разница (gzip) | собрано = новое |
|---|---|---|
| без изменений | 0,1 КБ | да |
| 0,1 % строк | 4,6 КБ | да |
| 1 % строк | 38 КБ | да |
| 10 % строк | 369 КБ | да |
| +500 строк в конце / +300 вразброс / −400 | 34 / 21 / 1 КБ | да |
| переназначено 2 000 договоров | 132 КБ | да |
| пересортировка всех строк / новая колонка | 3,3 / 3,2 МБ (как целиком) | да |

Расчёт разницы на пульте ~1 с, сборка на сервере ~0,3 с.

Итого по импорту: сегодня по туннелю дважды едет 45–57 МБ; с gzip — 3–6 МБ;
с разницей — десятки–сотни КБ при обычном ежедневном обновлении.

Один прогон `local` на одной книге (Хазраткулов, 99 ячеек в 20 договорах, без

`share` 6,6–8,5 с, `local` 4,0 с. Для записи сравнения на той же книге нет;
с этого коммита `local` пишет в отчёт время по шагам (`steps`).

## Чего опыт НЕ проверил и что нужно перед выкладкой

- Запись на настоящую шару не делалась (правило «не сорить на U:»). Нужна
  тестовая папка на шаре или один прогон `local` на одной книге под присмотром.
- Скорость туннеля до сервера не мерялась (не гонял мусор на прод); выигрыш gzip
  и разницы пересчитан из объёмов.
- Способ `local` в пульте пока не включён: `enrich_many` по умолчанию `share`.
- Разница пока только в пульте аналитика на Hélène (`desk_registry`); Qt-пульт
  и `limited_test_import.py` шлют целиком (и так и должны работать).

Порядок включения, если владелец скажет «да»: (1) gzip и «цифры» — в main сразу,
риск минимальный; (2) `local` — за переключателем, сначала один прогон на одной
книге; (3) разница — после выкладки сервера, с переключателем в пульте.
