### P0: умножение проверок входа и задержек
`server/crm/shared_auth.py:242-250` при каждом `authenticate` заново вызывает primary, затем выполняет привязку личности. Сеанс CRM подписан на 30 минут, но не освобождает запросы от синхронной зависимости от primary. `Authority` ждёт до 8 секунд (`shared_auth.py:100-114`).
Windows опрашивает изменения каждые 500 мс после успешного ответа (`hard-desk/src/main/crm-live.ts:13-35`). Его транспорт `changes` прекращает ожидание через 4 секунды (`crm-pilot.ts`), хотя только внутренняя проверка primary может занимать до 8 секунд. Мобильный `/mobile/api` сначала вызывает `authorize → context`, затем основное действие (`mobile_server.py:211-219`): цепочка CRM authentication выполняется дважды, а мобильное состояние SQLite также записывается после каждой части.
За предыдущие сутки в журнале primary найдены 204 600 обращений `/api/crm-identity` и 110 515 `/api/manager/device/me`: 315 115 проверок, в среднем 3,65 в секунду. Это подтверждённая нагрузка самой архитектуры, а не предположение о качестве внешнего канала.
Внешний `mobile/health` в 12 последовательных измерениях дал медиану 0,713 с. Изнутри сервера mobile health отвечал примерно за 0,03 с, CRM health — за 0,07 с. При этом `ready.json` primary в одном из восьми внутренних запросов занял 2,268 с. Следовательно, есть и стоимость внешнего TLS/канала, и внутренние всплески primary. Журнал API содержит два `ConnectionResetError` при чтении тела запроса; службы при этом продолжили работать.
### P0: мобильный вход не восстанавливается после invalid CRM token
`mobile_backend.py:174-178` повторяет `/auth/exchange` только для `pilot_session_expired`. Для `pilot_session_invalid` обмен не выполняется. `mobile_server.py:152-159` на полученные 401/403/410 удаляет BFF-сессию. Следовательно, смена ключа/конфигурации CRM или иная инвалидация промежуточного токена становится принудительным выходом даже при действующем исходном входе. Локальный пробник подтвердил: invalid возвращается наружу без попытки exchange.
Windows уже содержит иной путь: `crm-pilot.ts` обновляет CRM token после expired и invalid, а явный отзыв исходного аккаунта отделяет от временной сетевой ошибки. Не копируйте из этого поведения принудительный выход при любой 403: причина и fingerprint сохранённого аккаунта должны проверяться раздельно.
### Порядок устранения
1. Добавить регрессию mobile invalid → один exchange → повтор исходного действия с прежним operation_id; сохранить принудительный выход при действительном отзыве primary. Затем выровнять обработку invalid и expired в BFF.
2. Убрать двойной `context` и повторную запись состояния на обычный `/mobile/api`. Права должна проверять целевая операция; `authorize` для boot и для действия нужно разделить, не ослабляя серверную проверку конкретного договора.
3. Ввести короткий кэш подтверждения primary с явно ограниченной задержкой отзыва, например 15–30 секунд. Ответы 401/403/410 не кэшировать как разрешение. Поведение при временной недоступности primary определить явно: новый exchange запрещать, а для неистёкшей CRM-сессии допускать только короткий документированный grace при ранее подтверждённой личности. Не заменять это неограниченным fail-open.
4. Убрать опрос 2 Гц на клиента: начать с интервала около 2 секунд с jitter и экспоненциального backoff при простое/ошибке, затем рассмотреть long poll/SSE. Согласовать клиентский timeout с серверным бюджетом, чтобы отменённый клиентом запрос не продолжал неучтённую цепочку.
5. Добавить метрики route, status, CRM/upstream latency, exchange/refresh и причину выхода без токенов и персональных данных. Сейчас production p95 аутентифицированных действий из имеющихся access logs не восстанавливается, поэтому выигрыш нужно измерять до/после на одинаковом сценарии.
6. Отдельно решить политику 48 часов: скользящее продление при активности либо предупреждение до дедлайна и понятный повторный вход. Это текущее фиксированное поведение, а не случайный сбой.

## Архитектура и границы служб
### Один запрос от телефона
Браузер открывает https://hard.rimborso.ru. Корневая страница подключает ресурсы с /mobile/ того же origin. Caddy передаёт мобильные запросы в BFF, серверный адаптер браузера. BFF проверяет сеанс, обращается к службе входов и к API CRM. Браузер получает доступное представление и квитанции. Установленный Windows-клиент обращается к службам через свой основной процесс.
### Что где выполняется
- SOURCE `hard-desk/ui/` — общие экраны TypeScript. `crm-app.ts` задаёт меню роли и команды карточки. `ui/mobile/` — браузерный мост, оболочка, хранилище, маршрут и обновления. `src/crm-preload.ts` и `src/main/` — мост и привилегированный код Electron.
- `server/crm/mobile_server.py` и `mobile_backend.py` — HTTP, сессии и вызовы CRM. `shared_server.py` поднимает API и планировщик. `http.py` проверяет и распределяет запросы по операциям. `storage.py` подключает PostgreSQL для общего контура.
- Primary обслуживает существующие аккаунты и устройства в SQLite. В рабочей PostgreSQL находятся договоры, события CRM, назначения и действующий реестр. Файлы документов хранятся отдельно. Для новых XLSX на сервере есть Linux-исполнитель.
- `deploy/crm/compose.yml` задаёт mobile, api и exchange. Caddy направляет /mobile/* в crm-mobile-api:8081, а /crm-pilot/* со снятием префикса в crm-runtime-api:8080. Exchange использует смонтированный сокет PostgreSQL и статус очереди.
### Карта развёртывания
Основа Caddy и Docker находится в `/opt/hard/deploy/units/core`, рабочий каталог CRM — под `/opt/rimborso-crm-runtime/`. Шаблон Compose в Git и конфигурация рабочего выпуска могут содержать разные теги образов API и mobile. При разборе инцидента читайте фактические image ID, mounts и build ID.

## Первый запуск на учебных данных

Нужны Python с venv, Node с npm и Git. Для живых операций с Excel нужен Windows с Excel. В новом локальном клоне SOURCE или отдельном рабочем каталоге установите зависимости. Для уже подготовленного рабочего дерева используйте его окружение. Установка npm ci заменяет node_modules в выбранном каталоге.
```
python -m venv .venv

python -m pip install -r server/requirements-crm.txt
python -m pip install xlsxwriter==3.2.9

npm --prefix hard-desk run check
```
### Собрать и запустить только локальный сайт
В PowerShell из SOURCE задайте новый каталог учебного стенда под своим TEMP. Сборщик требует отдельный выходной путь. В журнале запуска появится локальный адрес со свободным портом.
```
$qa = Join-Path $env:TEMP ('crm-demo-' + (Get-Date -Format yyyyMMddHHmmss))
$env:HARD_CRM_MOBILE_OUT = Join-Path $qa 'web'
Push-Location hard-desk
node tools/build-mobile.mjs
Pop-Location
$env:PYTHONPATH = (Get-Location).Path
Push-Location server
python -X utf8 -m crm.mobile_server --demo-home "$qa/data" --assets "$qa/web"
```
Откройте напечатанный адрес /mobile/ и выберите учебную роль. «Сотрудник → Портфель» должен показать синтетические договоры. Под «Руководителем» откройте «Команда → Результаты». Для остановки нажмите Ctrl+C, затем выполните `Pop-Location`. Источники стенда и мобильное состояние лежат в каталоге QA. Этот запуск проверяет локальный BFF и интерфейс. Для проверок блокировок и прав SQL нужна отдельная PostgreSQL.

## Права пользователей и журнал событий
### Как проверяется действие
Primary проверяет аккаунт, устройство и действительность входа. API связывает подтверждённого пользователя с кадровой записью. Роль задаёт базовый набор действий, а область, действующее назначение, поручение и статус договора ограничивают конкретный запрос. Скрытая кнопка — только представление этой проверки. Проверьте и серверный путь записи, и выдачу детализации.
### Роли и границы
- Сотрудник получает call и/или visit для своих работ. Курьер фиксирует delivery в назначении, логист ведёт пулы своей страны. Курьерский обзвон даёт адресное право на один КД и сохраняет основное назначение.
- Руководитель распределяет в разрешённой области, получает отчёты, обслуживает доступные аккаунты. Владелец и специальный признак server_operator дают дополнительные возможности там, где это проверяет сервер. Наблюдателю доступно чтение. Аналитик имеет права на реестр, обмен и разрешённые учётные изменения.
### Данные для трассировки
`crm_people` и `crm_contracts` связывают лицо и КД. Используйте внутренний UUID договора. Во внешних книгах сверяйте ещё кредитора и, когда это требуется источником, дату входа. `crm_employees`, `crm_actor_links`, `crm_memberships` и `crm_assignments` отвечают за кадровую область и работу.
`crm_commands` хранит команды с устойчивым идентификатором, `crm_events` — принятую историю, `crm_event_contracts` — связь с одним или несколькими договорами. `crm_outbox` и квитанции доставки позволяют догнать проекции. Повтор после потери ответа должен использовать исходный operation_id. Исправление факта связывается с исходным событием.
> Основные точки чтения кода — server/crm/roles.py, access.py, shared_auth.py, store.py, assignments.py, withdrawals.py и postgres_schema.py. Версия схемы в проверенном SOURCE — 9 в schema.py. Значение работающей БД сверяйте с /health.

## От экрана до API и базы
### Трасса одного выезда
В `hard-desk/ui/crm-app.ts` найдите actionForm, затем `crm-visit.ts`. На телефоне мост готовит документ и запись команды. На сервере BFF принимает действие через /mobile/api или файловый маршрут, общий API передаёт его в обработчик по методу и имени операции. У операции есть автор, договоры, версия полей и устойчивая квитанция.
1. Для поиска причины начните с КД, автора, времени и operation_id. Проверьте ожидающую локальную запись либо квитанцию. Различайте время работы и момент приёма сервером.
2. Для принятого выезда проследите event_id через crm_event_contracts, проверьте исходный авторский профиль. Карточка, история и отчёт должны учитывать те же связи и область.
3. Для пропавшего фото сверяйте document_id, КД и SHA-256. Для расхождения суммы сопоставьте reported_payment, payment_confirmed и реестровый источник.
### Справочник точек входа
- `shared_server.py` — POST /auth/exchange и GET /health. `http.py` регистрирует GET/POST для /api/crm/{action} и /admin/crm/{action}. Префикс внешнего прокси — /crm-pilot/.
- Чтение портфеля, карточки и реестра — work-portfolio, portfolio, card, registry. При отладке передавайте штатные фильтры, проверяйте область до пагинации. Правки таблицы — registry-edit с версиями и явными очистками.
- Командные отчёты — manager-statistics и manager-report. Для аналитика есть отдельные analyst-statistics и analyst-report. Основной код в manager_reports.py, three_hour.py, team_visits_export.py, payment_read.py.
- Мобильные маршруты под /mobile/ — boot, login, resume, logout, password, api, upload, workbook, receipts, file и health. Смотрите точные методы и аргументы в нижней части mobile_server.py. Административные операции используют отдельные проверки.
### Изменение текущих полей
Пакет правок реестра проверяется целиком, с актуальными полномочиями и версиями затрагиваемых групп. Он создаёт registry_edit с аудитом «до/после». Отдельное событие звонка, выезда или доставки создаёт фактическую работу. Тестируйте одновременно карточку, реестр, историю и счётчик отчёта.

## Офлайн и доставка новой оболочки
### Два хранилища на одном origin
В Cache Storage находятся ресурсы оболочки с контрольными суммами. В IndexedDB `rimborso-crm-mobile-v1` лежат stores vault и keys. AES-GCM защищает записи, ключ создаётся неэкспортируемым. Адрес записи включает владельца и хеш имени, а связанные данные шифрования — origin и адрес. Чтения кешируются по запросу. «Загрузить выезды офлайн» последовательно читает страницы назначений и карточки.
### Порядок при записи выезда
1. Сохранить выбранные исходные байты и метаданные локально до обработки. Дождаться сохранения выбранной пачки. Подготовить фото со стабильным ID и записать привязку в долговечный черновик. После перезапуска продолжить подготовку от сохранённого состояния.
2. Проверить владельца, доступ и договор. Получить от сервера подтверждение document_id, КД и SHA-256. Затем отправить зависимую команду выезда. Проверить идентификаторы операции и события. При обрыве после приёма сервером повторить прежний ID.
3. При временном сбое или неубедительной квитанции оставить запись ожидающей. При содержательном конфликте показать сверку. Исходная старая PWA хранит данные в отдельной IndexedDB hardbot. Удаление устаревших ресурсов оболочки эту базу не переносит.
### Сеанс и доставка нового клиента
Срок подтверждённого сеанса BFF — 48 часов от начала; обычная активность его не сдвигает. Ещё действующие старые сеансы могут получить новый срок после проверки прав. Истёкшие требуют входа. Истечение блокирует локальный доступ, сохраняя данные владельца. Cookie рабочего HTTPS использует Secure, HttpOnly, SameSite=Strict. Отдельный CRM token действует 30 минут и обновляется через исходный вход. На 24 ноября мобильный BFF обновляет его после expired, но не после invalid — см. системное ревью в начале книги.
updates.ts проверяет BUILD.json при старте, возврате, появлении сети и раз в минуту. Обновление ждёт готовый worker, закрытие формы и завершение записей IndexedDB, затем перезагружает приложение. Корневой worker обеспечивает переход старого ярлыка. Проверяйте Chromium и WebKit на паре точных сборок с разрывом связи, открытой формой, холодным стартом и потерей квитанции.

## Обмен книгами и учёт платежей
### Три отдельных операции
Штатный импорт Аналитика обновляет рабочий реестр и закрепления по принятому предпросмотру. Обогащение записывает разрешённые результаты в личные книги и хранит подтверждения по полям. Версионированная книга CRM экспортируется со снимком и манифестом. Её возврат проходит import-preview и import-apply. Пустая ячейка сохраняет данные. Явная очистка возвращаемой книги задаётся `[[CLEAR]]`.
При импорте сверяйте источник, период, контрольную сумму, соответствия, выбранных сотрудников и снятия. Если расходятся доказанные значения книги и сервера, зарегистрируйте конфликт. Запуск с неизвестным исходом проверяется по сохранённому номеру операции.
### Исполнители и форматы
Windows меняет существующие XLSB/XLSM через Excel и xlwings, читает через calamine или xlwings. Серверный Linux-исполнитель создаёт новые XLSX через XlsxWriter, затем проверяет чтением. Отправка через Outlook выполняется в профиле Windows. Для новой серверной выгрузки сверяйте типы дат и чисел, SHA файла, квитанцию, листы и число строк.
Отдельный `registry_cycle/` переносит личные XLSB в общий реестр и обратно. Выбор владельца идёт по полю ответственного, соответствие — по заголовкам. Сумма и дата последнего платежа сотрудника имеют иного владельца данных, чем аналитические «Текущие платежи» и месячные суммы. См. registry_cycle/README.md.
### Деловые ограничения
Заявленная оплата, подтверждённое поступление и обещание — отдельные сущности. Сводки нужно сверять с источником за тот же период. Подтверждённый отзыв блокирует контакт и новое назначение независимо от старого Excel. Для смены статуса `tools/crm_runtime.py contact-status` требует доказательство источника. Предварительный результат даёт хеш для адресного применения оператором.
Для разбора доступны `server/registry_postgres.py`, `server/crm/exchange.py`, `legacy_exchange.py`, `payment_read.py` и `docs/CRM_CONFIRMED_WITHDRAWALS.md`. Подробности прежних Excel-колонок — в корневом инженерном руководстве по колонкам реестра.

## Назначения и отчётность по работе
### Распределение и устаревшие писатели
Предпросмотр фиксирует отбор договоров, версии и вид работы. Подтверждение сохраняет ID операции. Серверный worker продолжает пакеты после закрытия экрана, проверяя полномочия. Отмена останавливает остаток. Сверяйте квитанцию и изменения портфелей прежнего и нового сотрудника. Изменения доставляются через опрос с курсором; в текущем Windows-клиенте успешный цикл повторяется через 500 мс, что является подтверждённым источником лишней нагрузки из системного ревью.
При переходе на CRM прежний путь записи по выбранным КД блокируется в primary. PostgreSQL принимает дальнейшие команды. Точки кода — primary_fence.py, runtime.py, assignments.py и legacy_mirror.py. После рабочей отсечки штатный обмен использует PostgreSQL. Фоновый старый импорт и однократная миграция имеют разные условия запуска.
### Курьерский цикл
logistics_schema.py и logistics.py хранят пулы страны, назначения на обзвон и историю. Предпросмотр сопоставляет книгу по контрагенту и КД. Отдельными полномочиями располагают логист пула, физический курьер и исполнитель обзвона. Проверяйте замену или снятие Софта и отзыв права по прежней строке. Интерфейсы — crm-logistics.ts и crm-delivery.ts.
### Три ответа на вопрос о работе отдела
- manager-statistics считает события по исходному автору и области команды. Выгрузка выездов за интервал до 31 дня использует тот же журнал. Листы «Сводка», «Выезды» и «По дням» должны сходиться при одинаковом отборе. При частичной видимости связанного набора КД часть подробностей события скрыта.
- Трёхчасовой механизм хранит первый фактически записанный срез интервала. Пропущенный срез при простое остаётся пропущенным. Сравнивайте один канал и границы рабочего дня. Итоги месяца раскрываются до исходных событий.
- Портфель показывает текущее состояние договоров и закреплений. Переназначение меняет состав портфеля, но автор принятого факта сохраняется. Для месячных оплат проверьте происхождение суммы и дату последнего поступившего источника.
> Регрессия ноября: прежняя выгрузка читала SQLite и пропускала новые выезды. В проверке отчёта создайте факт в каноническом журнале и подтвердите его через экран команды и сохранённый XLSX.

Для SQL-прогона нужен приватный файл HARD_CRM_TEST_DSN_FILE, роль и база выделенного QA. tests/test_crm_postgres.py проверяет реальный адаптер. tests/test_crm_postgres_app_role.py проверяет ограниченную роль. Входы, реестры и устройства для проверки берите на стенде.
### Что проверять по затронутой функции
- Форма, очередь или сессия — два браузерных движка, закрытие при подготовке фото, отказ сети, принятый результат с потерянным ответом, повтор со стабильным ID. На 47-м часу есть доступ к закешированной карточке, на 49-м требуется вход. Проверить повторный вход того же владельца и переключение личности.
- Назначение, реестр или отзыв — разрешённый договор, чужой договор, отозванный доступ, запись из устаревшей карточки, конфликт версии и два одновременных изменения. Сверить историю, текущую проекцию и данные второго пользователя.
- Отчёт — выбор дня и периода, границы дат местной зоны, автора, офис, регион и частично доступное событие. Сопоставить цифру, детализацию и XLSX. Сохраняемую книгу прочитайте calamine.
- Windows — проверить точный установщик в отдельном QA-профиле, вход, повторный запуск, защищённую очередь, обновление с предыдущего выпуска. Для Excel-пути использовать настоящий Excel на проверочной книге. Для изменения мобильной оболочки дополнительно пройти обновление именно с прежнего раздаваемого пакета.
Результат браузерной автоматизации и приёмка физического Android/iPhone фиксируются отдельно. Для актуальной сборки ранее сохранены квитанции обоих движков. Скриншоты в пользовательской методичке получены из локального SyntheticBackend с точным опубликованным веб-пакетом.

### Windows
Для Харда, Софта, Руководителя и Аналитика основные точки — `hard-desk/tools/products.mjs`, `installers.mjs`, `prepare-release.mjs` и `src/main/updates.ts`. Проверьте идентификатор продукта и канал. Используйте отдельное сборочное дерево с зависимостями из package-lock и Windows-окружение сборки с PyInstaller и библиотеками бэкенда из tools/build-backend.py. Проверьте SOURCE-MANIFEST.json подготовленного бэкенда: сборщик использует манифест исходников.
```

npm run check
npm run backend
node tools/installers.mjs manager
```
Это локальная сборка выбранного пакета. Для другого продукта берите его id из products.mjs. Аналитик имеет собственный корпоративный канал. На машине сборки заранее проверьте место и прежние процессы. Подготовку подписи, совместимость старого обновлятора и зеркала сверяйте с квитанциями соответствующего продукта. Подпись канала и Windows Authenticode — разные проверки.

`node tools/test-setup-flow.cjs` проверяет реальные установку, обновление и удаление в отдельном QA appId. Обязательны Unicode-путь с пробелами, обновление сразу после запуска без ожидания сети, сохранение DPAPI/очереди, полный раздел `HKCU\Software\Microsoft\Windows\CurrentVersion\Uninstall\<guid>`, чтение `InstallLocation` и отдельный fallback из `UninstallString`. Обработчик выхода регистрируется до `backendStart()`/`identify()`; после запроса на выход запуск не должен продолжаться. Для удаления прежних файлов при NSIS-обновлении используется короткое системное имя пути; ожидание внешнего NSIS ограничено 180 секундами. Опубликованные на момент ревью EXE сотрудника и руководителя имеют Authenticode `NotSigned` — это отдельный блокер доверенной поставки, а не ошибка подписи канала Ed25519.

Собирайте веб из каталога hard-desk в новый выходной каталог. esbuild включает относительные имена модулей в JS и CSS, поэтому рабочий каталог влияет на build ID. Ранее опубликованный 7ba798597656d038 был воспроизведён побайтово, кроме времени built_at в BUILD.json. Текущий опубликованный пакет — 3ee3a405d58129ca; его автоматический переход с предыдущего проверен в Chromium и WebKit, а независимая воспроизводимость этой конкретной сборки здесь не повторялась.
Проверьте переход со старой раздачи до выкладки. Сохраните предыдущие assets и конфигурацию, запишите operation_id и новый хеш. После размещения сравните SHA ресурсов по обоим входам — / и /mobile/. Убедитесь, что корневой ярлык открывается после обновления офлайн.

Сверьте SHA-256 точного EXE, опубликованного файла и копии доставки. При адресной раздаче с докачкой проверьте частичный запрос по HTTPS, статус 206 и Content-Range. Операционная квитанция связывает исходное дерево, канальные метаданные, точные файлы, результаты и путь отката.

## Миграция и переключение рабочего контура
### Роли базы данных
API работает с ограниченными правами приложения. У обмена отдельное подключение, у оператора миграции — права владельца схемы. Пути к файлам задаются через окружение и read-only mounts в Compose. Переменные HARD_CRM_DATABASE_URL_FILE и HARD_CRM_PRIMARY_DB выбирают выделенную базу и прежнюю SQLite для оператора. Исходную конфигурацию, имена образов, владельцев файлов и список mount points сверяйте до перехода.
### Репетиция на согласованной копии
1. Восстановите согласованный срез в отдельные каталоги. Зафиксируйте schema_version, namespace, счётчики событий и последнюю квитанцию. Проверьте права uid 1000 на документы, состояние mobile и каталог WAL у восстановленной primary.
2. Команда `python tools/crm_runtime.py migrate` обновляет выбранную схему. Для рабочей модели реестра есть отдельный `tools/crm_migrate_registry.py` и права из crm_registry_permissions.sql. Сверьте количество и содержимое бизнес-таблиц и повторную миграцию на копии.
3. Подготовьте файл выбранных UUID. Команда `python tools/crm_runtime.py plan --contracts selected.json` строит план для этого набора. Проверьте кредиторов, назначения и selection_sha256. С тем же файлом и хешем оператор использует activate. Сначала primary закрывает прежнюю запись, затем PostgreSQL открывает новую. Повтор после сбоя должен завершить тот же переход.
4. Проверьте первичный вход, импорт, назначение, звонок, выезд с фото и книгу отчёта. Проверьте отказ старой записи по переведённому КД и доступ по оставшимся договорам. Сохраните значение migration_receipt и подтверждение рабочего обмена.
### Адресное обслуживание
`logistics-staff --roster` проверяет состав пула по стране. Добавление --expected-sha256 применяет ровно проверенный состав. `contact-status --evidence` аналогично разделяет сверку и применение подтверждений отзыва. Операторские параметры и условия возврата описаны в deploy/crm/README.md. Для обычной правки интерфейса этот переход заново запускать не требуется.

## Резервное копирование и восстановление
### Что восстанавливать вместе
Согласованный срез включает логический дамп PostgreSQL, primary SQLite с аккаунтами и устройствами, документы по хешам, фото, квитанции, мобильное состояние, конфигурации и принадлежащие им ключи. `deploy/crm/backup_postgres.py` входит в процедуру резервного копирования. Живую SQLite с WAL копируйте через backup API либо при остановленных писателях. Доступ к секретам оформляется через владельца контура.
1. Зафиксируйте момент и последнюю принятую операцию. Сохраните состояние после сбоя. Для пробного восстановления используйте отдельную базу и совместимые роли. Восстановите дамп через pg_restore с --exit-on-error, верните файлы и соответствующие ключи.
2. Проверьте контрольные суммы, namespace, схему, соответствие отсечки двух БД, входы и права. Прочитайте ранее принятый выезд с фото. Проверьте журнал, отчёт и повтор известной операции на копии.
3. При возврате версии оболочки или образа отдельно оцените совместимость уже принятых записей. Смена контейнера откатывает код. После новых рабочих действий восстановление старого среза требует сверки и переноса этих действий.
### Типовые обращения
- Старый Windows получает 426. Сопоставьте продукт, версию клиента, требуемый минимум и feed. Если обновлятор повреждён, используйте точный проверенный установщик своего продукта поверх штатного профиля.
- Пропал договор. Сверьте постоянный UUID, кредитора, область, назначение, отзыв, вид работы и фильтры. Уточните свежесть офлайн-страницы. Проверка от имени другого сотрудника даёт другую область.
- Отправка висит. Найдите исходную операцию и зависимые документы, прочитайте квитанцию и состояние сервера. Для отчёта проверьте и исходного автора, и территорию. Для провала обмена найдите предпросмотр, intent, файл и его хеш.
- Health API вернул 503. Проверьте доступ к PostgreSQL, schema_version, namespace и heartbeat scheduler. Для обмена проверьте отдельный health и состояние последней операции. Нужные команды запуска и порядок возврата собраны в deploy/crm/README.md.

## Карта прежнего проекта и передача агенту
### Компоненты за пределами интерфейса CRM
ROOT `server/web.py`, accounts.py и account_access.py обслуживают прежние HTTP-маршруты и входы. Код прежней PWA хранится в server/miniapp/. handlers_field.py, геокодирование и маршрутные службы относятся к работе выездника. stt/ и server/stt_client.py обслуживают распознавание голоса прежнего контура. Рабочие функции Telegram, скоринга, карт и обслуживания описаны в docs/Система «Хард» — руководство инженера.md.
Каталоги `pult/` и `pult_ruk/` содержат прежние пульты, `hard-pult/` — нативную ветку, `registry_cycle/` — перенос между личными и общим реестрами. Для изменения разбора заголовков откройте docs/Колонки реестра — руководство инженера.md, для доступа и хранения — SECURITY.md. ROOT/deploy/README.md описывает установку серверной основы. SOURCE/deploy/crm/README.md описывает надстройку CRM.
### Как передать незавершённую работу
Укажите дерево, ветку, HEAD, изменённые и новые файлы, экран и роль, ожидаемый результат и минимальный синтетический пример. Приложите команды и результат теста, включая пропуски, точную версию клиента и серверного компонента. Для выпуска укажите путь к приватной квитанции, последний подтверждённый шаг и следующее допустимое действие.
Ключи, пароли, DSN, токены, выгрузки с клиентами, скриншоты рабочего кабинета и базы хранятся в приватном контуре. В общую документацию передавайте названия параметров, схему и примеры с учебными данными. Приложение, QA-профиль и рабочую очередь владельца держите раздельно.
### Что остаётся проверить при переносе проекта
Сопоставьте изменённый SOURCE с точными артефактами и согласованным origin. Проверьте сборку на чистой копии, восстановление стенда и основной цикл «импорт → назначение → работа → отчёт». По эксплуатации отдельно зафиксируйте физические Android/iPhone, рабочие курьерские составы, подтверждения оставшихся отзывов и свежесть внешних оплат. Статус и доказательства передачи обновляйте в корневой памяти проекта.
