# Спека для исполнителя — редизайн мини-аппы и разброс реестров по сотрудникам

Черновик, собран по итогам созвона с коллегами (скриншот-резюме) + уточнений Егора. Разделы независимы, реализовывать можно в любом порядке/параллельно.

Контекст проекта: hardbot (Telegram-бот + Mini App) — полевые агенты («выездники») ходят к должникам, вносят данные через мини-аппу; пульт (Tauri/Rust) на стороне офиса импортирует/экспортирует Excel-реестры через admin-API сервера (166.88.185.90, `/opt/hardbot`).

## Раздел 1. Разброс реестров по сотрудникам (замена/перенос логики «Скрипт СНГ»)

Источник: папка `Скрипт СНГ/` (была на личном ноуте Егора, скопирована в корень репозитория для сверки — реальный слепок целевой структуры лежит в `Скрипт СНГ/Путь/`).

### Что это сейчас — 5 python-скриптов на машине с примонтированным сетевым диском `U:\rbr\Развитие СНГ\...` (это и есть «сетевая шара/рабочий контур»)
- `Бэкап.py` — ежедневный бэкап всех файлов сотрудников в `Архив реестров/{ДД.ММ}/{Страна}/`.
- `Предпроверка.py` — валидация числа колонок (Soft=45 / Hard=51 колонок), пишет 2 xlsx-отчёта на Desktop, данные не трогает.
- `Сборка.py` — направление employee → мастер: собирает данные ИЗ личных xlsb сотрудников В мастер-реестр `ОБЩИЙ РЕЕСТР {МЕСЯЦ}.xlsb`.
- `Разборка.py` — **это и есть «разброс»**: направление мастер → employee, из мастер-реестра раскладывает строки по личным xlsb сотрудников.
- `Сборка разборка.py` — оркестратор: Бэкап → Предпроверка → Сборка → Разборка строго по цепочке, останавливается при ошибке любого шага.

### Целевая структура папок (подтверждено по реальному слепку в `Скрипт СНГ/Путь/`)
```
{Страна}/{Портфели.../}/{Город-или-Soft}/{ФИО сотрудника}/{ФИО сотрудника}.xlsb
```
Два корня сейчас: `Узбекистан/Портфели сотрудников УЗБ/` (города: Андижан, Самарканд, Ташкент, + ветка `Soft`) и `Таджикистан/Портфели отдела взыскания РТ/` (города: Душанбе, Худжанд, + ветка `Soft`). `Soft` — не город, а отдельная линейка продукта (см. ниже). Есть ещё `!Архив` — туда вручную переносят папки уволенных/неактивных сотрудников (имена часто с висящим «-»: «Мухиддинов Фирузхон -»); текущий скрипт `!Архив` явно не исключает при построении карты папок — защита от случайного совпадения чисто неявная.

### Алгоритм «Разборка» (то, что переносим в пульт)
1. **Карта папок сотрудников**: обход `{страна}/{Портфели...}/` на 2 уровня вниз (город-или-Soft → папка сотрудника), ключ — `ФИО.strip().lower()`, значение — список путей (имя может встречаться в нескольких местах на диске).
2. **Классификация колонок**: у мастер-реестра есть служебная 3-я строка листа «Портфели» с типом каждой колонки: `хард` / `сх` / что-то содержащее «софт». Сотрудник получает **hard-шаблон** (колонки хард+сх) или **soft-шаблон** (софт+сх) — что именно, определяется НЕ по данным строки, а по тому, что папка сотрудника лежит внутри папки с именем `Soft`.
3. **Список сотрудников** — уникальные непустые значения колонки «ответственный Сотрудник» по всем строкам мастер-реестра.
4. **Для каждого сотрудника**: если есть папка в карте — сгенерировать личный xlsb (нужный шаблон колонок), положить туда только строки, где «ответственный Сотрудник» точно (после strip) равен его ФИО. Если папки нет — **сейчас молча пропускается**, без лога и без ошибки (кандидат на исправление, см. открытые вопросы).
5. **Лист «Статистика»**: если у сотрудника уже был файл — его лист «Статистика» (обычно ручные формулы/заметки офиса) переносится в новый файл перед перезаписью, с починкой формул (вырезание ссылок на старое имя файла).

### Объём подтверждён Егором
- **Только Hard-портфель.** `hardbot/fields.py` и вся текущая схема пульта/hardbot описывают только его (файл-эталон в репозитории так и называется — «Хард.xlsb», докстрока `fields.py:1-10` подтверждает). «Soft» — параллельная линия с другим набором колонок (45 против 51 у Hard), которой в текущей БД/схеме hardbot нет вообще; она остаётся на старом Python-скрипте, в разброс пульта не входит.
- **«Сборка» (employee-xlsb → мастер) всё ещё нужна** — часть Hard-сотрудников пока ведёт данные в личном Excel-файле, а не через мини-аппу, поэтому этот путь остаётся рабочим, не отмирает.

### Как это стыкуется со старым циклом «Скрипт СНГ»
Раз «Сборка» жива, у данных сейчас фактически два источника правды: БД сервера hardbot (пишут те, кто на мини-аппе) и мастер-файл `ОБЩИЙ РЕЕСТР {МЕСЯЦ}.xlsb` на `U:\rbr\...` (пишут те, кто ещё в Excel, через «Сборку»). Пульт уже умеет импортировать xlsb-файл в сервер (`POST /admin/import.json`, см. [[pult_xlsx_architecture]]) — значит естественный цикл сведения в одну точку правды:

1. `Сборка.py` (как сейчас) — Excel-сотрудники → мастер-xlsb на `U:\`.
2. Импорт мастер-xlsb в сервер через пульт (уже есть, `import.json`) — теперь сервер знает и про Excel-, и про мини-апп-сотрудников.
3. Экспорт из сервера (`export.json`, уже есть) → **новый разброс** (этот раздел) — раскладка по личным xlsb, в том числе для тех, кто пока в Excel (им нужен свежий файл с их клиентами).

Т.е. новый разброс в пульте встаёт ПОСЛЕ шага 2, не заменяя «Сборку», а опираясь на то, что она уже слила Excel-правки в общий мастер перед импортом. Порядок шагов 1-3 стоит проговорить с Егором отдельно (кто и как часто их руками запускает), но с точки зрения кода это не блокирует реализацию разброса.

### Предлагаемая реализация в пульте (по аналогии с текущим `build_registry`, main.rs:134)
- Новая Rust-функция (условно `build_employee_registries`) — тот же `rust_xlsxwriter`, тот же контракт полей из fields-схемы экспорта, но с группировкой строк по `responsible` перед записью каждого файла.
- Матчинг сотрудник → папка: тот же принцип (`trim + lowercase`), но карту папок пульт строит сам сканированием выбранной корневой директории (диалог выбора через `rfd`, как уже сделано для «Сохранить как» в `save_registry_xlsx`, main.rs:278) — **не хардкодить `U:\rbr\...`**: сетевой диск монтируется по-разному на разных машинах (ровно та путаница с «личный ноут», из-за которой в этом разговоре не сразу нашли скрипт).
- Результат матчинга (кто нашёл папку / у кого не нашлось) — обязательно показать в пульте списком ДО записи: в исходном скрипте несовпадения тонут молча в консольном выводе, в GUI так нельзя.
- Лист «Статистика»: сохранение формул при живом Excel (xlwings/COM) в оригинале — в Rust (calamine на чтение + rust_xlsxwriter на запись, без живого Excel-движка) прямой перенос формул с починкой ссылок нетривиален. Нужно решение — см. открытые вопросы.

## Раздел 2. Редизайн мини-аппы: удобство заполнения + устойчивость к обрыву связи

### Текущее состояние (проверено по коду)
- Единственный файл фронтенда: `hardbot/miniapp/index.html` (775 строк), Telegram Mini App, состояние — в глобальном JS-объекте `STATE` (только в памяти вкладки браузера).
- Вкладка «Заполнить» — `panelForm()` (index.html:500-516): плоский список `<select>` по `HARD_FIELDS` (см. `hardbot/fields.py:155-156` — это `visit_date, visit_comment, contact_with, agreed_payment, who_at_address, client_location, purpose_rf, call_status, call_comment, city, address_customer`) + 2 `<textarea>` (`call_comment`, `tips`) + кнопка фото + одна кнопка «Сохранить визит».
- Сохранение — `saveVisit()` (index.html:549-561): единственная точка записи, собирает значения из DOM прямо в момент клика и шлёт `POST /api/save {rep, values, finish:true}`. До этого клика ничего никуда не уходит и нигде не хранится.
- Идентификация — уже автоматическая: `TG.initData` (Telegram WebApp SDK, подключён `<script src="https://telegram.org/js/telegram-web-app.js">`, index.html:8) уходит в заголовке `X-Init-Data` на каждый запрос (`authHeaders()`, index.html:231-237); есть резервный `X-Dev-Uid` для тестирования вне Telegram (`?dev_uid=...` в URL).
- Сервер (`hardbot/web.py`): `_auth()` (web.py:119-126) резолвит `uid` → `emp` (привязанный сотрудник) на каждый запрос — фронтенду для автосохранения ничего специально идентифицировать не нужно, сервер и так знает, чей это визит по `uid`.
- **Важно и хорошо:** `_save` (web.py:381-399) уже поддерживает промежуточное сохранение без явного дизайна с нуля — `values` пишутся в БД (`db.update_person`) при **любом** значении `finish`; `visit_date` + `log_visit` + уведомление группе (`_notify_group`) вешаются **только** на `finish:true`. То есть вызов `/api/save` с `finish:false` уже сегодня безопасен и не создаёт лишних визитов/уведомлений — это ровно то, что нужно для тихого автосохранения черновика на сервер, без изменений на бэкенде.
- Поля, разрешённые к сохранению, — вайтлист `ALLOWED_SAVE = FORM_DROPDOWNS | FORM_TEXT` (web.py:64) — валидация уже есть, автосохранение может слать те же values, что и сейчас.

### Требования
1. **Черновик формы не должен теряться** при обрыве связи, случайном закрытии вкладки/приложения, переключении между клиентами.
2. Разделить по смыслу два действия:
   - тихое периодическое сохранение черновика (не требует всех полей, не помечает визит завершённым);
   - явное «Сохранить визит» (текущая кнопка, `finish:true`, как сейчас).
3. Восстановление черновика при повторном открытии карточки того же клиента (тем же сотрудником) — без дополнительных действий пользователя.

### Технический подход (предложение, не жёсткое ТЗ — исполнитель может скорректировать в реализации)
- **Локальное хранилище черновика:** `localStorage` (это прод-приложение в WebView, а не артефакт исполнитель — ограничение на localStorage в артефактах сюда не относится).
- **Ключ:** `draft:${uidOrEmployee}:${rep}` — `uid` можно взять из `Telegram.WebApp.initDataUnsafe.user.id` на клиенте (не требует повторного похода на сервер); `rep` — идентификатор карточки клиента, уже используется в `STATE.cur.rep`.
- **Запись черновика:** на каждое изменение `<select>`/`<textarea>` в панели формы (`change`/`input` с debounce ~500мс) — сериализовать текущие значения формы в `localStorage`.
- **Восстановление:** в `openP()` / `renderDetail()` перед отрисовкой `panelForm` — проверить `localStorage` на черновик для `rep` + текущего пользователя; если есть — замёржить поверх значений с сервера (`d.form[].current`), визуально пометить как «черновик, не сохранён на сервере».
- **Фоновая отправка на сервер:** пока панель формы открыта и есть несинхронизированные изменения — раз в 20-30 сек слать `POST /api/save {rep, values, finish:false}` (тот же формат, что и `saveVisit()`, только `finish:false`); при успехе — не чистить localStorage сразу (оставить как локальный кэш до явного `finish:true`, чтобы не потерять данные при повторном обрыве сразу после отправки).
- **Очистка черновика:** только после успешного `finish:true` (текущий `saveVisit()`), аналогично сегодняшнему поведению.
- **`beforeunload`/`visibilitychange`:** best-effort попытка досрочной отправки при уходе со страницы — не гарантирована в мобильном WebView, поэтому не единственная линия защиты; `localStorage` — основной источник истины.

### Edge cases
- Один сотрудник, два клиента подряд — черновики не путать (ключ включает `rep`).
- Переключение вкладок внутри карточки (визит/клиент/долг/форма) не должно сбрасывать несохранённый черновик формы.
- Сервер отклонил фоновую отправку (сеть есть, но ошибка) — черновик остаётся в `localStorage`, следующая попытка на следующем интервале.
- Два устройства у одного сотрудника (редкий кейс) — черновики не синхронизируются между устройствами; это явное ограничение, а не баг.

### Что НЕ входит в этот раздел (осознанно не описано, т.к. Егор не давал конкретики)
- Визуальный редизайн формы (порядок полей, прогрессивное раскрытие условных полей, крупные кнопки статуса вместо `<select>` и т.п.) — из созвона понятно, что «дизайн переделать под удобство», но конкретных болевых точек не названо. исполнитель может либо (а) ограничиться черновиком/автосохранением без визуальных правок, либо (б) предложить визуальный вариант и согласовать с Егором до реализации — решение делегируется, не додумывается здесь произвольно.

### Приёмка
- Ручной сценарий: открыть карточку клиента → заполнить часть формы → авиарежим →
