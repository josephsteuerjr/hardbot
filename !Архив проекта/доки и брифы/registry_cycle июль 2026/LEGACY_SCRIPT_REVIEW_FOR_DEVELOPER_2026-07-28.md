## 2. Краткий вывод

Основная проблема была не в одной неправильной колонке. Первая версия имела
архитектуру:

```text
прочитать доступную часть live-файлов
→ сразу изменить live-общий
→ заменить live-личные книги новыми копиями
→ напечатать результат
```

Для однопользовательской утилиты это понятный первый подход. Для 59 совместно
используемых сетевых книг он оказался fail-open и нетранзакционным:

- ошибка одного источника не останавливала сборку;
- последнее прочитанное значение молча побеждало остальные;
- подготовка личных файлов происходила прямо в рабочих путях;
- частичный успех считался общим успехом;
- не было способа доказать, какие именно ячейки разрешалось изменить;
- после сбоя не было автоматического возврата всего комплекта к исходному
  состоянию.

Именно сочетание этих свойств создавало путь к исчезновению, возврату старых
значений и смешению данных. Один локальный `if` не мог полностью исправить эту
модель.

## 3. Что в первой версии было сделано хорошо

Сначала о сильных сторонах:

- месяц общего реестра вычислялся автоматически;
- КД нормализовался функцией `clean_id`, включая пробелы, `.0` и часть
  экспоненциальных представлений;
- сборка сопоставляла основные рабочие поля по названиям заголовков, а не по
  абсолютным номерам колонок;
- пустые личные значения не записывались поверх непустого общего;
- матрицы читались и записывались блоками, что заметно быстрее поклеточного COM;
- исходные личные книги при чтении открывались с `read_only=True`;
- была попытка разделить HARD/SOFT, сделать предпроверку и резервное
  копирование;
- использовался `try/finally` для закрытия основного Excel Application.

Это хорошие инстинкты для первой автоматизации. Недостающей частью была не
скорость, а модель согласованности и восстановления.

## 5. P0: частичная ошибка считалась допустимой сборкой

В `Сборка.py` каждый личный файл обрабатывался так:

```python
try:
    ...
except Exception as e:
    print(f"Ошибка чтения файла {file_path.name}: {e}")
```

После этого скрипт продолжал запись общего, если `updates_db` был непустым хотя
бы благодаря другим сотрудникам.

### Минимальный сценарий

1. Есть книги сотрудников A и B.
2. A прочиталась, B занята или повреждена.
3. Ошибка B только печатается.
4. Данные A записываются в live-общий.
5. Процесс завершается кодом `0`.
6. Launcher запускает разборку.
7. Книга B пересобирается из общего, хотя её свежие локальные правки не были
   собраны.

Так локальная ошибка чтения B превращается в возможную потерю несобранных
данных B.

Правильный принцип для такого цикла: **один обязательный источник не прочитан —
до live-записи не доходим вообще**.

## 6. P0: сообщение «критическая ошибка» не означало неуспешный процесс

Launcher доверял только `subprocess.returncode`:

```python
result = subprocess.run(...)
if result.returncode == 0:
    return True
```

Но дочерние скрипты в большинстве ошибок:

- печатали сообщение;
- делали `return`;
- ловили исключение и не пробрасывали его;
- вызывали `main()` без `sys.exit(main())`.

Например, общий `except` сборки:

```python
except Exception as e:
    print(f"[КРИТИЧЕСКАЯ ОШИБКА] ...")
finally:
    app.quit()
```

После такого Python штатно завершает процесс кодом `0`. Launcher пишет
«успешно завершён» и переходит к разборке.

Та же проблема есть у:

- `Бэкап.py`: ошибки отдельных копий только печатаются;
- `Предпроверка.py`: возвращаемый `False` не передаётся в exit code;
- `Разборка.py`: ошибки отдельных сотрудников ловятся с `continue`, итоговый
  процесс остаётся успешным.

Минимальный безопасный шаблон:

```python
def main() -> int:
    try:
        run()
    except ExpectedFailure as exc:
        log.error(...)
        return 2
    return 0

if __name__ == "__main__":
    raise SystemExit(main())
```

## 7. P0: разборка публиковала заготовку раньше её подготовки

`Разборка.py` сначала создавал на сетевом диске два полных профильных шаблона из
общего реестра. Затем для каждого сотрудника:

1. переименовывал действующую книгу в `~old_...xlsb`;
2. копировал полный HARD- или SOFT-шаблон сразу по live-пути;
3. добавлял файл в очередь последующей очистки;
4. лишь на следующей фазе открывал его и удалял строки других сотрудников.

Между шагами 2 и 4 рабочая книга сотрудника содержала все строки соответствующего
профиля. При аварии процесса такой файл оставался в live-папке.

Последствия:

- временное раскрытие чужих кейсов;
- при падении — постоянный недофильтрованный файл;
- старая рабочая книга уже недоступна под штатным именем;
- частично обработанный набор сотрудников;
- невозможность одним действием вернуть весь комплект назад.

Дополнительно `~temp_hard.xlsb` и `~temp_soft.xlsb` создавались рядом с общим на
`U:` и в конце файла не удалялись. Два параллельных запуска использовали бы одни
и те же имена.

Безопасный порядок обратный:

```text
локальный staging → полная проверка → backup live → атомарный replace
```

До последнего шага пользователь не должен видеть ни заготовку, ни частичный
результат.

## 8. P0: старый файл удалялся даже после ошибки переноса

Старая личная книга переименовывалась в `~old_...xlsb`. Перенос листа
`Статистика` находился в `try/except`, но удаление старой книги выполнялось в
`finally`:

```python
except Exception:
    print("Не удалось скопировать Статистику")
finally:
    if old_file_path.exists():
        os.remove(old_file_path)
```

То есть сообщение «не удалось скопировать» сопровождалось уничтожением
единственного локального источника, из которого копирование можно было
повторить.

Наличие отдельного `Бэкап.py` не делает этот шаг безопасным:

- общий реестр вообще не входил в backup;
- сбой копирования отдельного файла не останавливал backup;
- папка имела только дату `DD.MM`, поэтому повторный запуск того же дня
  перезаписывал одноимённую копию;
- файлы складывались плоско по стране без сохранения полного относительного
  пути;
- SHA и проверка полноты отсутствовали;
- путь был привязан к desktop конкретной учётной записи.

Backup становится гарантией только тогда, когда подтверждены список целей,
отпечаток каждой копии и возможность автоматического rollback.

## 9. P0: «дедупликация» фактически была `last write wins`

Хранилище обновлений имело форму:

```python
updates_db[client_id][col_name] = val
```

Оно сохраняло только одно значение и не сохраняло:

- путь источника;
- строку источника;
- владельца версии;
- предыдущую версию;
- факт наличия второго кандидата.

Если один КД находился в двух книгах, второе встреченное непустое значение
молча заменяло первое. Порядок `Path.glob()` не являлся бизнес-правилом и не
должен определять данные.

Это не семантическая дедупликация. Это молчаливое схлопывание кандидатов.

Правильная промежуточная модель:

```python
candidates[(contract_id, field)].append(
    Candidate(value, owner, path, row, fingerprint)
)
```

После сбора возможны только явные решения:

- один кандидат;
- несколько одинаковых кандидатов;
- доказуемое дополнение комментария;
- конфликт, блокирующий весь пакет.

Полезный тест-инвариант: перестановка порядка входных файлов не должна менять
план или digest.

## 10. P1: проверка ответственного защищала только три поля

При несовпадении ответственного старая версия пропускала:

- `Общий результат`;
- `Cтатус звонка`;
- `статус звонка софт`.

Все остальные непустые поля старой книги продолжали записываться в общий:

- платежи и прогноз;
- основной/дополнительный номер;
- даты;
- комментарии HARD/SOFT;
- результаты визита и контакта.

### Сценарий перераспределения

1. КД был у A и уже назначен B.
2. В книге A осталась старая строка.
3. Ответственные различаются.
4. Три статуса пропускаются.
5. Телефоны, платежи, даты и комментарии A всё равно попадают в строку B.
6. Если книга B тоже содержит КД, победителя определяет порядок обхода.

Это не управляемый handoff. Это частичное смешение версий.

Безопасное правило:

- канонический текущий владелец берётся из общего;
- старая книга может быть источником handoff только при точном доказательстве
  через `пред отв`;
- непустое значение нового владельца приоритетно;
- отсутствие доказательства означает read-only, а не перенос или удаление.

## 11. P1: пропущено жёлтое поле `Телефон глав`

В опубликованном `TARGET_COLUMNS` было 20 рабочих полей. Фактическая схема общего
содержит 21 жёлтое поле. Единственное отсутствующее:

```text
Телефон глав
```

Прямая цепочка:

1. сотрудник заполняет `Телефон глав` только в личной книге;
2. сборка игнорирует поле;
3. общий остаётся пустым или старым;
4. разборка создаёт новую личную книгу из общего;
5. локальный номер исчезает.

На свежем контрольном snapshot новый план обнаружил 1 169 изменений общего по
`Телефон глав`. Это показывает масштаб слепой зоны, но само по себе не доказывает,
что все 1 169 расхождений создал один запуск старого скрипта.

Инженерный вывод: список управляемых полей нельзя поддерживать вручную отдельно
от схемы. Перед каждым запуском фактический набор жёлтых заголовков должен
сравниваться с конфигурацией, а любое расхождение — блокировать цикл.

## 12. P1: обратная разборка не различала снятие и отсутствие данных

Личная книга создавалась заново из строк общего, где:

```python
responsible == employee
```

Всё остальное очищалось и удалялось. Не проверялось:

- действительно ли кейс передан;
- совпадает ли сотрудник с `пред отв`;
- временно ли строка отсутствует в общем;
- есть ли в личной строке уникальные данные, которых нет в общем;
- существует ли конфликт владельцев.

На свежем snapshot:

- 4 строки имеют доказанное снятие через `пред отв`;
- 9 личных строк отсутствуют в общем без доказательства удаления.

Новый контур удаляет только четыре доказанные строки и сохраняет девять
read-only. Старая разборка при обработке соответствующих сотрудников не включила
бы эти девять строк в новый файл.

Кроме того, найдено 76 непустых локальных значений `Телефон`/`Город` при пустом
общем. Старая модель пересоздания не имела passthrough-правила и могла заменить
их пустотой из общего.

## 13. P1: обнаружение файлов и профиля было неоднозначным

Разные части решения использовали разные правила:

- сборка и backup брали любой `*/*.xlsb`, исключая только `~$`;
- предпроверка считала SOFT любой путь, содержащий строку `soft`;
- разборка считала SOFT только книгу в папке, чей родитель называется `Soft`;
- соответствие владельцу строилось по точному имени папки;
- aliases и временные делегации отсутствовали.

Практические последствия:

- `~old_...xlsb`, оставшийся после сбоя, снова попадал в сборку, потому что он не
  начинается с `~$`;
- backup- и sidecar-копии могли стать активными источниками;
- SOFT-книга внутри HARD-папки могла получить неправильный профиль или быть
  пропущена;
- делегированная книга Турсунова в папке Курбаниязова не сопоставлялась по имени
  папки;
- ФИО с alias или отличием имени папки пропускалось;
- несколько одноимённых папок получали один и тот же шаблон, выбранный по первой
  найденной папке;
- Андижан обрабатывался всегда, хотя сейчас группа отключена;
- добавление новой группы требовало синхронно изменить несколько файлов.

В свежем discovery уже есть два реальных случая нескольких активных книг в одной
папке и одна явная временная делегация. Поэтому это не теоретическая крайность.

## 14. P1: предпроверка выглядела строже, чем была

`Предпроверка.py`:

- ожидала ровно 45 колонок для SOFT и 51 для HARD;
- при другом количестве только печатала warning;
- затем всё равно обрезала или дополняла каждую строку до жёсткого размера;
- определяла профиль по тексту пути;
- при ошибке файла продолжала обработку;
- сохраняла отчёты на desktop конкретного пользователя.

Есть также off-by-one:

- для 45-колоночного SOFT заголовки читались максимум до 44-й колонки;
- для 51-колоночного HARD — максимум до 50-й.

Даже возврат `False` из `main()` не превращался в ненулевой exit code. Поэтому
launcher не использовал предпроверку как gate.

Предпроверка полезна только при условии:

```text
любая ошибка структуры → нет плана → нет staging → нет публикации
```

## 15. P1: даты, формулы и вся строка общего

Старая сборка сравнивала даты после преобразования в `%d.%m.%Y`, а новое
datetime-значение записывала строкой:

```python
row[c_idx] = new_val.strftime("%d.%m.%Y")
```

Это:

- меняет тип Excel date на text;
- теряет время;
- не сохраняет исходное представление;
- может сделать визуально одинаковые, но типово разные значения.

После изменения хотя бы одной разрешённой ячейки обратно записывалась вся строка:

```python
ws_main.range(
    (current_excel_row, 1),
    (current_excel_row, last_col_idx),
).value = row
```

Следовательно, разрешение поменять одно поле фактически давало скрипту запись во
все колонки строки. Если в строке появится формула, `.value` превращает её в
вычисленное значение. Даже без формул возможен нежелательный round-trip типов.

Отдельно скрипт принудительно менял высоту всех строк общего на `15`, хотя это не
относилось к сборке данных.

Безопаснее писать только разрешённые ячейки и затем доказать, что всё остальное
совпало.

## 16. Почему проблема затрагивала не только пилот

Старая сборка обходила все перечисленные папки обеих стран, а разборка
индексировала все подпапки стран. В коде не было ограничения на участников
пилота бота.

Поэтому любой общий ночной запуск потенциально затрагивал весь обнаруженный
контур СНГ, независимо от того, работал ли конкретный сотрудник с ботом.

Это важно для расследования: совпадение по времени с пилотом не является
доказательством, что источником каждого дефекта был бот.

## 17. Что можно и нельзя приписать старой версии

### Номера

Для потери номеров есть прямой причинный путь:

- `Телефон глав` не собирался;
- `Телефон` не имел правила сохранения при пустом общем;
- личные книги пересоздавались из версии общего.

Это сильная техническая гипотеза происхождения части инцидентов.

### Разные версии комментария одного поля

Старая версия не выполняла дедупликацию комментариев. Она молча оставляла
последнюю встреченную версию `(КД, поле)`. Поэтому потеря одной из двух версий
или возврат старого комментария технически возможны.

### Новые требования

Не стоит считать дефектами первой версии требования, которые были сформулированы
позже:

- месячный архив аналитических платежей;
- отдельное обнуление двух жёлтых платёжных полей;
- owner-only уведомления;
- группа новых ГПХ;
- делегированный SMB force-close.

Это развитие продукта, а не ретроспективная вина автора.

## 18. Почему потребовалась новая архитектура, а не набор патчей

Локальными исправлениями можно было:

- добавить `Телефон глав`;
- вернуть правильный exit code;
- исключить `~old` и backup-файлы;
- убрать преобразование дат.

Но оставались бы фундаментальные риски:

- нет согласованного snapshot всех источников;
- нет baseline для различения правки сотрудника и аналитика;
- нет детерминированного разрешения нескольких кандидатов;
- staging находится в live-пути;
- нет полного diff;
- нет optimistic-lock;
- нет атомарной публикации комплекта;
- нет rollback.

Поэтому безопасный цикл строится иначе:

```text
discovery
→ стабильные локальные snapshot-копии
→ чистый детерминированный plan
→ локальный Excel-staging
→ полная validation
→ повторный live-preflight
→ backup каждой цели
→ атомарная публикация
→ postcheck и baseline
```

Это не «усложнение ради усложнения». Каждый слой закрывает конкретный путь
потери данных из предыдущих разделов.

## 19. Практические рекомендации автору

### 19.1. Делать merge чистой функцией

Вход:

- master snapshot;
- personal snapshots;
- baseline;
- конфигурация.

Выход:

- список клеточных изменений;
- личные проекции;
- warnings/errors;
- digest.

До получения этого объекта Excel и live-файлы не меняются.

### 19.2. Хранить provenance каждого кандидата

Для любого значения должны быть известны:

- КД;
- поле;
- значение и исходный тип;
- владелец;
- путь и строка источника;
- fingerprint файла.

### 19.3. Fail closed

Блокировать пакет, если:

- обязательная книга не прочитана;
- схема неожиданна;
- один КД имеет неоднозначного владельца;
- два источника независимо изменили одно поле;
- число изменений выше лимита;
- staging содержит незаявленный diff;
- live-файл изменился или занят.

### 19.4. Никогда не готовить результат по live-пути

Все преобразования Excel выполняются в отдельной локальной папке. В live
попадает только уже проверенный файл, и только через:

```text
backup → sibling temp → atomic replace → SHA postcheck
```

### 19.5. Считать частичный результат неуспехом

Если из 59 файлов опубликовано 30, это не «почти успешно». Нужен rollback 30
заменённых файлов либо явно незавершённая sidecar-транзакция без активации нового
baseline.

### 19.6. Не подавлять диагностические сигналы глобально

`warnings.filterwarnings("ignore")` и голые `except: pass` убирают информацию,
которая особенно нужна в файловой автоматизации. Лучше классифицировать
ожидаемые ошибки и сохранять структурированный JSON-журнал.

## 20. Минимальный набор тестов для подобных задач

1. Один обязательный файл не читается — live не меняется.
2. Один КД находится у двух сотрудников — порядок файлов не влияет на результат.
3. Два разных непустых значения — пакет блокируется.
4. Старый и новый ответственный — handoff только при доказанном `пред отв`.
5. КД отсутствует в общем — личная строка не удаляется автоматически.
6. В схеме добавилось жёлтое поле — запуск блокируется до обновления конфига.
7. `.`, `23.07..2026`, datetime со временем и число проходят буквальный
   round-trip там, где это требуется.
8. Формулы, фильтры, порядок листов и незатронутые ячейки не меняются.
9. Файл открыт до snapshot, после snapshot и перед replace.
10. Сбой после каждой N-й замены приводит к полному rollback.
11. Повторный запуск формирует тот же digest и не дублирует действия.
12. Backup проверяется по SHA и действительно восстанавливается.
13. Дочерний процесс при любой критической ошибке возвращает ненулевой exit code.

## 21. Главный инженерный урок

При автоматизации общих Excel-реестров основная задача — не «быстро перенести
значения». Основная задача — доказать четыре вещи:

1. прочитаны все нужные источники одной согласованной версии;
2. для каждой изменяемой ячейки известны источник и разрешающее правило;
3. ни одна другая ячейка не изменилась;
4. любой сбой оставляет весь комплект в старом либо полностью новом состоянии.

Предыдущая версия хорошо решала задачу скорости массовой обработки. Следующий
уровень опыта — проектировать файловую автоматизацию как транзакцию с
конфликтами, журналом и доказуемым rollback.
