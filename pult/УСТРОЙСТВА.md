# Админское устройство: как задать и как отобрать

**Мастер-ключ больше не открывает данные.** После того как на сервере привязано
хоть одно устройство, `ADMIN_API_KEY` умеет ровно две вещи: привязать устройство
и отозвать устройство. Ни выгрузить реестр, ни загрузить его, ни посмотреть
карточку им нельзя — и это главное изменение.

Обычный путь привязки — **одноразовый код**, который выдают на сервере. Право
впустить новую машину привязано к доступу к серверу, а не к знанию строки из
`.env`: код рождается там же, где живут данные, и гаснет при первом обмене.

## Задать устройство по коду (обычный путь)

1. На сервере выдать код:

   ```bash
   cd /opt/hard/deploy/units/core
   docker compose exec -T app python /app/admin_access.py issue --name "Ноут дома"
   ```

   Код печатается **один раз**: на сервере остаётся только его хэш, поэтому
   «посмотреть код позже» нельзя — можно лишь выдать новый.

   Роли две: `operator` (по умолчанию) — пульт аналитика, `engineer` — панель
   обслуживания сервера. Роль вписана в сам код и при обмене не выбирается.

   Мелочь для Windows: если запускаешь эту команду из Git Bash, добавь спереди
   `MSYS_NO_PATHCONV=1`. Иначе оболочка перепишет `/app/admin_access.py` в
   `C:/Program Files/Git/app/...`, и питон ответит «нет такого файла» про
   существующий файл. На сервере, где это и выполняется, ничего добавлять не надо.

2. Пульт → вкладка **«Сервер»** → **«Привязать по коду»**. Вставить код, задать
   имя устройства. Имя видно в списке — называй так, чтобы через месяц понять,
   что отзываешь.

3. Готово. В настройках пульта остаётся только токен; код погас и второй раз не
   сработает.

Посмотреть, что выдано и что уже обменяно:

```bash
docker compose exec -T app python /app/admin_access.py codes --all
docker compose exec -T app python /app/admin_access.py devices
```

## Задать устройство мастер-ключом (аварийный путь)

Нужен, когда выдать код некому — например, вы и есть тот, кто у сервера, а лезть
в контейнер не хочется. Кнопка **«Привязать мастер-ключом»**, ключ вводится в
поле «Admin-ключ» и после привязки не сохраняется.

Ключ узнать или сменить — на сервере:

```bash
grep '^ADMIN_API_KEY=' /opt/hardbot2/.env
```

## Откуда берутся сами секреты

Это два разных секрета, и генерируют их разные стороны.

**Мастер-ключ** (`ADMIN_API_KEY`) живёт в `.env` сервера. Его заводит и меняет
тот, у кого есть доступ к серверу — то есть да, «тот, у кого пароль от сервера».
Плановая смена на контуре владельца делается owner-скриптом ротации из `_local/`:
он генерирует новое значение сам, кладёт его в `.env` по месту и перезапускает
контейнер, не показывая ключ в командной строке и логах. Руками ключ придумывать
не надо.

**Токен устройства** генерирует **сервер**, а не человек: при нажатии «Привязать
это устройство» он создаёт случайный токен, отдаёт его пульту **один раз** в
ответе и сохраняет у себя только SHA-256. Поэтому «посмотреть токен на сервере»
нельзя — там его нет. Потеряли — привязывайте заново; старый токен той же машины
при этом гасится.

Доступ к серверу нужен только для первого: чтобы узнать или сменить мастер-ключ.
Выдать себе токен устройства может любой, у кого мастер-ключ уже есть.

## Отобрать

Две разные кнопки, и путать их не надо:

| Что нажать | Что происходит |
|---|---|
| **«Отвязать это устройство»** | пульт забывает токен ЗДЕСЬ. На сервере токен остаётся действующим. Это «я больше не хочу хранить доступ на этой машине». |
| **«Отозвать»** в списке устройств | токен гасится НА СЕРВЕРЕ немедленно и нигде больше не работает. Это «ноутбук потерян». |

Отзыв требует мастер-ключа — вставь его в поле выше перед нажатием. Так сделано
намеренно: иначе укравший ноутбук привязал бы себе второе устройство и отозвал
все остальные, заперев тебя снаружи, а сам остался бы внутри.

## Если отозвал всё и остался без доступа

Мастер-ключ **по-прежнему умеет привязать устройство** — это и есть путь
восстановления. Вставляешь ключ в поле, жмёшь «Привязать мастер-ключом», и у
тебя снова есть рабочее устройство. Данные при этом ключ не открывает ни на
секунду: он выдаёт токен, дальше работает токен.

Обратной дороги у этого нет намеренно. Мастер-ключ теряет право на данные при
первой же привязке в жизни сервера и не получает его назад, даже если отозвать
все устройства. Иначе тот, кто раздобыл ключ, отозвал бы всё (отзыв ключу
разрешён) и вернул себе полный доступ — «одна строка открывает всё» вернулось бы
через два шага и выглядело бы как штатное восстановление.

## Что это даёт

- **Утёкший мастер-ключ не открывает данные вообще.** Максимум, что им можно, —
  привязать устройство, а это видно в списке устройств поимённо.
- **Утёкший токен не работает на чужой машине.** Отпечаток сверяется на каждом
  запросе, а не только при выдаче: скопированный файл настроек бесполезен.
- **Утёкший код привязки почти наверняка мёртв**: он одноразовый. А если ещё
  не обменян — это видно в `admin_access.py codes`.
- **Потерянный ноутбук отзывается по одному.** Ключ менять не нужно, остальные
  устройства продолжают работать.
- **В аудите видно устройство**, а не просто «кто-то с admin-ключом».
- В базе лежит SHA-256 токена, а не токен: дамп таблицы войти не даёт.

## Мелочи, о которые можно споткнуться

- **Повторная привязка с той же машины гасит прежний токен**, а не заводит второе
  устройство. Переустановил пульт — привязал заново, список не зарастает.
- Отпечаток машины считается из имени компьютера, MAC-адреса и имени пользователя,
  и уезжает на сервер **хэшем**. Смена железа или переименование ПК = новое
  устройство; старое надо отозвать руками. Теперь это не только про повторную
  привязку: отпечаток идёт с КАЖДЫМ запросом, и после переименования ПК прежний
  токен перестанет работать сразу — привяжись заново по новому коду.
- Сброс базы перед ограниченным тестом устройства **не трогает**: он чистит данные
  взыскания, а не выбивает пульт наружу посреди процедуры.
